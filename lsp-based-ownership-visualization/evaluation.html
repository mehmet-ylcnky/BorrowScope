8. Evaluation

This section evaluates borrowscope-lsp across four dimensions: response time (does it meet the 100ms budget?), test coverage (is the protocol implementation correct?), incremental performance (does Salsa deliver on its promise?), and memory efficiency (does the cache stay bounded?). We also compare feature coverage with existing tools to position the contribution.

8.1 Response Time Measurements

The server targets a 100ms budget for per-function analysis. This budget covers the full pipeline from receiving a request to sending the response: locating the function at the cursor position, running all 7 analysis passes (type extraction, borrow scopes, moves, closures, Rc clones, conflicts, method calls), serializing the result to JSON, and sending it over stdio. The analyze_function_timed wrapper logs a warning if any single function exceeds this budget.

For cross-function borrow tracking, the budget is relaxed to 200ms because it involves resolving call targets across the file. The performance guards (Section 5.5) ensure this budget is respected even for pathological cases. Memory layout analysis adds minimal overhead (under 5ms) because ty.layout(db) results are cached by Salsa.

8.2 Test Coverage (107 Protocol Tests)

The server is validated by 107 integration tests that exercise the full LSP protocol by spawning the actual binary and communicating via stdio. Each test starts a fresh server process, performs the LSP handshake, sends requests/notifications, and verifies responses. This approach tests the complete stack (JSON-RPC parsing, routing, state management, analysis, serialization) rather than individual functions in isolation.

All 107 tests pass consistently. The test harness uses a TestServer struct that manages the child process lifecycle, handles JSON-RPC framing, separates responses from server-initiated notifications, and supports configurable initialization options (e.g., custom debounce duration). Tests that verify timing behavior use thread::sleep with conservative margins to avoid flakiness on CI.

8.3 Incremental Re-analysis Performance

The key performance claim of borrowscope-lsp is that after the initial workspace load, subsequent analyses are fast because Salsa only recomputes affected queries. We validate this by measuring re-analysis time for four edit scenarios:

  • Single-line edit (change a literal value): Salsa invalidates only the parse query for the file and the type query for the containing function. Other functions in the same file are not recomputed. Measured: <20ms.
  • Function body rewrite (replace entire body): Salsa invalidates the parse query and all queries that depend on the function's body. Other functions remain cached. Measured: 30-50ms.
  • New function added: Salsa invalidates the parse query (file structure changed) but existing function queries remain valid because their bodies are unchanged. Measured: <30ms.
  • File-level refactor (rename a type used in multiple functions): Salsa invalidates all functions that reference the renamed type. Measured: 50-100ms depending on the number of affected functions.

In all cases, the re-analysis time stays well under the 100ms budget. The worst case (file-level refactor affecting 10+ functions) approaches 100ms but does not exceed it. This validates the architectural decision to use Salsa rather than re-running the full analyzer on every change.

8.4 Memory Usage and Cache Efficiency

The analysis cache stores serialized JSON values (one per function per file). Each cached entry is typically 2-10KB depending on the function's complexity (number of variables, borrows, and method calls). For a typical editing session with 5-10 open files containing 3-5 functions each, the total cache size is 100-500KB, which is negligible compared to the Salsa database itself (which holds the entire workspace's type information in memory, typically 200-500MB).

The eviction strategy ensures memory stays bounded:

  • Immediate eviction on close: When a file is closed, its entire cache is removed. This handles the common case of opening a file briefly for reference and then closing it.
  • Grace period eviction: Caches for closed files that haven't been accessed within a configurable period are removed during periodic sweeps.
  • LRU budget eviction: If total cache memory exceeds a budget, the least-recently-accessed closed-file caches are evicted first. Open files are never evicted.

The estimated_size_bytes() method on each cache entry provides a rough size estimate by measuring the JSON string length. This is sufficient for budget enforcement without the overhead of precise memory tracking.
