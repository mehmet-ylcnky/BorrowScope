5. Cross-Function Borrow Tracking

Standard borrow scope computation (Section 4.3) operates within a single function body. It finds the last use of a reference variable and reports the scope as the range from declaration to last use. However, when a reference is passed to another function as an argument, the borrow extends beyond the caller's visible scope into the callee. Understanding these cross-function borrows is essential for reasoning about why certain operations are blocked: the borrow checker may reject code because a reference is still alive inside a called function, even though the caller never uses it again after the call.

5.1 Problem: Borrows That Escape Function Boundaries

Consider a function that creates a reference and passes it to a helper. From the caller's perspective, the reference is "used" at the call site and the borrow scope ends there. But from the program's perspective, the borrow is alive for the entire duration of the callee's execution. If the callee stores the reference, passes it further, or holds it across an await point, the borrow may live much longer than the caller expects.

The challenge is that the LSP server must answer the question "where does this borrow go?" without performing whole-program analysis. We cannot trace through every possible callee recursively (that would be unbounded in time and complexity). Instead, we resolve one level: for each call site that passes a reference, we identify the target function and the parameter that receives it. This gives the developer immediate visibility into where their borrows flow without requiring deep interprocedural analysis. 

fn process(data: &mut Vec<i32>) {
    data.push(42);
    validate(data);  // borrow flows further into validate()
}

fn main() {
    let mut items = vec![1, 2, 3];
    process(&mut items);  // &mut items flows into process::data
    items.push(4);         // OK: borrow returned
}

In this example, the &mut items borrow crosses into process() as the parameter data, and then flows further into validate(). The engine traces the first hop (main -> process) and reports it as a cross-function borrow with the parameter name, file location, and mutability.

5.2 Call Target Resolution via sema.resolve_path

For each CallExpr in the function body, the engine checks whether any argument is a reference type (via sema.type_of_expr(&arg).is_reference()). If so, it resolves the callee by extracting the path expression from the call and invoking sema.resolve_path(&path). If the resolution is PathResolution::Def(ModuleDef::Function(f)), the engine has the target hir::Function and can extract its name, source file, and parameter names.

The source file is obtained via f.source(db), which returns an InFile containing the file ID. This file ID is converted to a VFS path for display. Parameter names are extracted via f.params_without_self(db), which returns each parameter with its name and type. The engine matches arguments to parameters by position (argument index corresponds to parameter index), giving a clear mapping from "this variable in the caller" to "this parameter in the callee". 

fn resolve_call_target(sema, db, callee: &ast::Expr) -> Option<(String, String, Vec<String>)> {
    let path_expr = ast::PathExpr::cast(callee.syntax().clone())?;
    let path = path_expr.path()?;
    let resolution = sema.resolve_path(&path)?;

    match resolution {
        hir::PathResolution::Def(hir::ModuleDef::Function(f)) => {
            let name = f.name(db).to_string();
            let file_path = f.source(db).map(|s| {
                let file_id = s.file_id.original_file(db).file_id(db);
                format!("file_id:{}", file_id.index())
            }).unwrap_or_default();
            let params = f.params_without_self(db).iter()
                .map(|p| p.name(db).map(|n| n.to_string()).unwrap_or("_".into()))
                .collect();
            Some((name, file_path, params))
        }
        _ => None,
    }
}

5.3 Method Receiver Analysis via self_param.access

Method calls (data.process()) are handled separately from function calls because the receiver is an implicit argument. The engine resolves the method via sema.resolve_method_call(&method_call) to get the hir::Function, then checks func.self_param(db) to determine if the method takes &self (shared borrow of receiver), &mut self (exclusive borrow), or self (consuming move). Only the first two cases create cross-function borrows; the third is a move (handled by Section 4.4).

When a method borrows the receiver, the engine creates a CrossFunctionBorrow with the receiver variable as the origin and "self" as the parameter name in the callee. The mutability is determined by self_param.access(db): Access::Shared produces a shared cross-function borrow, Access::Exclusive produces a mutable one. This captures the common pattern where vec.sort() creates an exclusive borrow that extends into the sort implementation.

5.4 Borrow Path Construction

Each detected cross-function borrow is represented as a CrossFunctionBorrow struct containing a path of segments. The path describes the journey of the reference from its origin in the caller to its destination in the callee. Each segment records: the file path, function name, variable name, start/end lines, mutability, and a kind tag (Origin, Parameter, PassThrough, or Return).

For a simple case like process(&data), the path has two segments: an Origin segment (variable data in the caller at the call site line) and a Parameter segment (parameter data in process()). For method calls, the Parameter segment uses "self" as the variable name. The file_id:N references in the path are resolved to actual file paths by the request handler before sending the response to the client, using the VFS to map file IDs back to paths.

5.5 Performance Guards (Time Budget, Max Results)

Cross-function analysis iterates over every call expression and method call in a function body, resolving each one semantically. For large functions with many call sites, this can become expensive. Two guards prevent the analysis from blocking the LSP response:

  • MAX_CROSS_BORROWS = 50: The analysis stops collecting results after 50 cross-function borrows. For most functions, the actual count is well under 10. The cap protects against pathological cases (e.g., a function that calls 200 helper functions with reference arguments).
  • MAX_CROSS_ANALYSIS_TIME_MS = 200: The analysis checks elapsed time on each iteration and aborts if it exceeds 200ms. This ensures that even if individual call resolutions are slow (e.g., resolving into deeply nested dependency crates), the total response time stays bounded.

Both guards are checked at the top of the iteration loop, before processing each call expression. When either limit is hit, the analysis returns whatever results it has collected so far. The response does not indicate truncation explicitly; the client receives a partial but valid result. In practice, these guards are rarely triggered: typical functions complete cross-function analysis in under 20ms with fewer than 10 results. 

const MAX_CROSS_BORROWS: usize = 50;
const MAX_CROSS_ANALYSIS_TIME_MS: u64 = 200;

let start_time = std::time::Instant::now();

for node in body.syntax().descendants() {
    // Performance guards: abort if limits exceeded
    if results.len() >= MAX_CROSS_BORROWS { break; }
    if start_time.elapsed().as_millis() >= MAX_CROSS_ANALYSIS_TIME_MS as u128 { break; }

    // ... resolve call targets and collect cross-function borrows
}
