Abstract

The BorrowScope project previously established two components for understanding Rust ownership at runtime: borrowscope-runtime, which records 88 event types during program execution, and borrowscope-macro, a procedural macro that instruments source code with tracking calls. A critical finding from that work was that the macro requires a static type-info.json file, produced by the borrowscope-analyzer, to make semantic decisions about how to instrument each variable. Without this file, the macro cannot distinguish an Rc::clone from a generic .clone(), or a Cow::Borrowed from a Cow::Owned. This dependency on pre-computed type information revealed a fundamental gap: the runtime pipeline requires compilation and execution to produce results, sees only one execution path per run, provides no feedback during the development process itself, and the type-info.json file becomes stale the moment the source code changes, requiring a full re-analysis cycle to update.

This paper presents borrowscope-lsp, a Language Server Protocol implementation that brings the same semantic ownership analysis directly into the editor, in real-time, without requiring compilation or execution. Built on the ra_ap_* crate ecosystem (the same semantic engine that powers rust-analyzer), the server performs full type extraction, borrow scope computation, move detection, closure capture analysis, Rc/Arc clone tracking, and conflict detection. All of this is computed from the same compiler-grade type information that the analyzer produces as type-info.json, but on-demand as the developer types. Where the runtime shows what did happen along one execution path, the LSP shows what could happen across all paths simultaneously.

The three components are designed to form a complementary system: the LSP provides instant static feedback (all paths, no compilation), the runtime provides precise dynamic truth (actual reference counts, real drop order, exact timing), and a future VS Code extension can merge both views with divergence detection, highlighting where static prediction differs from observed runtime behavior. The LSP server exposes 5 custom requests (ownershipGraph, borrowScopes, variableInfo, crossFunctionBorrows, memoryLayout) plus standard LSP features (CodeLens, InlayHints, Hover, Diagnostics), validated by 107 integration tests. Analysis completes within a 100ms budget per function, enabled by Salsa's incremental computation model and a debounced change pipeline that prevents thrashing during rapid editing.
