7. Real-Time Editor Integration

The analysis engine (Section 4) produces ownership information on demand. But delivering it to the developer in real-time requires careful orchestration: changes must be debounced to avoid thrashing, results must be cached to serve stale data during re-analysis, notifications must be filtered to avoid unnecessary UI updates, and multiple LSP features (CodeLens, InlayHints, Hover, Diagnostics) must present the information in complementary ways. This section describes the integration layer that connects the analysis engine to the editor.

7.1 Debounced Analysis Pipeline

When a developer types, the editor sends a textDocument/didChange notification for every keystroke (or batch of keystrokes, depending on the editor's buffering). Running full ownership analysis on every change would be wasteful: most intermediate states (mid-word, incomplete expressions) are not meaningful for analysis. The server implements a debounce mechanism that delays analysis until the developer pauses typing.

The debounce duration defaults to 300ms and is configurable via initializationOptions.debounceMs. When a change arrives, the server stores the new content immediately (so subsequent requests see the latest text) but only marks the change as "pending." The main loop checks on every iteration (50ms polling) whether the debounce timer has expired. When it has, the server flushes all pending changes in a single batch: marks cached analysis as stale, applies VFS changes to the Salsa database, sends borrowscope/analysisUpdated notifications for affected functions, and publishes diagnostics.

Setting debounceMs to 0 disables debouncing entirely, causing analysis to fire on the next main loop iteration (within 50ms). This is useful for testing but not recommended for production use, as it increases CPU usage during rapid typing without providing meaningful intermediate results.

7.2 Smart Notification Filtering (Only Affected Functions)

When the debounce timer fires and analysis runs, the server sends a borrowscope/analysisUpdated notification to the client listing which functions were affected by the change. This allows the client to re-render only the relevant portions of its UI (e.g., update the graph panel only if the currently displayed function changed). Without this filtering, every keystroke would cause a full UI refresh.

The filtering works by comparing the previous file content with the new content at the function level. The server extracts function names and bodies from both versions using a lightweight brace-counting parser (not a full AST parse, since the file may be in an incomplete state). It then reports three categories of affected functions: newly added functions (present in new but not old), removed functions (present in old but not new), and modified functions (present in both but with different body text). Functions whose bodies are identical between versions are not reported.

This means that adding a comment outside any function body, or editing whitespace, produces no notification at all. Only changes that affect the ownership structure of a function (adding/removing variables, changing types, modifying control flow) trigger a notification. This dramatically reduces the notification frequency in practice: during a typical editing session, most keystrokes affect only one function at a time. 

fn send_analysis_updated_if_changed(sender, uri, previous, current) {
    let old_bodies = extract_function_bodies(previous);
    let new_bodies = extract_function_bodies(current);
    let mut affected: Vec<String> = Vec::new();

    // New functions
    for f in &new_functions {
        if !old_functions.contains(f) { affected.push(f.clone()); }
    }
    // Changed functions (body differs)
    for f in &new_functions {
        if old_bodies.get(f) != new_bodies.get(f) { affected.push(f.clone()); }
    }

    if !affected.is_empty() {
        send_notification(sender, uri, &affected);
    }
    // If nothing changed: no notification sent at all
}

7.3 Analysis Cache (Fresh/Stale States)

The server maintains a per-file, per-function analysis cache with two states: Ready (fresh result from the latest analysis) and Stale (previous result, file has changed since). When a file changes, all cached entries for that file are marked Stale. When a request arrives for a function that has a Stale entry, the server returns the stale data with a _stale: true flag, allowing the client to display it (perhaps grayed out) while fresh analysis runs in the background.

This approach ensures that the UI is never empty: even during the debounce window or while Salsa recomputes, the client has something to display. The staleness flag lets the client indicate visually that the data may be outdated (e.g., by showing a subtle "updating..." indicator). Once fresh results are available, the next request returns them with _stale: false.

Memory management is handled by two eviction strategies. First, when a file is closed (textDocument/didClose), its cache is cleared immediately. Second, a background eviction pass removes caches for closed files that haven't been accessed within a configurable grace period. Third, if total cache memory exceeds a budget, the least-recently-accessed closed-file caches are evicted first (LRU). Open files are never evicted regardless of memory pressure. 

pub enum AnalysisState {
    Ready(serde_json::Value),  // Fresh result
    Stale(serde_json::Value),  // Previous result, file changed
}

impl AnalysisCache {
    pub fn mark_all_stale(&mut self) {
        for state in self.functions.values_mut() {
            if let AnalysisState::Ready(v) = state.clone() {
                *state = AnalysisState::Stale(v);
            }
        }
    }
}

7.4 CodeLens: Per-Function Ownership Summary

CodeLens is a standard LSP feature that displays actionable text above code elements. The server generates two CodeLens entries above each function signature. The first shows ownership statistics: variable count, borrow count, move count, and conflict count. If conflicts are detected, the text includes an exclamation mark to draw attention. The second shows memory layout summary: total stack size, estimated heap size, and pointer count.

Both CodeLens entries are clickable. They trigger the borrowscope.showGraph command with the file URI and function name as arguments, which a client extension can use to open a detailed visualization panel. The CodeLens text is computed by running the full analyze_function and analyze_memory_layout passes for each function in the file, which is efficient because Salsa caches the underlying queries across functions.

7.5 InlayHints: Inline Ownership Annotations

InlayHints are small text labels displayed inline with the code, after variable names or type annotations. The server generates ownership category hints for variables with non-trivial ownership: [&] for shared references, [&mut] for mutable references, [Rc] for reference-counted pointers, [Arc] for atomic reference-counted pointers, [Cell] for interior mutability types, [*ptr] for raw pointers, and [closure] for closure types. Plain owned values and Copy types do not receive hints, keeping the display clean.

Hints are filtered to the visible range requested by the editor (the range parameter in the textDocument/inlayHint request). This means the server only computes hints for functions that overlap with the viewport, avoiding unnecessary work for large files where most functions are scrolled out of view. Each hint is positioned at the end of the variable name (column = declaration column + name length) with left padding for visual separation from the code.

7.6 Hover: Rich Ownership Tooltips

When the developer hovers over a variable declaration line, the server returns a markdown-formatted tooltip containing comprehensive ownership information for that variable. The tooltip includes: the variable name and type, ownership category, whether it implements Copy, which variables borrow from it, which variables it borrows from, where it is moved to (if applicable), and its layout size in bytes.

The hover handler finds the function containing the cursor position, runs analyze_function to get the full ownership summary, then locates the variable whose declaration line matches the hover line. All relationship information (borrowed-by, borrows-from, moved-to) is extracted from the summary's borrow scopes and moves lists. The result is formatted as markdown with bold labels and inline code for type names, which the editor renders as a rich tooltip popup.

Hover is one of the requests that requires the workspace to be loaded (it needs semantic type information). Before the workspace is ready, hover returns null, and the editor shows no tooltip. This is preferable to showing incorrect or incomplete information based on heuristics.

7.7 publishDiagnostics: Borrow Conflict Warnings

When the debounced analysis detects borrow conflicts (Section 4.7), the server publishes them as standard LSP diagnostics via the textDocument/publishDiagnostics notification. Each conflict becomes a diagnostic with severity "Information" (not Error or Warning, since the Rust compiler already reports actual borrow errors). The diagnostic message explains the conflict in plain language: which two borrows overlap, which variable they target, and on which lines the overlap occurs.

Each diagnostic includes relatedInformation entries pointing to both borrow sites, allowing the editor to show "related" links that jump between the two conflicting borrows. The diagnostic range covers the overlap region (from overlap_start_line to overlap_end_line), so the squiggly underline appears exactly where both borrows are simultaneously active. The source is set to "BorrowScope" to distinguish these diagnostics from compiler errors or clippy warnings.

When a file changes and the new analysis finds no conflicts, the server publishes an empty diagnostics array for that file, clearing any previously shown conflict indicators. This ensures that fixing a conflict immediately removes the visual feedback without requiring a save or rebuild. 

// Convert each detected conflict into an LSP diagnostic
for conflict in &summary.conflicts {
    diagnostics.push(json!({
        "range": {
            "start": {"line": conflict.overlap_start_line - 1, "character": 0},
            "end": {"line": conflict.overlap_end_line - 1, "character": 0}
        },
        "severity": 3, // Information
        "source": "BorrowScope",
        "message": format!("`{}` and `{}` both borrow `{}`",
            conflict.borrow_a, conflict.borrow_b, conflict.variable),
        "relatedInformation": [
            { "location": { "uri": uri, "range": ... },
              "message": format!("First borrow (`{}`) here", conflict.borrow_a) },
            { "location": { "uri": uri, "range": ... },
              "message": format!("Second borrow (`{}`) here", conflict.borrow_b) }
        ]
    }));
}

7.8 VS Code WebView Panel Integration

The LSP server provides all the data needed for rich visualization through its custom requests. A potential VS Code extension can consume the borrowscope/ownershipGraph response and render it as an interactive force-directed graph in a WebView panel. In this model, nodes represent variables (colored by ownership category: blue for owned, green for shared references, red for mutable references, purple for Rc/Arc), and edges represent relationships (solid for borrows, dashed for moves, dotted for clones).

The borrowscope/analysisUpdated notification enables real-time updates: when the developer edits a function, the extension receives a notification listing the affected function names. If the currently displayed function is in that list, the extension re-requests the ownership graph and re-renders the panel. Functions not in the list are not re-rendered, avoiding unnecessary visual disruption.
