6. Memory Layout Visualization

Understanding how Rust variables are laid out in memory is essential for performance reasoning, unsafe code correctness, and FFI interoperability. The borrowscope/memoryLayout request reconstructs the stack frame of a function, identifies heap allocations, and maps pointer relationships between variables. All information is derived from the Salsa type database using ty.layout(db) for sizes and alignments, ty.fields(db) for struct internals, and ADT path resolution for category classification. No runtime observation is needed.

6.1 Stack Frame Reconstruction

For each function, the engine iterates all let bindings and simulates stack allocation. For each variable, it queries ty.layout(db) to obtain the size (in bytes) and alignment requirement. The offset is computed by aligning the current stack pointer to the variable's alignment, then advancing by its size. The result is a StackFrame struct containing the total frame size and a list of StackVariable entries, each with its name, type, offset, size, alignment, declaration line, and last-use line.

The alignment simulation follows the same rules as the Rust compiler: each variable's offset must be a multiple of its alignment. For example, a u8 (align 1) can start at any offset, but a u64 (align 8) must start at an offset divisible by 8. If the previous variable ends at offset 5 and the next requires alignment 8, the engine inserts 3 bytes of padding (advancing to offset 8). This padding is not explicitly stored but is visible as gaps in the offset sequence.

The last-use line for each variable is computed using the same Definition::usages mechanism from Section 4.3. This allows the visualization to show variable lifetimes within the stack frame: a variable that is dropped early frees its stack slot for reuse (though the Rust compiler may or may not actually reuse it depending on optimization level). 

let mut current_offset: u64 = 0;

for let_stmt in body.syntax().descendants().filter_map(ast::LetStmt::cast) {
    let ty = sema.type_of_expr(&init)?.original;
    let (size, alignment) = match ty.layout(db) {
        Ok(layout) => (layout.size(), layout.align()),
        Err(_) => (0, 1),  // Unknown layout: skip gracefully
    };

    // Align offset to variable's alignment requirement
    if alignment > 0 {
        current_offset = (current_offset + alignment - 1) & !(alignment - 1);
    }

    stack_vars.push(StackVariable {
        name, type_display, offset: current_offset, size, alignment, line, end_line, ..
    });
    current_offset += size;
}

6.2 Field-Level Layout for Standard Library Types

Many standard library types have well-known internal layouts that are stable across Rust versions. The engine provides hardcoded field decompositions for 12+ types, giving developers immediate insight into what a String, Vec, or HashMap actually looks like in memory. This is particularly valuable for understanding why certain types have specific sizes (e.g., String is always 24 bytes on 64-bit: three pointer-sized fields) and where the actual data lives (on the heap, pointed to by the ptr field).

The decompositions are returned as Vec<MemoryFieldInfo>, each entry containing the field name, type display string, byte offset within the parent type, and field size. For types with pointer fields (String, Vec, Box, Rc, Arc), the engine also generates a PointerRelation entry indicating that the stack variable "owns" a heap allocation, enabling the visualization to draw arrows from stack to heap. 

fn extract_type_fields(db, display_target, ty) -> Vec<MemoryFieldInfo> {
    let type_str = ty.display(db, display_target).to_string();

    if type_str == "String" {
        return vec![
            MemoryFieldInfo { name: "ptr", ty: "*const u8",  offset: 0,  size: 8 },
            MemoryFieldInfo { name: "len", ty: "usize",     offset: 8,  size: 8 },
            MemoryFieldInfo { name: "cap", ty: "usize",     offset: 16, size: 8 },
        ];
    }
    if type_str.starts_with("Vec<") {
        return vec![
            MemoryFieldInfo { name: "ptr", ty: "*const T",  offset: 0,  size: 8 },
            MemoryFieldInfo { name: "len", ty: "usize",     offset: 8,  size: 8 },
            MemoryFieldInfo { name: "cap", ty: "usize",     offset: 16, size: 8 },
        ];
    }
    if type_str.starts_with("Rc<") {
        return vec![
            MemoryFieldInfo { name: "ptr", ty: "NonNull<RcBox<T>>", offset: 0, size: 8 },
        ];
    }
    if type_str.starts_with("HashMap<") {
        return vec![
            MemoryFieldInfo { name: "ctrl",        ty: "*const u8", offset: 0,  size: 8 },
            MemoryFieldInfo { name: "bucket_mask", ty: "usize",     offset: 8,  size: 8 },
            MemoryFieldInfo { name: "items",       ty: "usize",     offset: 16, size: 8 },
            MemoryFieldInfo { name: "growth_left", ty: "usize",     offset: 24, size: 8 },
        ];
    }
    // ... RefCell, Cell, Option, Result, Box, Arc, &T
}

6.3 User-Defined Struct Field Extraction via ty.fields

For user-defined structs, the engine cannot rely on hardcoded layouts. Instead, it calls ty.fields(db) which returns an iterator of (hir::Field, hir::Type) pairs. For each field, it queries field_ty.layout(db) to get the size and alignment, then computes the field offset by simulating the compiler's layout algorithm (aligning each field to its requirement and advancing). The field name is obtained via field.name(db) and the type display string via field_ty.display(db, display_target), giving both human-readable and machine-processable representations.

This approach works for any struct visible to the Salsa database, including structs defined in the current crate, in dependencies, and in the standard library (though standard library types are handled by the hardcoded path in Section 6.2 for accuracy). Enum variants and union fields are not decomposed in the current implementation; only named struct fields are extracted. If ty.layout(db) fails for a field (e.g., the field type contains an unresolved generic), that field is included with size 0 and the layout continues with the next field. The Rust compiler may reorder fields for optimization (unless #[repr(C)] is specified), so the computed layout represents the logical field order as declared in source, which may differ from the actual memory order at runtime. 

// For user-defined structs: enumerate fields via ADT
if let Some(hir::Adt::Struct(_)) = ty.as_adt() {
    let mut fields = Vec::new();
    let mut field_offset = 0u64;

    for (field, field_ty) in ty.fields(db) {
        let field_name = field.name(db).to_string();
        let field_size = field_ty.layout(db).ok().map(|l| l.size()).unwrap_or(0);
        let field_align = field_ty.layout(db).ok().map(|l| l.align()).unwrap_or(1);

        // Align the offset
        field_offset = (field_offset + field_align - 1) / field_align * field_align;

        fields.push(MemoryFieldInfo {
            name: field_name, type_display: field_ty.display(..).to_string(),
            offset: field_offset, size: field_size,
        });
        field_offset += field_size;
    }
    return fields;
}

6.4 Heap Allocation Detection and Estimation

Not all memory lives on the stack. Types like Vec, String, Box, and HashMap allocate backing storage on the heap. The engine detects these by classifying each variable into a MemoryCategory (see Section 6.6) and generating a HeapAllocation entry for heap-backed and ref-counted types. Each entry records the owning variable name, a description of what is allocated, an estimated size, and the allocation kind. This separation between stack representation (the pointer/length/capacity triple) and heap storage (the actual data) is fundamental to understanding Rust's memory model.

Heap size estimation is necessarily approximate without runtime observation. The engine uses type-based heuristics: a Vec<T> is estimated at 24 bytes of heap storage (3 elements of average size), a String at 16 bytes, a HashMap at 64 bytes (initial bucket array), and a Box<T> at the size of T. For Rc and Arc, the heap allocation includes the inner value plus 16 bytes for the strong and weak reference counts. These estimates provide relative sizing for visualization purposes rather than exact byte counts. When the runtime component is available, it can supply actual allocation sizes observed during execution, replacing these estimates with precise measurements.

6.5 Pointer Relationship Graph

The engine builds a graph of pointer relationships between variables and their heap allocations. Three relationship kinds are tracked:

  • owns_heap: A heap-backed variable (Vec, String, Box) owns its backing storage. The stack representation contains a pointer that points to the heap allocation.
  • owns_heap (ref-counted): An Rc or Arc variable owns a pointer to the shared inner allocation (which contains the value plus reference counts).
  • borrows: A reference variable (&T or &mut T) points to another stack variable. The target is extracted from the initializer expression (e.g., let r = &data produces a "borrows" edge from r to data).

These relationships are returned as Vec<PointerRelation> in the MemoryLayoutInfo response. Each entry has a from (the variable holding the pointer), a to (the target, either a heap allocation name like "data.data" or another variable name), and a kind string. Visualization tools use these to draw arrows between stack slots and heap regions, making the ownership topology visible at a glance.

6.6 Memory Category Classification

Every variable is classified into one of five memory categories that determine how it appears in the visualization and whether heap allocation entries are generated:

Category Criteria Examples Visualization
StackOnly Copy type with size <= 16 bytes i32, f64, bool, (u8, u8) Simple colored block, no heap arrow
HeapBacked ADT name is Vec, String, Box, HashMap, etc. Vec<i32>, String, Box<dyn Trait> Stack block + arrow to heap region
Reference ty.is_reference() = true &str, &mut Vec<i32> Thin block + arrow to target variable
RefCounted ADT name is Rc or Arc Rc<Config>, Arc<Mutex<T>> Stack pointer + arrow to shared heap inner
InteriorMut ADT name is RefCell, Cell, Mutex, RwLock RefCell<Vec<i32>>, Mutex<State> Stack block with borrow_flag field shown

Classification uses the resolved ADT name from hir::Adt::name(db), not the display string. This ensures that type aliases and re-exports are correctly classified (e.g., type MyVec = Vec<i32> is still classified as HeapBacked). The classification is performed once per variable during the analyze_memory_layout pass and stored in the StackVariable::category field. The category drives both the heap allocation generation (only HeapBacked and RefCounted produce entries) and the pointer relationship generation (only HeapBacked, RefCounted, and Reference produce edges). StackOnly variables appear as simple blocks with no outgoing arrows, making the visualization cleaner for functions with many primitive locals. The InteriorMut category is particularly important because it signals that the variable's contents can be mutated through shared references, which affects borrow conflict analysis.
