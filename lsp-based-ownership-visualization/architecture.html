3. Architecture

3.1 System Overview

borrowscope-lsp is a standalone binary that communicates with any LSP-compatible editor via JSON-RPC over standard input/output. The editor sends text document notifications (open, change, close) and requests (hover, codeLens, custom ownership queries). The server maintains an in-memory semantic database of the entire workspace and responds with structured ownership information derived from that database. Because it uses the standard LSP protocol, it is not tied to any specific editor: VS Code, Neovim, Emacs, Helix, and any other LSP client can connect without modification. The server process is long-lived, starting when the editor opens a Rust project and terminating on shutdown, maintaining state across multiple file edits throughout the session.

The architecture has three layers: the LSP protocol layer (message parsing, routing, response formatting), the state management layer (file tracking, caching, debouncing), and the analysis layer (type extraction, borrow scope computation, conflict detection). Each layer is independent: the protocol layer knows nothing about ownership, the analysis layer knows nothing about LSP, and the state layer mediates between them. This separation allows the analysis engine to be tested in isolation (as a library crate) without spawning an LSP server, and allows the protocol layer to be swapped for alternative transports (e.g., WebSocket) without touching the analysis logic. The main loop uses a 50ms polling timeout, which balances responsiveness (debounce checks, background load completion) against CPU usage when idle.

3.2 The ra_ap_* Semantic Engine

The server builds on the ra_ap_* crate ecosystem, which is the public API surface of rust-analyzer's internal compiler. These crates provide full semantic understanding of Rust code without invoking rustc directly. They are versioned and published to crates.io, allowing external tools to depend on specific versions (we use 0.0.318). The same APIs that power rust-analyzer's go-to-definition, type inference, and completion are available to us for ownership analysis. This means we get the same precision as the compiler itself for type resolution, trait checking, and layout computation. The key crates used are:

  • ra_ap_hir: High-level intermediate representation. Provides hir::Type (40+ query methods), hir::Function, hir::Module, hir::Semantics for name resolution and type inference.
  • ra_ap_ide_db: The RootDatabase (Salsa-based) and Definition::usages for finding all references to a binding.
  • ra_ap_syntax: Concrete syntax tree (CST). Provides ast::Fn, ast::LetStmt, ast::MethodCallExpr, TextRange, and tree traversal.
  • ra_ap_vfs: Virtual file system that tracks file contents in memory, enabling incremental updates without disk I/O.
  • ra_ap_load_cargo: One-shot workspace loader that resolves Cargo.toml, discovers the sysroot, and populates the Salsa database with all crate metadata.
  • ra_ap_hir_ty: Provides attach_db for executing type queries within the correct database context.
use ra_ap_hir::{self as hir, HirDisplay, Semantics};
use ra_ap_ide_db::RootDatabase;
use ra_ap_syntax::{ast, AstNode, Edition};
use ra_ap_vfs::VfsPath;
use ra_ap_load_cargo::{load_workspace_at, LoadCargoConfig};
use ra_ap_hir_ty::attach_db;

3.3 Workspace Loading via load_workspace_at

The most expensive operation in the server's lifecycle is the initial workspace load. This resolves all dependencies declared in Cargo.toml, discovers the Rust sysroot (standard library source), and builds the complete Salsa database containing type information for every crate in the dependency graph. For a medium-sized project (50-100 crates in the dependency tree), this takes 30-40 seconds. The result is a RootDatabase that can answer any semantic query about any symbol in the workspace or its dependencies, and a Vfs (virtual file system) that holds all file contents in memory.

The load is configured with two structures: CargoConfig (which sets sysroot discovery to automatic) and LoadCargoConfig (which enables output directory loading for build scripts, disables proc-macro expansion to avoid spawning a separate server, and enables cache prefilling for faster subsequent queries). Disabling proc-macro expansion is a deliberate trade-off: it means that types generated by procedural macros (such as derive macros) may not be fully resolved, but it eliminates the complexity and latency of maintaining a proc-macro server process. For ownership analysis, this trade-off is acceptable because the vast majority of ownership-relevant types are defined in user code or the standard library, not generated by macros. 

pub fn load_workspace(root_path: &Path) -> Result<WorkspaceData> {
    let mut cargo_config = CargoConfig::default();
    cargo_config.sysroot = Some(RustLibSource::Discover);

    let load_config = LoadCargoConfig {
        load_out_dirs_from_check: true,
        with_proc_macro_server: ProcMacroServerChoice::None,
        prefill_caches: true,
        proc_macro_processes: 0,
    };

    let (db, vfs, _) = load_workspace_at(root_path, &cargo_config, &load_config, &|msg| {
        tracing::debug!("Loading: {}", msg);
    })?;

    Ok(WorkspaceData { db, vfs })
}

3.4 Salsa Incremental Computation Model

After the initial load, the Salsa database enables incremental re-analysis. Salsa is a demand-driven computation framework: queries are only recomputed when their inputs change. When the developer edits a file, the server pushes the new content into the VFS, then calls db.apply_change() to notify Salsa that one input has changed. Subsequent queries (type resolution, name lookup, layout computation) automatically recompute only the portions of the dependency graph affected by that change. Salsa tracks dependencies at a fine granularity: if a query only reads the body of one function, changing a different function in the same file does not invalidate it. This granularity is what makes sub-100ms re-analysis possible even for files with dozens of functions.

This is the key architectural difference from the borrowscope-analyzer, which performs a full workspace analysis and writes a complete type-info.json on every run. The LSP server never performs a full re-analysis after the initial load. A single-character edit in a function body triggers recomputation of only that function's type information, keeping response times under 100ms. The Salsa model also means that queries for unmodified functions return instantly from cache, making it efficient to analyze an entire file (for CodeLens) even when only one function changed. This is fundamentally different from the batch model where any change requires regenerating the entire output. 

// Push edited file content into VFS
let vfs_path = VfsPath::new_real_path(file_path.clone());
ws.vfs.set_file_contents(vfs_path, Some(content.as_bytes().to_vec()));

// Apply VFS changes to Salsa database
let changes = ws.vfs.take_changes();
let mut change = ChangeWithProcMacros::default();
for (file_id, _) in &changes {
    change.source_change.change_file(*file_id, Some(content.clone()));
}
ws.db.apply_change(change);
// Next query on this file will recompute only affected results

3.5 LSP Protocol Layer

The server uses the lsp-server crate for JSON-RPC framing over stdio. On startup, it performs the standard LSP handshake: receives initialize, responds with server capabilities, waits for initialized, then enters the main message loop. The main loop processes three message types: requests (which require a response), notifications (fire-and-forget from client), and responses (to server-initiated requests like progress token creation). If the client sends a shutdown request, the server responds with null and exits cleanly with code 0. If the connection drops without shutdown, the server exits with code 1, signaling an abnormal termination. The declared capabilities are:

  • textDocumentSync: Full document sync (the client sends the entire file content on each change).
  • hoverProvider: Ownership tooltips on variable declarations.
  • codeLensProvider: Per-function ownership statistics above each function signature.
  • inlayHintProvider: Inline ownership category annotations after variable names.
pub fn server_capabilities() -> ServerCapabilities {
    ServerCapabilities {
        text_document_sync: Some(TextDocumentSyncCapability::Options(
            TextDocumentSyncOptions {
                open_close: Some(true),
                change: Some(TextDocumentSyncKind::FULL),
                save: Some(TextDocumentSyncSaveOptions::SaveOptions(SaveOptions {
                    include_text: Some(false),
                })),
                ..Default::default()
            },
        )),
        hover_provider: Some(HoverProviderCapability::Simple(true)),
        code_lens_provider: Some(CodeLensOptions { resolve_provider: Some(false) }),
        inlay_hint_provider: Some(OneOf::Left(true)),
        ..Default::default()
    }
}

3.6 Custom Request Protocol

Beyond standard LSP features, the server exposes 5 custom requests and 1 custom notification for ownership-specific analysis. These use the standard JSON-RPC mechanism with method names prefixed by borrowscope/. Any LSP client can invoke them by sending a request with the appropriate method name and parameters. The custom requests follow the same error handling conventions as standard LSP: if the workspace is not yet loaded, requests that require semantic analysis return error code -32002 (ServerNotInitialized). The ownershipGraph request is an exception: it returns a structured loading indicator instead of an error, allowing the client to show a placeholder UI while the workspace loads. All responses include a _status field ("ready" or "loading") and a _stale boolean indicating whether the result comes from cache.

Method Parameters Returns
borrowscope/ownershipGraph TextDocumentPosition Full ownership summary for the function at cursor: variables, borrows, moves, clones, conflicts, stats
borrowscope/borrowScopes TextDocument All active borrow scopes in the file with line ranges and mutability
borrowscope/variableInfo TextDocumentPosition Detailed ownership info for the variable at cursor: type, category, borrows, traits, layout
borrowscope/crossFunctionBorrows TextDocument All borrows that cross function boundaries with path segments
borrowscope/memoryLayout TextDocumentPosition Stack frame, heap allocations, pointer relationships for the function at cursor
borrowscope/analysisUpdated (notification) N/A (server-initiated) Sent to client when analysis results change, listing affected function names

3.7 Background Loading with Progress Reporting

Since workspace loading takes 30-40 seconds, the server must remain responsive during this period. The solution is to spawn the load in a background thread and continue processing messages in the main loop. During loading, requests that require the semantic database return a structured response with "_status": "loading" rather than an error, allowing the client to display a loading indicator. File open and change notifications are still processed during this time: the server stores file contents in its open_files map so that when loading completes, it already has the latest content for all open files. This means the developer can start editing immediately after opening a project, and ownership analysis becomes available seamlessly once the background load finishes.

Progress is reported to the editor via the standard LSP $/progress mechanism. The server creates a progress token (borrowscope/loading), sends a WorkDoneProgressBegin notification, and when loading completes (or fails), sends WorkDoneProgressEnd. The editor displays this as a progress bar or status message. If loading fails (e.g., no valid Cargo.toml, missing sysroot, or dependency resolution error), the failure message is included in the progress end notification and logged to stderr. The server continues running in a degraded mode where only file tracking works but no semantic analysis is available. 

// Spawn loading in background thread
let root_path = state.root_path.clone();
let (load_sender, load_receiver) = crossbeam_channel::bounded(1);
state.loading_receiver = Some(load_receiver);

thread::spawn(move || {
    let result = workspace::load_workspace(&root_path);
    send_progress(&sender, &token, WorkDoneProgress::End(
        WorkDoneProgressEnd { message: Some("Ready".to_string()) }
    ));
    load_sender.send(result).ok();
});

// Main loop checks non-blocking:
match receiver.try_recv() {
    Ok(Ok(ws)) => { state.workspace = Some(ws); }
    Ok(Err(e)) => { tracing::error!("Loading failed: {}", e); }
    Err(TryRecvError::Empty) => { /* still loading */ }
}
