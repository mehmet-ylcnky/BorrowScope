1. Introduction

1.1 The Invisible Ownership Problem

Rust's ownership system is the language's defining feature: it guarantees memory safety without a garbage collector by enforcing strict rules about who owns a value, who borrows it, and when it is dropped. These rules are checked at compile time by the borrow checker, which rejects programs that violate them. However, the borrow checker operates as a gatekeeper: it reports violations but never shows the positive case. A developer working on a function with five variables, three borrows, and two moves must mentally reconstruct the ownership graph to understand why the code compiles, or why a proposed change would break it.

Consider a function that creates a Vec, takes a shared reference to it, passes that reference to a helper function, then later attempts to push into the vector. The developer must reason about: when does the shared borrow start, when does it end (last use of the reference), does the helper function extend the borrow's lifetime, and does the push happen after the borrow is no longer active. None of this reasoning is visible in the editor. The developer works from memory and intuition. 

fn process_data() {
    let mut data = vec![1, 2, 3];  // owned, heap-backed, 24B stack + heap
    let snapshot = &data;            // shared borrow starts here
    validate(snapshot);              // borrow crosses into validate()
    // snapshot's last use was line above, borrow ends here
    data.push(4);                    // &mut self - safe because borrow ended
}

In this example, the developer must know that Rust uses Non-Lexical Lifetimes (NLL), meaning the borrow of data ends at the last use of snapshot (the call to validate), not at the end of the enclosing scope. This is not visible in the source code. A tool that shows borrow scopes, ownership categories, and conflict zones would eliminate this mental overhead entirely.

1.2 From Runtime Instrumentation to Static Analysis

The development of borrowscope-analyzer, borrowscope-macro, and borrowscope-runtime taught us three things: that the ra_ap_* compiler APIs provide sufficient information to classify every variable's ownership category without heuristics, that a structured type-info schema can drive automated code instrumentation across 82 initializer categories, and that recording ownership events at runtime produces a complete picture of dynamics along a given execution path. These findings established that semantic ownership visualization is achievable. The question became: can we deliver it without requiring the developer to leave the editor?

The existing pipeline works as follows. The borrowscope-analyzer loads the workspace via ra_ap_load_cargo, resolves types for every variable, and writes a type-info.json file containing per-variable metadata: whether a variable is Rc, Arc, RefCell, a closure, a raw pointer, or a plain owned value. The borrowscope-macro (#[track_ownership]) reads this file at compile time to decide which track_* function to emit for each variable. Without it, the macro cannot distinguish Rc::clone(&x) (shared ownership) from x.clone() (deep copy). Finally, borrowscope-runtime records 88 event types during execution and exports them as JSON for post-hoc analysis.

This architecture works but has four fundamental limitations:

  • Requires compilation and execution: The developer must save, compile, run the program, and then inspect the output. The feedback loop is measured in seconds to minutes.
  • Sees only one execution path: Each run traces one path through the program. Branches not taken, error paths not triggered, and concurrent interleavings not observed remain invisible.
  • No editor feedback: Results appear in a separate JSON file or visualization tool, disconnected from the source code where the developer is working.
  • Stale type information: The moment the developer edits the source code, the type-info.json file becomes outdated. A variable that was Rc might now be Arc, a function parameter might have changed type, or a new variable might not appear in the file at all. The developer must re-run the analyzer to update it.

These limitations motivated borrowscope-lsp: a system that provides the same semantic ownership analysis, using the same compiler-grade type information, but computed in real-time inside the editor as the developer types. The LSP server uses the ra_ap_* crate ecosystem (rust-analyzer's internal APIs) to access the Salsa incremental computation database, which maintains an always-up-to-date semantic model of the entire workspace. When a file changes, only the affected queries are recomputed, keeping response times under 100ms.

The three components serve complementary roles:

Property borrowscope-runtime borrowscope-macro borrowscope-lsp
Requires compilation Yes Yes (expands at compile time) No
Requires execution Yes No (but output needs runtime) No
Sees all code paths No (one path per run) N/A (instruments all paths) Yes
Real-time editor feedback No No Yes (<100ms)
Precision of ownership info Exact (observed at runtime) Exact (semantic type-info) Static approximation (all paths)
Handles dynamic dispatch Yes (sees actual types) Partially (monomorphized) No (static types only)
Type info freshness Snapshot at compile time Snapshot (type-info.json) Always current (Salsa DB)

1.3 Research Questions

This work addresses four research questions. Each targets a specific technical challenge that must be solved to deliver real-time ownership visualization without sacrificing the semantic precision established by the analyzer and runtime components.

  • RQ1: Can ownership relationships be extracted from the rust-analyzer semantic database in real-time, within a 100ms budget per function?
  • RQ2: Can cross-function borrow paths be resolved without whole-program analysis, using only local call-site resolution?
  • RQ3: Can memory layout (stack frame structure, heap allocations, pointer relationships) be reconstructed from type information alone, without runtime observation?
  • RQ4: Can a debounced incremental analysis pipeline maintain responsiveness during rapid editing while still providing accurate results?

1.4 Contributions

This paper makes the following contributions. Together, they demonstrate that compiler-grade ownership analysis can be delivered as an interactive editor service, bridging the gap between the static type-info approach of the analyzer and the dynamic event recording of the runtime.

  1. An LSP server implementation with 5 custom requests and 1 custom notification for ownership-specific analysis, built entirely on ra_ap_* compiler APIs with zero heuristics.
  2. An ownership analysis engine that extracts 40+ type properties per variable, classifies ownership into 8 categories, computes borrow scopes via Definition::usages, detects 4 move patterns, and identifies borrow conflicts through scope overlap analysis.
  3. Cross-function borrow tracking that resolves call targets via sema.resolve_path and traces reference parameters into callees, with performance guards (200ms timeout, 50 result cap).
  4. Field-level memory layout visualization that reconstructs stack frames, identifies heap allocations, and maps pointer relationships for 12+ standard library types and arbitrary user-defined structs.
  5. A debounced incremental analysis pipeline with fresh/stale caching, smart notification filtering (only affected functions), and LRU eviction, keeping the server responsive during rapid editing.
  6. Validation through 107 integration tests covering the full LSP protocol lifecycle, custom requests, debounce behavior, cache management, and performance budgets.
