4. Error Taxonomy

Through systematic analysis of compiler errors across all five projects, we identified six primary error patterns. Each pattern represents a distinct failure mode of syntactic analysis, and each traces to specific manifestations of the type information barrier.

4.1 Classification System

Error Code Name Frequency Projects Affected
ERR-003 Mutable Borrow Conflicts Very High ALL 5
ERR-012 Trait Impl Signature Mismatch Very High tokio, ripgrep
ERR-002 Tuple Destructuring High 4 projects

4.2 ERR-003: Mutable Borrow Conflicts

Problem: Wrapping method calls on mutable references creates a second borrow, violating Rust's borrowing rules.

This is the most pervasive error, appearing in all five projects. When the macro wraps a method call for tracking, it may inadvertently create an additional borrow: 

// Original code
fn process(data: &mut Vec<u8>) {
    data.push(42);  // Single mutable borrow
}

// After macro transformation (problematic)
fn process(data: &mut Vec<u8>) {
    track_call(data.push(42));  // data borrowed by track_call AND push
}

The macro cannot determine that data is mutably borrowed because it cannot see the type of data or the signature of push. Syntactically, data.push(42) looks identical whether data is &mut Vec, &Vec, or an owned Vec.

4.3 ERR-012: Trait Implementation Signature Mismatch

Problem: The macro instruments trait method declarations (which have no body) or changes impl signatures to not match the trait definition.

This error accounts for 54% of tokio's failures. The fundamental issue is that trait definitions and trait implementations look syntactically similar: 

// Trait definition - should NOT be instrumented
trait AsyncRead {
    fn poll_read(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
        buf: &mut ReadBuf<'_>,
    ) -> Poll<io::Result<()>>;  // No body!
}

// Trait implementation - SHOULD be instrumented
impl AsyncRead for TcpStream {
    fn poll_read(
        self: Pin<&mut Self>,
        cx: &mut Context<'_>,
        buf: &mut ReadBuf<'_>,
    ) -> Poll<io::Result<()>> {
        // Implementation body
    }
}

The macro sees fn poll_read(...) in both cases. Without type information, it cannot distinguish a trait declaration (no body, just a signature) from a trait implementation (has a body). When it instruments the declaration, it may add tracking code that changes the signature, causing the impl to no longer match the trait.

4.4 ERR-002: Tuple Destructuring

Problem: Wrapping tuple expressions breaks pattern matching and destructuring bindings. 
// Original code
let (a, b) = get_pair();

// After macro transformation (problematic)
let (a, b) = track_return(get_pair());  // track_return returns wrong type

The macro wraps the return value of get_pair(), but the wrapper function may not preserve the tuple type in a way that allows destructuring. The macro cannot see that the left-hand side expects a tuple pattern.

4.5 ERR-009: Self-Consuming Functions

Problem: Functions that take self by value (consuming ownership) fail when the macro interferes with move semantics. 
impl Builder {
    // Consumes self, returns new owned value
    fn build(self) -> Product {
        // self is moved here
    }
}

// Usage
let product = builder.build();  // builder is consumed

The macro sees builder.build() but cannot determine that build takes self by value. If it wraps the call in a way that borrows builder first, the move semantics are violated.

4.6 ERR-014: Trait Method Declarations

Problem: The macro attempts to add tracking code to trait method declarations that have no body.

This is related to ERR-012 but distinct: here the macro tries to instrument a method that has no body at all (just a semicolon). The transformation fails because there's no code to wrap. 

trait Handler {
    fn handle(&self, event: Event);  // No body - just declaration
    
    fn default_impl(&self) {
        // Has body - can be instrumented
    }
}

4.7 ERR-008: Trait Bound Failures

Problem: Wrapping arguments breaks impl Trait and generic bounds. 
fn process<T: Into<String>>(value: T) {
    let s: String = value.into();
}

// Call site
process("hello");  // &str implements Into<String>

// After macro transformation (problematic)
process(track_arg("hello"));  // track_arg's return type may not impl Into<String>

The macro cannot see that the parameter has a trait bound. When it wraps the argument, the wrapper's return type may not satisfy the bound, causing a type error.
