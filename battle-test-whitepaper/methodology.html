2. Battle Test Methodology

Validating a code transformation tool requires testing against code that was not written with the tool in mind. Synthetic benchmarks risk bias—consciously or unconsciously constructed to succeed or fail. Production codebases, maintained by independent teams with their own priorities, provide the unbiased ground truth necessary for meaningful evaluation.

2.1 Project Selection Criteria

We selected test subjects based on five criteria:

  • Production quality: Actively maintained projects with significant user bases
  • Domain diversity: Different application types exercise different language features
  • Code style variation: Different teams have different idioms and patterns
  • Size range: From focused utilities to large frameworks
  • Rust feature coverage: Async/await, traits, generics, unsafe code, FFI

2.3 Instrumentation Process

For each project, we applied the #[trace_borrow] attribute to every function using an automated Python script. The script parses Rust source files, identifies function definitions (including methods in impl blocks), and inserts the attribute: 

// Before instrumentation
fn process_data(input: &[u8]) -> Result<Output> {
    // function body
}

// After instrumentation
#[trace_borrow]
fn process_data(input: &[u8]) -> Result<Output> {
    // function body
}

The instrumentation script handles several edge cases:

  • Preserves existing attributes (derives, cfg, inline, etc.)
  • Skips functions already annotated with #[trace_borrow]
  • Handles both free functions and methods in impl blocks
  • Processes async functions and const functions
  • Maintains original formatting and comments

2.4 Measurement Framework

After instrumentation, we compile each project using cargo check with full feature flags enabled. We capture compiler output and classify each function as:

  • Pass: Function compiles without errors after macro transformation
  • Fail: Compiler reports errors in the transformed code

For failed functions, we extract the error message and classify it according to our error taxonomy (Section 4). A single function may trigger multiple compiler errors, but we count the function once in pass/fail statistics while tracking all error types for pattern analysis.

Reproducibility

All instrumentation scripts, raw compiler output, and analysis tools are available in the battle-test/ directory of the BorrowScope repository. Each project includes a BATTLE_TEST_REPORT.md with detailed per-file results.
