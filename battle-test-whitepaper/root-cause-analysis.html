5. Root Cause Analysis

The six error patterns identified in Section 4 share common root causes. Understanding these causes is essential for developing effective solutions—treating symptoms without addressing causes leads to whack-a-mole fixes that create new problems.

5.1 Syntactic Ambiguity

The most fundamental cause is that Rust's syntax is designed for human readability and compiler processing, not for distinguishing semantic categories. Constructs that mean very different things look identical at the token level:

Syntax Possible Meanings Affected Errors
fn foo(&self) Trait declaration, trait impl, inherent impl ERR-012, ERR-014
x.method() Immutable borrow, mutable borrow, move ERR-003, ERR-009
func(arg) Owned, borrowed, impl Trait, generic ERR-008
let x = expr Simple binding, destructuring, pattern match ERR-002

The macro sees tokens: fn, foo, (, &, self, ). It cannot see that this particular fn is inside a trait block versus an impl block without tracking context through the entire file—and even then, it cannot determine if the impl is for a trait or an inherent impl without resolving the type names.

5.2 Ownership Semantics Blindness

Rust's ownership system is enforced through types, not syntax. The difference between &T, &mut T, and T is semantic—it determines what operations are valid—but the syntax for using them is often identical: 

let a: &Vec<i32> = ...;
let b: &mut Vec<i32> = ...;
let c: Vec<i32> = ...;

// All three look identical syntactically:
a.len();  // Immutable borrow - safe to wrap
b.len();  // Mutable borrow - wrapping may conflict
c.len();  // Owned - wrapping may interfere with moves

The macro cannot distinguish these cases. It sees identifier.method() and must make a decision about how to wrap it without knowing whether the identifier is borrowed, mutably borrowed, or owned.

Key Insight: ERR-003 (mutable borrow conflicts) appears in ALL five projects because mutable borrows are ubiquitous in Rust code, and the macro has no way to detect them.

5.3 Context Sensitivity

Many semantic properties depend on context that spans beyond the immediate syntax:

  • Name resolution: Is foo() a local function, an imported function, a method, or an FFI call? The answer requires resolving the name through use statements, impl blocks, and extern declarations.
  • Type inference: What type does let x = expr bind? The answer may depend on how x is used later in the function, requiring forward analysis the macro cannot perform.
  • Trait resolution: Which impl of a trait applies to a given method call? The answer requires knowing the concrete type and searching for matching impls—a process that happens during type checking. 
use std::io::Write;

fn example<W: Write>(writer: &mut W) {
    writer.write_all(b"hello")?;  // Which write_all?
}

// The macro sees: writer.write_all(b"hello")
// It cannot know:
//   - W is a generic type parameter
//   - W has a Write bound
//   - write_all comes from the Write trait
//   - writer is mutably borrowed

This context sensitivity explains why tokio—with its heavy use of generics, traits, and async patterns—has the lowest pass rate. The more a codebase relies on Rust's advanced type system features, the more context is needed to understand the code, and the less effective syntactic analysis becomes.

The 80/20 Pattern

Our results suggest an 80/20 pattern: approximately 80% of real-world Rust code uses patterns simple enough for syntactic analysis, while 20% requires type information. This aligns with the theoretical prediction and suggests that the annotation system proposed in the companion paper can effectively handle the remaining cases.
