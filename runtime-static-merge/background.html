2. Background

2.1 Static Ownership Analysis (borrowscope-lsp)

The static side of the merge is provided by borrowscope-lsp, a Language Server Protocol implementation that performs real-time ownership analysis using the ra_ap_* crate ecosystem (rust-analyzer's internal compiler APIs). For each function, the LSP produces a FunctionOwnershipSummary containing: every variable with its ownership category (Owned, SharedRef, MutableRef, Rc, Arc, InteriorMut, RawPointer, Copy), borrow scopes with start/end line ranges and mutability, detected moves with source and destination, Rc/Arc clone operations, closure captures with capture mode, and borrow conflicts where scopes overlap.

The LSP analysis is fully semantic: it uses hir::Type methods to classify variables, Definition::usages to compute borrow scope endpoints (matching NLL semantics), and sema.resolve_method_call to determine self-borrow modes. It produces results within 100ms per function and updates incrementally as the developer types, thanks to Salsa's demand-driven computation model. The key property for the merge is that static analysis provides predictions about all code paths: it reports every variable that exists in the function, every borrow that could be active, and every conflict that could occur, regardless of which execution path is taken at runtime.

The static output serves as the "expected" side of the merge. Each variable's ownership category, borrow count, and move status represent what the compiler's type system guarantees about the code's behavior. When runtime observation agrees with these predictions, the merge reports "match." When it disagrees, the merge investigates why.

2.2 Runtime Event Tracking (borrowscope-runtime)

The runtime side is provided by borrowscope-runtime, a library that records ownership events during program execution. The library is activated by the #[trace_borrow] procedural macro (from borrowscope-macro), which instruments function bodies with track_* calls at each ownership operation. When the track feature is enabled, these calls record events to a thread-local buffer; when disabled, they compile to no-ops (zero runtime cost).

Each event carries a nanosecond-precision timestamp, a variable identifier (format: "name_counter", e.g., "data_0"), and type-specific fields. A New event records the variable name, ID, and type name. A Borrow event records the borrower name/ID, owner ID, and mutability. A Drop event records the variable ID and optional location. An RcClone event records the clone's name/ID, source ID, and the resulting strong/weak counts. The events are exported as a JSON array, either written to a file at program exit or streamed via WebSocket during execution.

The runtime output serves as the "observed" side of the merge. Each event represents something that actually happened during one execution of the program. The timestamps provide ordering, the variable IDs provide identity, and the type-specific fields provide the precise state at each point. When the merge correlates these observations with static predictions, divergences become visible.

2.3 The 88 Event Type Taxonomy

The runtime defines 88 distinct event types organized into 15 categories. Each category covers a different aspect of Rust's ownership system. The full taxonomy ensures that no ownership-relevant operation goes unrecorded, providing the merge algorithm with complete observational data for any instrumented function.

Category Events What They Capture
Core Ownership New, Borrow, Move, Drop Variable creation, reference creation, ownership transfer, destruction
Smart Pointers (Rc/Arc) RcNew, RcClone, ArcNew, ArcClone Shared ownership creation and cloning with strong/weak counts
Weak References WeakNew, WeakClone, WeakUpgrade Weak pointer lifecycle and upgrade success/failure
Interior Mutability RefCellNew, RefCellBorrow, RefCellDrop, CellNew, CellGet, CellSet Runtime borrow checking and interior mutation
Unsafe Operations RawPtrCreated, RawPtrDeref, UnsafeBlockEnter/Exit, Transmute, FfiCall Raw pointer usage, unsafe blocks, FFI boundaries
Async/Await AsyncBlockEnter/Exit, AwaitStart, AwaitEnd Async block boundaries and suspension points
Concurrency ThreadSpawn, ThreadJoin, ChannelSend/Recv, LockGuardAcquire/Drop Thread lifecycle, message passing, lock acquisition
Box/Pin/Cow BoxNew, BoxIntoRaw, BoxFromRaw, PinNew, CowBorrowed, CowOwned, CowToMut Heap allocation, pinning, clone-on-write
OnceCell/MaybeUninit OnceCellNew, OnceCellSet, OnceCellGet, MaybeUninitNew, MaybeUninitAssumeInit Lazy initialization and uninitialized memory
Control Flow FnEnter/Exit, LoopEnter/Exit, LoopIteration, Branch, Return, Break, Continue Function boundaries, loop iterations, branching decisions
Expressions Call, Clone, Deref, Unwrap, IndexAccess, FieldAccess, BinaryOp, TypeCast Method calls, dereferences, unwrap operations
Closures ClosureCreate, ClosureCapture Closure creation with capture mode (ByRef, ByMutRef, ByMove)
Data Structures StructCreate, TupleCreate, ArrayCreate, Range Composite type instantiation
Scopes RegionEnter, RegionExit Lexical scope boundaries for drop order tracking
Statics StaticInit, StaticAccess, ConstEval Static/const variable initialization and access

Not all 88 event types are equally relevant to the merge. The core ownership events (New, Borrow, Move, Drop) and smart pointer events (RcNew, RcClone, ArcNew, ArcClone) are the primary inputs for divergence detection. The async events (AwaitStart, AwaitEnd) are critical for async borrow tracking. The remaining events provide context (function boundaries, loop iterations) but do not directly trigger divergence checks. The merge algorithm processes all events but only aggregates ownership-relevant ones into the RuntimeInfo structure.
