3. Event Ingestion

Before the merge can operate, runtime events must be loaded into the extension. The ingestion layer handles two transport modes (file-based and WebSocket), validates incoming data, and normalizes the event format regardless of how the runtime serialized it. The design prioritizes robustness: malformed events are skipped rather than crashing the extension, partial files are handled gracefully, and format differences between serialization modes are resolved transparently.

3.1 File-Based Ingestion (JSON Watcher)

The primary ingestion mode uses a file system watcher that monitors the configured events file (default: .borrowscope/events.json relative to the workspace root). When the instrumented program finishes execution and writes its events to this file, the watcher detects the change and triggers a reload. The watcher uses VS Code's FileSystemWatcher API with a debounce to avoid reading partial writes (the runtime writes the entire file atomically, but on some file systems the watcher may fire before the write completes).

On each file change, the watcher reads the entire file content, parses it as a JSON array, validates each event, and emits an onEventsUpdated event that the extension's merge pipeline consumes. The file path is configurable via borrowscope.runtime.filePath, allowing projects to place events in custom locations. If the file does not exist or is empty, the watcher remains active but does not trigger the merge (the extension operates in static-only mode until events appear). 

export class RuntimeWatcher {
  private watcher: vscode.FileSystemWatcher | undefined;
  private events: RuntimeEvent[] = [];
  private _onEventsUpdated = new vscode.EventEmitter<RuntimeEvent[]>();

  start(workspaceRoot: string): void {
    const config = vscode.workspace.getConfiguration("borrowscope.runtime");
    const filePath = config.get<string>("filePath", ".borrowscope/events.json");
    const pattern = new vscode.RelativePattern(workspaceRoot, filePath);

    this.watcher = vscode.workspace.createFileSystemWatcher(pattern);
    this.watcher.onDidChange(() => this.reload(workspaceRoot, filePath));
    this.watcher.onDidCreate(() => this.reload(workspaceRoot, filePath));

    // Initial load if file already exists
    this.reload(workspaceRoot, filePath);
  }

  private reload(root: string, filePath: string): void {
    const fullPath = path.join(root, filePath);
    const content = fs.readFileSync(fullPath, "utf-8");
    const parsed = JSON.parse(content);
    this.events = parseEvents(parsed);
    this._onEventsUpdated.fire(this.events);
  }
}

3.2 WebSocket Live Streaming

The alternative ingestion mode connects to a WebSocket server for live event streaming. This mode is useful for long-running programs (servers, daemons) where the developer wants to observe ownership patterns as they happen rather than waiting for program exit. The runtime opens a WebSocket connection on a configurable port (default: 9876) and sends each event as a JSON message immediately after it occurs.

The extension's RuntimeSocket class manages the WebSocket connection lifecycle: connecting on activation, reconnecting on disconnect, and buffering events for the merge pipeline. Events arrive one at a time (not as a batch), so the merge must support incremental updates. In practice, the extension batches incoming WebSocket events with a 100ms debounce before triggering a re-merge, balancing responsiveness against CPU usage.

The WebSocket mode is enabled by setting borrowscope.runtime.source to "websocket" and configuring the port via borrowscope.runtime.websocketPort. Both modes produce the same RuntimeEvent[] array for the merge pipeline; the transport is transparent to downstream processing.

3.3 Event Validation and Parsing

Raw JSON from either transport is validated before entering the merge pipeline. The parseEvents() function iterates the array and checks each element for the required structure: it must be an object with either a type field (internally-tagged) or exactly one key matching a known event type name (externally-tagged). Events that fail validation are skipped with a warning logged to the output channel, ensuring that a single malformed event does not prevent the remaining events from being processed.

The parser also applies filtering based on configuration. The filterOwnershipEvents() function removes events that are not relevant to ownership analysis (e.g., LoopIteration, BinaryOp, IndexAccess) to reduce the event count before the merge. The filterByFile() function retains only events whose location matches the currently active editor file, ensuring the merge operates on relevant data. These filters are applied in sequence: parse -> validate -> filter by relevance -> filter by file. 

export function parseEvents(raw: any[]): RuntimeEvent[] {
  return raw.filter(item => {
    if (!item || typeof item !== "object") return false;
    // Internally-tagged: { "type": "New", "var_name": "x", ... }
    if (item.type && typeof item.type === "string") return true;
    // Externally-tagged: { "New": { "var_name": "x", ... } }
    const keys = Object.keys(item);
    return keys.length === 1 && isKnownEventType(keys[0]);
  });
}

export function filterOwnershipEvents(events: RuntimeEvent[]): RuntimeEvent[] {
  const relevant = new Set([
    "New", "Borrow", "Move", "Drop",
    "RcNew", "RcClone", "ArcNew", "ArcClone",
    "WeakNew", "WeakUpgrade", "AwaitStart", "AwaitEnd",
    "UnsafeBlockEnter", "RawPtrDeref", "ChannelRecv",
    // ... other ownership-relevant types
  ]);
  return events.filter(e => relevant.has(eventType(e)));
}

3.4 Internally-Tagged vs Externally-Tagged Format Handling

Rust's serde library supports multiple enum serialization formats. The default for Rust enums is externally-tagged: {"New": {"var_name": "x", "timestamp": 1000}}, where the variant name is the object key. An alternative is internally-tagged: {"type": "New", "var_name": "x", "timestamp": 1000}, where the variant name is a field within the object. The borrowscope-runtime uses externally-tagged by default, but some configurations (particularly when events pass through middleware or logging systems) may produce internally-tagged format.

The extension handles both formats transparently through two helper functions. The eventType() function extracts the event type name regardless of format: if the object has a type field, it returns that; otherwise it returns the single key name. The eventData() function extracts the payload: if internally-tagged, it returns the object itself (minus the type field); if externally-tagged, it returns the value of the single key. All downstream code uses these helpers exclusively, never accessing the raw event structure directly. 

/** Get the event type name (handles both formats) */
export function eventType(event: RuntimeEvent): string {
  if ((event as any).type) return (event as any).type;
  return Object.keys(event)[0];
}

/** Get the event payload (handles both formats) */
export function eventData(event: RuntimeEvent): { timestamp: number; [key: string]: any } {
  if ((event as any).type) return event as any;
  return Object.values(event)[0] as any;
}

This dual-format handling was introduced after discovering that some CI environments and logging pipelines transform the JSON format during transit. By supporting both at the parser level, the extension works correctly regardless of how events are serialized, stored, or transmitted between the runtime and the editor.
