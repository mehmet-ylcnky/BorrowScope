4. Variable Mapping

The most critical step in the merge pipeline is correlating runtime variable IDs with static variable declarations. Without this correlation, the system cannot compare what was predicted with what was observed. The mapping must handle ambiguity (multiple variables with the same name), incompleteness (variables that appear in only one source), and robustness (graceful degradation when correlation fails). This section describes the correlation problem, the matching strategy, and how edge cases are resolved.

4.1 The Correlation Problem (Runtime IDs vs Static Declarations)

Runtime events identify variables using string IDs in the format "name_counter" (e.g., "data_0", "r_1", "config_2"). The counter increments globally across all variables in the instrumented function, ensuring uniqueness even when multiple variables share the same name (shadowing). Static analysis identifies variables by their declaration: name, type, line number, column, and file path. These two identification schemes have no shared key: the runtime does not know the line number, and the static analysis does not know the counter suffix.

The correlation must bridge this gap. Given a runtime ID "data_0", the system must determine which static variable declaration it corresponds to. The answer is not always obvious: a function may declare let data = vec![1,2,3]; on line 5 and let data = data.clone(); on line 8 (shadowing). The runtime assigns "data_0" to the first and "data_1" to the second, but the static analysis sees two declarations both named "data" at different lines. The mapping must use the counter suffix to disambiguate.

4.2 Name + Line + File Matching Strategy

The mapping algorithm operates in three steps. First, it extracts the variable name from the runtime ID by stripping the counter suffix: "data_0" becomes "data", "config_2" becomes "config". Second, it finds all static variable declarations with the same name in the same file. Third, if multiple declarations match (shadowing), it uses the counter value as a declaration index: counter 0 maps to the first declaration of that name, counter 1 to the second, and so on.

The mapVariables() function takes the static variable list and the runtime event array as inputs. It scans the events for creation events (New, RcNew, ArcNew, etc.) to identify all runtime variables, then correlates each with a static declaration. The output is a MappedVariable[] where each entry contains: the runtime var_id, the var_name, the matched static declaration (or null if unmapped), the parsed location (file, line), and the subset of events that reference this variable. 

export function mapVariables(
  staticVars: StaticVariable[],
  events: RuntimeEvent[],
  file?: string
): MappedVariable[] {
  const mapped: MappedVariable[] = [];

  // Find all creation events (these define runtime variables)
  for (const event of events) {
    const type = eventType(event);
    const data = eventData(event);
    if (!isCreationEvent(type)) continue;

    const varName = data.var_name;
    const varId = data.var_id;
    const location = parseLocation(data.location);

    // Find matching static variable by name + declaration order
    const candidates = staticVars.filter(s => s.name === varName);
    const declIndex = extractCounter(varId); // "data_0" -> 0
    const staticMatch = candidates[declIndex] || candidates[0] || null;

    // Collect all events referencing this var_id
    const varEvents = events.filter(e => referencesVar(e, varId));

    mapped.push({ var_id: varId, var_name: varName, static_match: staticMatch,
                  location, events: varEvents });
  }

  return mapped;
}

4.3 Handling Shadowed Variables

Variable shadowing is common in Rust: let x = compute(); let x = transform(x); creates two distinct variables both named "x." The runtime assigns them sequential IDs ("x_0" and "x_1"), and the static analysis reports two declarations at different lines. The mapping uses the counter suffix as a declaration index within the set of same-named variables, ordered by line number.

This approach works correctly when the analyzer and runtime agree on declaration order (which they do, since both process the function body top-to-bottom). Edge cases arise when the analyzer skips a variable (e.g., a compiler-generated temporary that the runtime tracks but the analyzer does not see). In such cases, the counter may exceed the number of static declarations, and the variable is marked as unmapped (static_match: null). The merge still processes it as a "runtime_only" entry, preserving all runtime observations even without a static counterpart.

4.4 Unmapped Variables (runtime_only and static_only)

Not every variable maps cleanly between the two worlds. runtime_only variables appear in the event stream but have no corresponding static declaration. Common causes: compiler-generated temporaries (e.g., the intermediate value in a.b.c()), variables inside macro expansions that the analyzer does not traverse, or variables in functions that the LSP did not analyze (e.g., functions in dependencies). These variables still receive a MergedVariable entry with static_info: null, and their runtime behavior is fully tracked. They appear in the Runtime view but cannot be correlated with source lines.

static_only variables appear in the LSP analysis but have no corresponding runtime events. Common causes: the function was never called during the traced execution, the variable is in a branch that was not taken, or the macro did not instrument that particular binding (e.g., function parameters in some configurations). These variables receive a MergedVariable entry with runtime_info: null and agreement status "static_only". They appear in the static ownership graph but have no timing, drop order, or ref count data.

Both categories are valuable. runtime_only variables reveal runtime behavior that static analysis cannot see (useful for understanding macro-generated code or compiler optimizations). static_only variables reveal code that was never exercised (useful for identifying dead code or insufficient test coverage). The merge preserves both rather than discarding unmatched entries, giving the developer a complete picture of what was predicted, what was observed, and what was missed by each side.
