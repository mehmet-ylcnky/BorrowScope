8. Async Borrow Tracking

Async Rust introduces a unique ownership challenge: when a function suspends at an .await point, any local variables that are still alive must be stored in the future's state machine. If a borrow is active during the suspension, it becomes part of the future's captured state. This has implications for the Send trait: if the borrowed type is not Sync, the future cannot be sent to another thread, preventing it from being spawned on multi-threaded runtimes like tokio. This section describes how the merge layer detects borrows held across await points and explains the resulting compiler errors.

8.1 The Problem: Borrows Held Across Await Points

Consider an async function that borrows a RefCell and then awaits a network operation: 

async fn process(cell: &RefCell<Vec<i32>>) {
    let guard = cell.borrow(); // Ref<Vec<i32>> is not Send
    let data = fetch_remote(guard.len()).await; // suspension point!
    println!("{:?} {:?}", *guard, data);
}

// Error: future is not Send because Ref<'_, Vec<i32>> is not Send
// tokio::spawn(process(&cell));

The guard variable (a Ref<Vec<i32>>) is alive when .await is reached. Since Ref is not Send (it contains a raw pointer to the RefCell's borrow flag), the entire future becomes non-Send. The compiler reports this as a cryptic error about the future's type not implementing Send, often pointing to the spawn site rather than the actual borrow that causes the problem.

Static analysis can detect that a borrow could be held across an await (by checking if the borrow scope spans a line containing .await), but it cannot determine whether the await is actually reached while the borrow is active (the await might be in a branch that is only taken when the borrow has already been dropped). Runtime observation resolves this ambiguity: it records the exact moment the await fires and checks whether the borrow is still active at that point.

8.2 Detecting AwaitStart Events During Active Borrows

The detection algorithm maintains a set of active borrows for each variable. When a Borrow event fires with owner_id matching the tracked variable, the borrower's ID is added to the active set. When a Drop event fires for a borrower in the active set, it is removed. At any point, the active set represents all borrows currently alive on this variable.

When an AwaitStart event fires and the active set is non-empty, an await crossing is recorded. The crossing captures: which await point (from the event's location field), which future was being awaited (from the future_name field), and the start timestamp. When the corresponding AwaitEnd event fires (matched by await_id), the duration is computed. The result is an AwaitCrossing entry added to the variable's RuntimeInfo. 

function detectAwaitCrossings(varId: string, events: RuntimeEvent[]): AwaitCrossing[] {
  const crossings: AwaitCrossing[] = [];
  let activeBorrows = new Set<string>();

  for (const event of events) {
    const type = eventType(event);
    const data = eventData(event);

    // Track active borrows on this variable
    if (type === "Borrow" && data.owner_id === varId) {
      activeBorrows.add(data.borrower_id);
    }
    if (type === "Drop" && activeBorrows.has(data.var_id)) {
      activeBorrows.delete(data.var_id);
    }

    // Check if await fires while borrows are active
    if (type === "AwaitStart" && activeBorrows.size > 0) {
      const awaitStart = data.timestamp;
      const loc = parseLocation(data.location);

      // Find matching AwaitEnd for duration
      const endEvent = events.find(
        e => eventType(e) === "AwaitEnd" && eventData(e).await_id === data.await_id
      );
      const duration = endEvent ? eventData(endEvent).timestamp - awaitStart : 0;

      crossings.push({
        await_line: loc?.line ?? 0,
        duration_ns: duration,
        future_name: data.future_name || "unknown",
      });
    }
  }

  return crossings;
}

8.3 Duration Measurement and Future Identification

Each AwaitCrossing records three pieces of information that help the developer understand the impact of the held borrow:

  • await_line: The source line where .await appears, extracted from the AwaitStart event's location field. This tells the developer exactly which await point is problematic.
  • duration_ns: How long the suspension lasted, computed as AwaitEnd.timestamp - AwaitStart.timestamp. A borrow held for 1 microsecond across an await is less concerning than one held for 500 milliseconds (which blocks other tasks from accessing the borrowed data for that duration).
  • future_name: Which future was being awaited (e.g., "fetch_remote", "tokio::time::sleep"). This helps the developer understand what operation is causing the suspension and whether it can be restructured to release the borrow first.

When multiple await points exist in a function, a single borrow may cross several of them. Each crossing is recorded separately, producing a list that shows the full pattern: "this borrow was held across 3 await points, totaling 12ms of suspension time." The divergence detector aggregates these into a single async_borrow_held divergence with the total count and duration in the description.

8.4 Implications for Send Trait Compliance

The practical consequence of a borrow held across an await is that the future may not implement Send. In Rust's async model, a future that is Send can be moved between threads (required by tokio::spawn and similar multi-threaded executors). A future is Send if all types stored in its state machine are Send. A borrow (&T or &mut T) is Send only if T is Sync. Many common types are not Sync: Ref<T> (from RefCell), MutexGuard<T> (on some platforms), raw pointers, and Rc<T>.

When the merge detects an async_borrow_held divergence, it directly explains the "future is not Send" error that the developer may encounter. The suggestion ("clone before the await or restructure to drop the borrow first") provides the two standard solutions: either clone the data so the borrow can be released before the await, or restructure the code to ensure the borrow's scope ends before the suspension point. The runtime evidence shows exactly which await point and which borrow are involved, eliminating the guesswork that the compiler's error message often requires.

This is one of the most practically valuable divergence kinds because the compiler's error message for non-Send futures is notoriously confusing. It points to the spawn site and says "future is not Send" without indicating which specific borrow or which specific await causes the problem. The merge layer fills this gap by showing the exact crossing point with timing data, turning a frustrating compiler error into an immediately actionable finding.
