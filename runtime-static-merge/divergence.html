6. Divergence Detection

Divergence detection is the core contribution of the merge layer. It transforms raw disagreements between static predictions and runtime observations into classified, actionable findings. Each divergence kind targets a specific class of ownership issue, carries a severity level that determines how prominently it is displayed, and includes a suggestion that tells the developer what to investigate. This section describes the detection architecture and each of the 9 divergence kinds in detail.

6.1 Detection Architecture (Per-Variable Analysis)

The detectAllDivergences() function runs all 9 checks on each MergedVariable independently. It receives the merged variable (with both static_info and runtime_info populated) and the full event stream (needed for some checks that look beyond the variable's own events, such as WeakUpgrade). Each check is a pure function that returns zero or more DetailedDivergence entries. The checks are ordered from most severe to least, but all run regardless of earlier results (a single variable can have multiple divergences).

Each DetailedDivergence contains five fields: kind (one of 9 enum values), severity ("error", "warning", or "info"), description (human-readable explanation of what was observed), suggestion (what the developer should do), and runtime_evidence (the specific observations that triggered the detection, useful for debugging false positives). The separation of description and suggestion ensures that the developer understands both what happened and what to do about it. 

export function detectAllDivergences(
  merged: MergedVariable,
  allEvents: RuntimeEvent[]
): DetailedDivergence[] {
  const divergences: DetailedDivergence[] = [];
  const s = merged.static_info;
  const r = merged.runtime_info;
  if (!r) return divergences;

  // Run all 9 checks
  checkRcLeak(s, r, divergences);
  checkRcCycle(s, r, divergences);
  checkMissingDrop(s, r, divergences);
  checkAsyncBorrowHeld(r, divergences);
  checkUnsafeHidden(s, r, divergences);
  checkConditionalMove(s, r, divergences);
  checkWeakUpgradeFail(merged, allEvents, divergences);
  checkChannelRecvFail(merged, allEvents, divergences);
  checkUseAfterMove(merged, allEvents, divergences);

  return divergences;
}

6.2 Rc/Arc Leak Detection (rc_leak)

Condition: Static analysis classifies the variable as Rc or Arc, and runtime observation shows that it was never dropped (drop_timestamp < 0) while the final reference count is greater than zero (ref_count_final > 0).

Meaning: The reference-counted value will never be freed. Memory is leaked. This is one of the few ways to leak memory in safe Rust (the other being std::mem::forget or Box::leak). The most common cause is a reference cycle: two Rc values pointing to each other, preventing either from reaching zero.

Severity: Error. This is a genuine bug that causes unbounded memory growth in long-running programs.

Suggestion: "Check for reference cycles. Consider using Weak references to break the cycle." 

if (s && (s.ownership_category === "Rc" || s.ownership_category === "Arc") &&
    r.drop_timestamp < 0 && r.ref_count_final > 0) {
  divergences.push({
    kind: "rc_leak",
    severity: "error",
    description: `${s.ownership_category} never dropped (final ref count: ${r.ref_count_final})`,
    suggestion: "Check for reference cycles. Consider using Weak references.",
    runtime_evidence: `Created with ref_count=1, peaked at ${r.ref_count_peak}, never reached 0`,
  });
}

6.3 Reference Cycle Detection (rc_cycle)

Condition: Rc or Arc, ref_count_peak > 1, clone_count >= 2, ref_count_final > 0, and never dropped. This is a stricter version of rc_leak that specifically identifies cycles (multiple clones that form a loop).

Meaning: Not just a forgotten Rc, but an actual cycle where multiple Rc values reference each other. The ref count went up (clones were created) but never came back down (no clone was ever the last reference). This distinguishes a cycle from a simple leak where a single Rc was forgotten.

Severity: Error. Cycles are harder to fix than simple leaks because breaking them requires restructuring the ownership graph.

Suggestion: "Break the cycle with Weak<T> or restructure ownership. The ref count peaked at N with M clones."

6.4 Missing Drop Detection (missing_drop)

Condition: The variable is non-Copy, was not moved, was never dropped, and is not Rc/Arc (those are handled by rc_leak). This catches variables that should have been destroyed but weren't.

Meaning: A value that owns resources (heap memory, file handles, network connections) was never cleaned up. Possible causes: std::mem::forget was called explicitly, the program exited (panic or std::process::exit) before the scope ended, or the variable was leaked through unsafe code.

Severity: Warning. Unlike Rc leaks, this may be intentional (some patterns use mem::forget deliberately, e.g., when transferring ownership to C code via FFI).

Suggestion: "This may indicate a leak, std::mem::forget, or program exit before scope end."

6.5 Async Borrow Held Across Await (async_borrow_held)

Condition: The variable has borrows that are active (not yet dropped) when an AwaitStart event fires. The detectAwaitCrossings() function tracks active borrows and checks them against await events.

Meaning: A borrow is held across a suspension point. When the future is suspended at .await, the borrow must be stored in the future's state machine. If the borrow is mutable and the borrowed type is not Sync, the future cannot implement Send, meaning it cannot be spawned on a multi-threaded runtime like tokio. This is the root cause of the common "future is not Send" compiler error.

Severity: Warning. The code may still compile (if the future is only used on a single-threaded runtime), but it limits composability.

Suggestion: "Consider cloning before the await or restructuring to drop the borrow first."

6.6 Unsafe Hidden Behavior (unsafe_hidden)

Condition: The variable has unsafe_accesses > 0 (raw pointer dereferences or unsafe block entries) but is not classified as RawPointer by static analysis.

Meaning: The variable participates in unsafe operations that static analysis cannot verify. The ownership guarantees that the LSP reports may be incomplete because unsafe code can bypass the borrow checker. The runtime observed operations that the static analysis cannot account for.

Severity: Info. This is not necessarily a bug; it simply indicates that the static view is incomplete for this variable. The developer should review the unsafe blocks for soundness.

Suggestion: "Review unsafe blocks for soundness. Static analysis cannot verify ownership inside unsafe code."

6.7 Conditional Move Detection (conditional_move)

Condition: Static analysis says the variable is Owned (could be moved), it is non-Copy, but runtime shows: never moved, never borrowed (0 borrows), and dropped normally. The variable existed, was never used by anyone, and was simply destroyed.

Meaning: A move expression exists in the source code (the static analysis sees it), but the branch containing the move was not taken during this execution. The variable was created and dropped without ever being consumed or borrowed. This may indicate dead code, an untaken error path, or simply a branch that this particular test input did not exercise.

Severity: Info. This is expected behavior for programs with conditional logic. It becomes interesting when aggregated across multiple runs: a variable that is never moved in any run may indicate truly dead code.

Suggestion: "The move may be in a branch that wasn't executed in this run."

6.8 Weak Upgrade Failure (weak_upgrade_fail)

Condition: A WeakUpgrade event with success: false exists for this variable (or a Weak reference derived from it).

Meaning: Weak::upgrade() was called but returned None because the strong reference had already been dropped. The Weak pointer is dangling. This may indicate a lifetime ordering issue: the code assumes the strong reference outlives the weak, but it doesn't.

Severity: Warning. The code handles the None case (otherwise it would panic), but the failed upgrade may indicate a design issue where the weak reference is used after its referent is gone.

Suggestion: "Handle the None case from Weak::upgrade, or ensure the strong reference outlives the weak."

6.9 Channel Receive Failure (channel_recv_fail)

Condition: A ChannelRecv event with success: false exists, indicating that a receive operation failed because the sender was dropped.

Meaning: The sending half of a channel was dropped before the receiver could read all messages. This may indicate a task ordering issue (the producer finished before the consumer), a panic in the sender task, or intentional shutdown signaling.

Severity: Warning. Failed receives are common in shutdown scenarios but may indicate bugs in producer-consumer patterns.

Suggestion: "Ensure sender outlives receiver, or handle the RecvError gracefully."

6.10 Use After Move (use_after_move)

Condition: Events referencing this variable's ID exist after a Move event from it (excluding the final Drop event). The variable was moved away but then used again.

Meaning: This should be impossible in safe Rust. The borrow checker prevents use-after-move at compile time. If the runtime observes it, the cause is either: (1) unsafe code that bypasses the borrow checker, (2) an instrumentation error in the macro, or (3) a bug in the event recording. Regardless of cause, this is a serious finding.

Severity: Error. This indicates potential undefined behavior or a soundness hole.

Suggestion: "This should not happen in safe Rust. Check for unsafe code or instrumentation errors."

6.11 Severity Classification and Actionable Suggestions

The three severity levels determine how divergences are presented to the developer. Error (red) indicates genuine bugs that should be fixed: Rc leaks cause unbounded memory growth, reference cycles prevent deallocation, and use-after-move indicates undefined behavior. Warning (yellow) indicates potential issues that may or may not be bugs depending on context: missing drops may be intentional, async borrows may be acceptable on single-threaded runtimes, and channel failures may be expected during shutdown. Info (gray/subtle) indicates observations that are informational rather than problematic: unsafe code is not inherently wrong, and conditional moves are expected in branching code.

Kind Severity Condition (simplified) Suggestion
rc_leak Error Rc/Arc, never dropped, ref_count > 0 Check for reference cycles, use Weak
rc_cycle Error Rc/Arc, 2+ clones, ref_count never reached 0 Break cycle with Weak or restructure
use_after_move Error Events after Move (excluding Drop) Check unsafe code or instrumentation
missing_drop Warning Non-Copy, non-moved, never dropped Check for mem::forget or early exit
async_borrow_held Warning Active borrow during AwaitStart Clone before await or drop borrow first
weak_upgrade_fail Warning WeakUpgrade with success=false Ensure strong outlives weak
channel_recv_fail Warning ChannelRecv with success=false Ensure sender outlives receiver
unsafe_hidden Info Unsafe accesses on non-RawPointer var Review unsafe blocks for soundness
conditional_move Info Owned, non-Copy, never moved, 0 borrows Move may be in untaken branch

The visualization layer uses severity to determine presentation: errors produce red inline highlights and appear prominently in the Runtime view, warnings produce yellow highlights and appear in the divergence list, and info-level divergences appear only in the detailed panel view (not as inline decorations). This graduated approach ensures that critical issues are impossible to miss while informational observations do not create visual noise.
