2. Architecture

The extension follows VS Code's extension model: a TypeScript module that activates when a Rust file is opened, manages a language client connection to the LSP server, and registers commands, decorations, and a WebView panel. The architecture separates concerns into four layers: the LSP client (data acquisition), the state layer (caching and coordination), the decoration layer (inline editor feedback), and the panel layer (WebView visualization). Each layer operates independently and communicates through well-defined interfaces.

2.1 Extension Activation and Lifecycle

The extension activates when VS Code opens a file with languageId: "rust". The activate() function performs five initialization steps in sequence: creates an output channel for logging, initializes the performance monitor, shows the welcome panel on first activation, registers all 27 commands, and starts the LSP client connection. If the workspace contains a Rust project, it also starts the runtime watcher, creates runtime decoration types, and initializes the status bar.

The deactivate() function stops the LSP client and disposes the runtime watcher. All resources (decoration types, file watchers, status bar items) are registered in context.subscriptions for automatic disposal when the extension is deactivated or uninstalled. This ensures no resource leaks even if deactivation is triggered by VS Code shutting down unexpectedly. 

export async function activate(context: vscode.ExtensionContext): Promise<void> {
  outputChannel = vscode.window.createOutputChannel("BorrowScope");
  perfMonitor = new PerformanceMonitor(outputChannel);
  registerPerformanceCommand(context, perfMonitor);
  showWelcomeIfNeeded(context);
  registerCommands(context);

  // Register 27 commands (inspect, toggle, navigate, export, views...)
  context.subscriptions.push(
    vscode.commands.registerCommand("borrowscope.inspectVariable", inspectVariable),
    vscode.commands.registerCommand("borrowscope.toggleDecorations", toggleDecorations),
    vscode.commands.registerCommand("borrowscope.nextConflict", nextConflict),
    vscode.commands.registerCommand("borrowscope.focusGraph", focusGraph),
    // ... 23 more commands
  );

  await startClient(context);

  // Runtime watcher (file + WebSocket)
  runtimeWatcher = new RuntimeWatcher();
  runtimeStatusBar = new RuntimeStatusBar();
  runtimeStatusBar.attachWatcher(runtimeWatcher);
  runtimeWatcher.start(workspaceRoot);
}

2.2 LSP Client Connection

The extension uses vscode-languageclient/node to spawn and communicate with the borrowscope-lsp binary. The server is started via stdio transport, with the binary path resolved from configuration (borrowscope.server.path), the extension's bundled binary, or the system PATH. The client registers a document selector for Rust files and a file system watcher for **/*.rs to trigger re-analysis on external file changes.

After the client starts, the extension registers two notification handlers. The first listens for borrowscope/analysisUpdated: when received, it invalidates the graph cache, refreshes inline decorations, and live-updates the WebView panel if the currently displayed function is in the affected list. The second listens for textDocument/publishDiagnostics: when received, it applies conflict zone highlighting to the active editor. Both handlers check that the notification's URI matches the active editor before acting, preventing stale updates from background files. 

client.onNotification("borrowscope/analysisUpdated", async (params) => {
  const editor = vscode.window.activeTextEditor;
  if (!editor || editor.document.uri.toString() !== params.uri) return;

  lastGraph = undefined; graphCache.clear(); // invalidate cache
  refreshInlayHints(editor);
  refreshDecorations(editor);

  // Live update the graph panel if open and showing an affected function
  const panel = GraphPanel.getPanel();
  if (panel && panel.getGraph()) {
    const currentFn = panel.getGraph().function_name;
    if (params.functions?.includes(currentFn)) {
      const graph = await client.sendRequest("borrowscope/ownershipGraph", { ... });
      if (graph) panel.updateGraph(graph);
    }
  }
});

The extension also implements a pre-fetch strategy: after the workspace finishes loading (detected by the first successful analysisUpdated notification), it fires parallel ownershipGraph requests for every function in the active file. This warms the Salsa cache on the server side and populates the local graph cache, making subsequent CodeLens clicks and panel opens instantaneous.

2.3 Graph Cache and State Management

The extension maintains a per-function graph cache (graphCache: Map<string, any>) that stores the most recent ownershipGraph response for each function name. When the developer clicks a CodeLens or switches the panel to a different function, the extension first checks this cache before sending a request to the LSP server. Cache hits are served immediately (zero latency); cache misses trigger an LSP request and store the result for future use.

The cache is invalidated entirely when an analysisUpdated notification arrives, because any function in the file may have been affected by the change. The previous graph is preserved separately (_previousGraph) to enable the comparison view, which shows what changed between the last two analyses. The current graph is also persisted to workspaceState so that the panel can restore its content when VS Code is restarted or the panel is hidden and re-shown.

2.4 Configuration System (33 Settings)

The extension exposes 33 settings organized into 9 groups, all accessible via VS Code's standard settings UI. The getConfig() function returns a fully typed BorrowScopeConfig object that is read fresh on each access (no stale configuration). Settings changes take effect immediately without requiring an extension restart, because each feature checks its configuration at render time rather than caching it at activation. 

export interface BorrowScopeConfig {
  server:       { path: string; extraArgs: string[] };
  analysis:     { debounceMs: number };
  decorations:  { enabled: boolean; borrowScopes: boolean; gutterIcons: boolean;
                  inlayHints: boolean; codeLens: boolean; lifelines: boolean };
  graph:        { layout: "force" | "hierarchical" | "radial";
                  showTypes: boolean; animateUpdates: boolean };
  colors:       { sharedBorrow: string; mutableBorrow: string; move: string;
                  rcArc: string; owned: string; drop: string };
  crossFunction: { enabled: boolean; maxDepth: number; showInline: boolean };
  memoryLayout: { enabled: boolean; showAlignment: boolean; animationSpeed: number };
  runtime:      { enabled: boolean; source: "file" | "websocket"; filePath: string;
                  websocketPort: number; showTimings: boolean; showDropOrder: boolean;
                  showRefCounts: boolean; highlightDivergences: boolean };
  diagnostics:  { enabled: boolean; severity: "information" | "hint" | "warning" };
}

The color settings deserve special attention. Each ownership category has a configurable color that is used consistently across all views: the same blue for shared borrows appears in the graph nodes, the lifeline gutter, the timeline bars, and the inlay hint text. This consistency helps the developer build a mental model where color always means the same thing regardless of which view they are looking at. The defaults follow a semantic color scheme: blue for shared (safe, read-only), red for mutable (exclusive, dangerous), green for owned (stable), purple for Rc/Arc (shared ownership), orange for moves (transfer), and gray for drops (end of life).
