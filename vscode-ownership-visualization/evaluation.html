9. Evaluation

This section evaluates the extension across two dimensions: rendering performance (how quickly visual feedback appears after a code change) and user experience (how many interactions are needed to access ownership information). The evaluation demonstrates that the extension meets its design goal of feeling instantaneous for common operations while providing deep analysis on demand.

9.1 Rendering Performance

The end-to-end latency from keystroke to visual update is the sum of three components: the editor's debounce (300ms), the LSP server's analysis time (typically <50ms for a single function), and the extension's rendering time (decoration application + panel update). The total pipeline completes in 350-400ms for the common case, which is below the 500ms threshold where users perceive delay as "laggy."

Operation Typical Latency Bottleneck
Inlay hint refresh (after edit) 320-380ms Debounce (300ms) + LSP response (20-80ms)
Lifeline decoration refresh 320-400ms Debounce + borrowScopes request + decoration application
Graph panel update (live) 350-450ms Debounce + ownershipGraph request + D3 re-render
CodeLens click (cached) <50ms Graph cache hit + panel HTML generation
CodeLens click (cold) 80-150ms LSP request + panel HTML generation
Editor switch (decoration restore) 150-250ms Editor switch debounce (150ms) + decoration application
Memory view scrub (per line) <16ms DOM update only (no LSP request, data already loaded)
Runtime event file load (1000 events) 50-100ms JSON parse + merge + decoration application
Graph D3 force simulation (10 nodes) <100ms to settle D3 physics simulation convergence
Graph D3 force simulation (50 nodes) 200-400ms to settle D3 physics with more repulsion calculations

The pre-fetch strategy (Section 6.3) eliminates the cold-start penalty for CodeLens clicks after the initial workspace load. Once pre-fetch completes, all function graphs are cached locally, making panel opens effectively instantaneous. The memory view scrub operates at 60fps because it only manipulates DOM elements with pre-computed data (no LSP requests during scrubbing). The runtime event merge is a one-time cost when the events file changes, after which the merged data is cached for the session.

9.2 User Experience Metrics

The extension is designed to minimize the number of interactions needed to access any piece of ownership information. The following table shows how many actions are required to answer common ownership questions:

Question Actions Required Mechanism
"Is this variable a reference or owned?" 0 (visible immediately) Inlay hint annotation appears automatically
"When does this borrow end?" 0 (visible immediately) Lifeline gutter shows ╰─ 💧 at the end line
"Are there any borrow conflicts?" 0 (visible immediately) Squiggly underline + yellow highlight on conflict zone
"Where does this borrow flow to?" 0 (visible immediately) Cross-function annotation at call site
"Show me the full ownership graph" 1 click (CodeLens) Click the stats CodeLens above the function
"How much stack space does this use?" 1 click (CodeLens) Memory CodeLens shows stack/heap summary; click for detail
"What is the drop order?" 2 clicks CodeLens click + switch to Scopes view (shows drop order at bottom)
"Is there an Rc leak at runtime?" 0 (visible when runtime enabled) Divergence highlight appears automatically on the variable
"Navigate to the next conflict" 1 keystroke Ctrl+Shift+N jumps to next conflict
"What changed since my last edit?" 2 clicks CodeLens click + switch to Compare view

The key insight is that the most common questions (is it a reference? when does the borrow end? are there conflicts?) require zero actions. The information is visible as part of the normal code reading experience. More detailed questions (full graph, memory layout, runtime divergences) require at most 1-2 clicks. No question requires more than 2 interactions to answer, and keyboard shortcuts reduce even those to a single keystroke for power users.
