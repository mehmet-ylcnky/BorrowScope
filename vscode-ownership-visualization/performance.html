6. Performance and Responsiveness

A visualization tool that lags behind the developer's typing is worse than no tool at all: it shows stale information that may mislead. The extension is designed to feel instantaneous for the common case (single-function edits) while gracefully degrading for expensive operations (full-file analysis, cross-function resolution). This section describes the three mechanisms that ensure responsiveness: debounced refresh, performance monitoring, and graph caching.

6.1 Debounced Refresh Pipeline

The extension uses multiple debounce timers to avoid redundant work during rapid editing. When the developer types, VS Code fires onDidChangeTextDocument events for every keystroke. The extension does not refresh decorations on every event. Instead, it waits 300ms after the last change before triggering a refresh. This matches the LSP server's own debounce (also 300ms by default), ensuring that the extension requests fresh data only after the server has finished processing the change.

A separate, shorter debounce (150ms) is used for editor switches (onDidChangeActiveTextEditor). When the developer clicks a different tab, the extension waits 150ms before refreshing decorations for the new file. This prevents flickering when rapidly switching between tabs (e.g., using Ctrl+Tab to cycle through recent files). If the developer settles on a file, decorations appear within 150ms, which is below the perceptual threshold for "instant."

The analysisUpdated notification from the LSP server triggers an immediate cache invalidation and refresh (no debounce), because this notification already incorporates the server's own debounce. When it arrives, the data is guaranteed to be fresh, so the extension can render immediately. The refresh pipeline is: invalidate graph cache, request new inlay hints, request new borrow scopes, request ownership graph for the current function (if panel is open), and apply all decorations. These requests are fired in parallel for maximum speed. 

// Debounced refresh on text change (300ms)
context.subscriptions.push(
  vscode.workspace.onDidChangeTextDocument((e) => {
    const editor = vscode.window.activeTextEditor;
    if (editor && e.document === editor.document && e.document.languageId === "rust") {
      setTimeout(() => refreshDecorations(editor), 300);
    }
  })
);

// Debounced refresh on editor switch (150ms)
let editorChangeTimer: NodeJS.Timeout | undefined;
context.subscriptions.push(
  vscode.window.onDidChangeActiveTextEditor((editor) => {
    if (editorChangeTimer) clearTimeout(editorChangeTimer);
    editorChangeTimer = setTimeout(() => {
      if (editor && editor.document.languageId === "rust") {
        refreshDecorations(editor);
      }
    }, 150);
  })
);

// Immediate refresh on analysisUpdated (server already debounced)
client.onNotification("borrowscope/analysisUpdated", async (params) => {
  graphCache.clear();
  refreshInlayHints(editor);
  refreshDecorations(editor);
});

6.2 Performance Monitoring

The extension includes a built-in performance monitoring system that tracks the duration of every significant operation. The PerformanceMonitor class records timings per operation label, keeps the last 100 measurements for each, and logs a warning to the output channel when any operation exceeds the 100ms slow threshold. The developer can view a full performance report via the borrowscope.showPerformanceReport command, which shows average, maximum, minimum, and count for each tracked operation.

The monitor provides both synchronous and asynchronous timing wrappers. The synchronous time(label, fn) method wraps a function call and records its duration. The asynchronous timeAsync(label, fn) method does the same for Promise-returning functions. Both return the original function's result transparently, so they can be inserted into any call chain without changing behavior. The commands.ts module uses these wrappers around every LSP request to track response times in production. 

export class PerformanceMonitor {
  private timings: Map<string, number[]> = new Map();
  private slowThresholdMs: number = 100;

  /** Time an async operation */
  async timeAsync<T>(label: string, fn: () => Promise<T>): Promise<T> {
    const start = performance.now();
    const result = await fn();
    this.record(label, performance.now() - start);
    return result;
  }

  /** Record a timing and warn if slow */
  record(label: string, elapsedMs: number): void {
    const times = this.timings.get(label) || [];
    times.push(elapsedMs);
    if (times.length > 100) times.shift(); // keep last 100
    this.timings.set(label, times);

    if (elapsedMs > this.slowThresholdMs) {
      this.outputChannel?.appendLine(`[perf] ${label} took ${elapsedMs.toFixed(1)}ms (slow)`);
    }
  }

  /** Generate full report */
  report(): string {
    const lines = ["BorrowScope Performance Report:", ""];
    for (const label of [...this.timings.keys()].sort()) {
      const stats = this.getStats(label)!;
      lines.push(`  ${label}: avg=${stats.avg.toFixed(1)}ms, max=${stats.max.toFixed(1)}ms, count=${stats.count}`);
    }
    return lines.join("\n");
  }
}

The extension also includes a file size guard: files exceeding 10,000 lines are skipped for analysis entirely, because the LSP server's response time scales with function count and large files may exceed the 100ms budget. The guard is implemented as a simple check before any LSP request, returning early with no decorations rather than blocking the editor with a slow request.

6.3 Graph Cache Strategy

The most expensive LSP request is borrowscope/ownershipGraph, which runs all 7 analysis passes for a single function. To avoid repeating this work on every decoration refresh, the extension maintains a per-function cache (graphCache: Map<string, any>). When the developer's cursor is inside a function, the extension checks the cache before sending a request. Cache hits are served with zero latency; cache misses trigger an LSP request and store the result.

The cache is invalidated entirely when an analysisUpdated notification arrives, because any function in the file may have been affected by the edit. This is a conservative strategy (it may invalidate functions that were not actually affected), but it guarantees correctness: the developer never sees stale ownership information after an edit. The trade-off is acceptable because the LSP server's incremental computation (Salsa) makes re-analysis fast even after cache invalidation.

The extension also implements a pre-fetch strategy to warm the cache proactively. After the workspace finishes loading (detected by the first successful response), the extension identifies all function declarations in the active file and fires parallel ownershipGraph requests for each. The results are stored in the cache, making subsequent CodeLens clicks and panel opens instantaneous. This pre-fetch runs in the background and does not block the editor; if it fails (e.g., the server is still loading), it silently retries after 10 and 20 seconds. 

// Pre-fetch all functions in background (warms Salsa cache)
const preFetchAll = async () => {
  const editor = vscode.window.activeTextEditor;
  if (!editor || editor.document.languageId !== "rust") return;

  const fnLines: number[] = [];
  for (let i = 0; i < editor.document.lineCount; i++) {
    if (/\bfn\s+\w+/.test(editor.document.lineAt(i).text)) fnLines.push(i);
  }

  // Fire all requests in parallel for maximum speed
  const results = await Promise.all(fnLines.map(line =>
    client.sendRequest("borrowscope/ownershipGraph", {
      textDocument: { uri }, position: { line, character: 4 },
    }).catch(() => null)
  ));

  results.forEach((r: any) => {
    if (r && r.function_name) graphCache.set(r.function_name, r);
  });
};

// Retry at multiple points during workspace loading
setTimeout(preFetchAll, 10000);
setTimeout(preFetchAll, 20000);
