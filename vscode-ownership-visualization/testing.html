8. Testing

The extension is validated by 689 tests distributed across 42 test files. Every source module has a corresponding test file that exercises its public API with both normal and edge cases. Tests run against a comprehensive VS Code mock (__mocks__/vscode.js) that simulates the editor environment without requiring a live VS Code instance. This enables fast, deterministic test execution in CI (under 10 seconds for the full suite) while still testing the actual extension logic including decoration application, panel HTML generation, runtime event processing, and configuration handling.

8.1 Test Architecture

The test suite uses Mocha as the test runner with a custom setup file (test-setup.js) that loads the VS Code mock before any test executes. The mock provides implementations for all VS Code APIs used by the extension: window.createTextEditorDecorationType, workspace.getConfiguration, languages.getDiagnostics, commands.registerCommand, Uri, Range, Position, Selection, StatusBarAlignment, MarkdownString, and more. The mock tracks all calls (decorations applied, commands registered, messages shown) so tests can assert on side effects.

Tests are organized by module: each source file src/foo.ts has a corresponding src/test/suite/foo.test.ts. This one-to-one mapping ensures complete coverage and makes it easy to find tests for any given feature. Tests are grouped using Mocha's describe/it blocks with descriptive names that document the expected behavior (e.g., "should apply blue decoration for shared borrow", "should detect rc_leak when ref_count never reaches 0").

The extension is compiled with esbuild for production (single bundled file) and with tsc for testing (individual files for accurate stack traces). The build and test pipeline runs: npm run build (esbuild bundle), tsc --noEmit false (type-check + emit for tests), then npx mocha --require ./test-setup.js (run all tests). All 689 tests must pass before any commit.

8.3 Testing Methodology

Tests follow a consistent pattern: arrange (set up mock data or configuration), act (call the function under test), assert (verify the output or side effects). For decoration tests, the assertion checks that editor.setDecorations was called with the correct decoration type and ranges. For panel tests, the assertion checks that the generated HTML contains expected elements (node circles, edge paths, table rows). For runtime tests, the assertion checks that events are correctly parsed, filtered, and mapped to static variables.

Edge cases are tested explicitly. The runtime parser tests include: empty event arrays, events with missing fields, events in both internally-tagged and externally-tagged JSON formats, events with timestamps of 0, and events with unicode variable names. The divergence detector tests include: Rc with ref_count that never reaches 0 (leak), variables that are moved and then have subsequent events (use-after-move), and borrows that span across await points (async_borrow_held). The configuration tests verify that every setting has a sensible default and that invalid values fall back gracefully.

The test suite runs in under 10 seconds on a standard development machine, making it practical to run on every save during development. The CI pipeline (GitHub Actions) runs the full suite on every push and pull request, ensuring that no regression is merged. Test failures block the build, and the failure output includes the specific assertion that failed with expected vs actual values.
