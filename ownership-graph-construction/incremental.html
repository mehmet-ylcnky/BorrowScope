5. Incremental Updates

5.1 Mutation Operations

After construction, the graph is not frozen. Real-world usage requires modifications: removing variables that are no longer relevant to the analysis, ending edges when new information arrives, or combining graphs from multiple instrumented functions into a unified view. The graph supports four mutation operations, each of which maintains all internal indices (adjacency lists, name index) consistently.

The most common mutation is mark_dropped(), which sets a node's dropped_at timestamp without removing it from the graph. The node remains queryable (you can still ask "when was this variable created?") but temporal queries will correctly report it as no longer alive after the drop time. This is the operation triggered by Event::Drop during construction.

The end_edge() operation similarly sets an edge's ended_at timestamp. A borrow edge that has been ended is no longer "active" at timestamps after its end time, but it remains in the graph for historical analysis. You can still ask "what borrows existed at t=30?" and get correct answers because the edge retains its full temporal metadata. 

impl OwnershipGraph {
    /// Mark a node as dropped. Does NOT remove it from the graph.
    pub fn mark_dropped(&mut self, id: NodeId, timestamp: u64);

    /// End an edge (set ended_at). Does NOT remove it from the graph.
    pub fn end_edge(&mut self, id: EdgeId, timestamp: u64);

    /// Remove a node AND all its connected edges. Destructive.
    pub fn remove_node(&mut self, id: NodeId);

    /// Remove a single edge. Updates adjacency lists.
    pub fn remove_edge(&mut self, id: EdgeId);
}

The destructive operations (remove_node and remove_edge) permanently delete elements from the graph. remove_node is a cascading operation: it removes the node itself and all edges where the node appears as either source or target. This prevents dangling edge references, which would cause the graph to fail validation. The operation also cleans the name index, removing the node's ID from its name entry.

The distinction between "ending" and "removing" is important. Ending preserves history (the edge existed, it just stopped being active). Removing erases history (the edge never existed as far as the graph is concerned). For most analysis scenarios, ending is preferred because it preserves the full temporal record. Removing is used for graph simplification: filtering out irrelevant nodes to focus on a subset of the program.

5.2 Graph Merging

The merge() operation combines two graphs into one, remapping all NodeIds and EdgeIds to avoid collisions. This is essential for building program-wide ownership graphs from per-function analysis. Each instrumented function produces its own event stream and its own graph. To answer cross-function questions ("does function A's return value get borrowed in function B?"), these graphs must be combined. 

/// Merge another graph into this one. Returns ID mapping.
pub fn merge(&mut self, other: &OwnershipGraph) -> HashMap<NodeId, NodeId>;

// Usage: combine graphs from two functions
let mut program_graph = OwnershipGraph::from_events(&fn_a_events);
let fn_b_graph = OwnershipGraph::from_events(&fn_b_events);
let id_map = program_graph.merge(&fn_b_graph);

// id_map: { NodeId(0) => NodeId(5), NodeId(1) => NodeId(6), ... }
// All IDs from fn_b_graph are remapped to avoid collision with fn_a's IDs

The merge operation proceeds in two phases. First, it iterates over all nodes in the source graph, creating new nodes in the destination graph with fresh IDs. The mapping from old IDs to new IDs is recorded in the returned HashMap. Second, it iterates over all edges in the source graph, remapping their source and target NodeIds using the mapping, then creating new edges in the destination graph.

Edge timestamps and metadata are preserved unchanged during merge. If a node in the source graph had dropped_at: Some(50), the merged node retains that value. This means temporal queries on the merged graph produce correct results for both the original and merged portions.

The returned HashMap<NodeId, NodeId> is useful for post-merge analysis. If you need to find a specific variable from the merged graph, you look up its original NodeId in the map to get its new ID in the combined graph. This is particularly important when establishing cross-function edges (e.g., a return value from function A being used in function B).

5.3 Index Rebuilding

The graph's internal indices (outgoing adjacency, incoming adjacency, name index) are not serialized. They are marked #[serde(skip)] because they contain redundant information that can be reconstructed from the node and edge vectors. This reduces serialized size by approximately 40% for typical graphs.

After deserialization (loading a graph from JSON or MessagePack), the rebuild_indices() method reconstructs all three indices in a single O(n + m) pass: 

pub fn rebuild_indices(&mut self) {
    self.outgoing.clear();
    self.incoming.clear();
    self.name_index.clear();

    for node in &self.nodes {
        self.name_index.entry(node.name().to_string())
            .or_default().push(node.id());
    }
    for edge in &self.edges {
        self.outgoing.entry(edge.source).or_default().push(edge.id);
        self.incoming.entry(edge.target).or_default().push(edge.id);
    }
}

This method is called automatically by the import functions (from_json(), from_msgpack()) so users never need to call it manually in normal usage. It is exposed publicly for advanced scenarios where the graph's internal vectors are modified directly (e.g., by a custom deserialization format or a graph transformation pass).

The rebuild cost is proportional to the graph size: O(n) for the name index (one HashMap insert per node) and O(m) for the adjacency lists (two HashMap inserts per edge, one for outgoing and one for incoming). For a graph with 10,000 nodes and 15,000 edges, this takes approximately 1-2ms, which is negligible compared to the I/O cost of reading the serialized file from disk.
