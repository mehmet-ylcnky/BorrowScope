3. Construction Algorithm

3.1 Event-to-Graph Mapping

The construction algorithm processes events in a single pass, maintaining a mapping from runtime variable IDs to graph NodeIds. The mapping is straightforward: each event type corresponds to exactly one graph operation. Events that create entities (variables, scopes) produce nodes. Events that establish relationships (borrows, moves, clones) produce edges. Events that terminate entities (drops, scope exits) update existing nodes and edges.

Not all 88 runtime event types produce graph elements. Many events record information that is useful for other analyses (loop iterations, binary operations, field accesses) but do not create ownership relationships. These are silently skipped during construction. The algorithm processes only the subset of events that represent structural ownership changes, which typically accounts for 30-50% of the total event stream.

Event TypeGraph OperationResult
Event::Newadd_variable()New node created, registered in var_ids map
Event::Borrowadd_borrow()Borrow edge from borrower to owner, tracked in active_borrows
Event::Moveadd_variable() + add_move()New destination node + move edge from source
Event::Dropmark_dropped() + end_edge()Node terminated, all active borrows on it ended
Event::RcCloneadd_rc_clone()Clone edge with strong_count metadata
Event::ArcCloneadd_arc_clone()Clone edge with strong_count metadata
Event::ClosureCaptureadd_capture()Capture edge with mode (ByRef, ByMutRef, ByMove)

Event::RegionEnteradd_scope(Block)Block scope node created

The mapping is deterministic: given the same event stream, the algorithm always produces the same graph. This property is essential for reproducibility and testing. It also means that the graph can be reconstructed from a saved event stream (JSON file) at any time, without needing access to the original program.

3.2 Active Borrow Tracking

The most subtle aspect of graph construction is determining when borrow edges end. Unlike node creation (which corresponds to a single event), borrow termination is implicit: a borrow ends when the borrower variable is dropped. There is no explicit "end borrow" event in the stream. The algorithm must correlate Borrow events with later Drop events to determine edge lifetimes.

The solution is an active_borrows HashMap that maps each variable's runtime ID to the list of borrow EdgeIds it currently holds. When a Borrow event is processed, the new edge's ID is pushed onto the borrower's active list. When a Drop event is processed for that borrower, all edges in its active list are terminated with the drop timestamp. 

let mut active_borrows: HashMap<String, Vec<EdgeId>> = HashMap::new();

// On Borrow event: record the edge as active for this borrower
let eid = graph.add_borrow(borrower, owner, mutable, timestamp);
active_borrows.entry(borrower_id.clone()).or_default().push(eid);

// On Drop event: end all borrows held by this variable
if let Some(edges) = active_borrows.remove(&var_id) {
    for eid in edges {
        graph.end_edge(eid, timestamp);
    }
}

This approach correctly handles several edge cases. A variable that borrows from multiple owners simultaneously (e.g., a struct that holds two references) will have multiple entries in its active list, and all are terminated together when the variable is dropped. A variable that is dropped without ever borrowing anything simply has no entry in the map, and the remove() call returns None harmlessly.

The HashMap is keyed by the runtime's string ID (e.g., "r_0") rather than the graph's NodeId. This is because the Drop event carries the runtime ID, not the graph ID. Using the same key type avoids an extra lookup step during the critical drop-processing path.

3.3 Variable ID Resolution

The runtime assigns each variable a unique string ID in the format "name_counter" (e.g., "x_0", "r_1", "data_2"). The counter increments globally across all variables, ensuring uniqueness even when multiple variables share the same name (shadowing). The construction algorithm maintains a var_ids: HashMap<String, NodeId> that maps these runtime IDs to graph NodeIds.

This mapping is essential for correlating events. When a Borrow event references owner_id: "x_0", the algorithm looks up "x_0" in var_ids to find the corresponding NodeId, then creates an edge targeting that node. If the lookup fails (the owner was never created, or the event stream is corrupted), the event is silently skipped rather than panicking. This defensive approach ensures that partial or truncated event streams still produce valid (if incomplete) graphs.

Variable shadowing is handled naturally by this scheme. When a function declares let x = 1; followed by let x = x + 1;, the runtime assigns IDs "x_0" and "x_1". Both map to distinct graph nodes, both appear in the graph's name_index under the key "x", and both can be queried independently. The graph preserves the full history of all declarations, not just the final one.

3.4 Handling Move Events

Move events require special treatment because they simultaneously create a new variable and establish a relationship. When the runtime records Event::Move { from_id: "a_0", to_name: "b", to_id: "b_0" }, the algorithm must:

First, create a new node for the destination variable b (since the move target may not have been seen before). Second, register "b_0" in the var_ids map. Third, create a Move edge from the source node to the destination node. The source node is not dropped by a move (it remains in the graph with its original created_at timestamp), but it is effectively invalidated. Any subsequent borrow or use of the source would be a use-after-move error, which the conflict detection module (Section 3 of the companion paper) can identify.

3.5 Complexity Analysis

The construction algorithm is O(n) in the number of events, with constant-factor overhead per event. Each event triggers at most one HashMap lookup, one HashMap insert, and one Vec push. The dominant cost is HashMap operations, which are O(1) amortized with occasional rehashing.

OperationCostFrequency
Node creation (add_variable)O(1) amortizedOnce per New/Move event
Edge creation (add_borrow, etc.)O(1) amortizedOnce per relationship event
Drop processingO(k) where k = active borrowsOnce per Drop event, k typically 0-3
ID lookup (var_ids.get)O(1)1-2 per event
Active borrow trackingO(1) insert/removeOnce per Borrow/Drop pair

Total construction time for n events is O(n) with a small constant factor dominated by HashMap operations. Memory usage is O(n + m) where n is the number of nodes and m is the number of edges, plus O(b) for the active_borrows map where b is the maximum number of simultaneously active borrows (typically much smaller than n).

In practice, construction of a graph from 10,000 events takes less than 10ms in release mode. This means that even for complex programs with hundreds of instrumented functions, graph construction adds negligible overhead to the development workflow.

3.6 The Complete Algorithm

The following code shows the core of the construction algorithm. Each event type is matched and dispatched to the appropriate graph operation. The var_ids and active_borrows maps maintain the state needed to correlate events across time. 

pub fn from_events(events: &[Event]) -> OwnershipGraph {
    let mut graph = OwnershipGraph::new();
    let mut var_ids: HashMap<String, NodeId> = HashMap::new();
    let mut active_borrows: HashMap<String, Vec<EdgeId>> = HashMap::new();

    for event in events {
        match event {
            Event::New { var_id, var_name, type_name, timestamp, .. } => {
                let id = graph.add_variable(var_name, type_name, *timestamp);
                var_ids.insert(var_id.clone(), id);
            }
            Event::Borrow { borrower_id, owner_id, mutable, timestamp, .. } => {
                if let (Some(&borrower), Some(&owner)) =
                    (var_ids.get(borrower_id), var_ids.get(owner_id))
                {
                    let eid = graph.add_borrow(borrower, owner, *mutable, *timestamp);
                    active_borrows.entry(borrower_id.clone())
                        .or_default().push(eid);
                }
            }
            Event::Drop { var_id, timestamp, .. } => {
                if let Some(&id) = var_ids.get(var_id) {
                    graph.mark_dropped(id, *timestamp);
                    if let Some(edges) = active_borrows.remove(var_id) {
                        for eid in edges {
                            graph.end_edge(eid, *timestamp);
                        }
                    }
                }
            }
            Event::Move { from_id, to_name, to_id, timestamp, .. } => {
                if let Some(&from) = var_ids.get(from_id) {
                    let to = graph.add_variable(to_name, "", *timestamp);
                    var_ids.insert(to_id.clone(), to);
                    graph.add_move(from, to, *timestamp);
                }
            }
            Event::RcClone { var_id, var_name, source_id, strong_count, timestamp, .. } => {
                let clone_id = *var_ids.entry(var_id.clone())
                    .or_insert_with(|| graph.add_variable(var_name, "Rc", *timestamp));
                if let Some(&src) = var_ids.get(source_id) {
                    graph.add_rc_clone(clone_id, src, *strong_count as u32, *timestamp);
                }
            }
            Event::FnEnter { fn_id, fn_name, timestamp, .. } => {
                let id = graph.add_scope(fn_name, ScopeKind::Function, *timestamp);
                var_ids.insert(fn_id.clone(), id);
            }
            Event::FnExit { fn_id, timestamp, .. } => {
                if let Some(&id) = var_ids.get(fn_id) {
                    graph.mark_dropped(id, *timestamp);
                }
            }
            _ => {} // Events without ownership relationships are skipped
        }
    }
    graph
}

The algorithm is intentionally defensive: every lookup uses if let Some rather than unwrap(), ensuring that malformed or truncated event streams produce incomplete graphs rather than panics. This robustness is important for real-world usage where event streams may be captured from programs that crash mid-execution.
