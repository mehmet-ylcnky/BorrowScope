4. Streaming Construction

4.1 The GraphStream Builder

Batch construction via from_events() requires all events to be available upfront. This works well for post-hoc analysis where the instrumented program has already finished executing and the complete event stream is available as a JSON file or in-memory buffer. However, for real-time visualization scenarios where events arrive one at a time during program execution, waiting for the full stream is not an option. The user wants to see the graph evolve as the program runs.

The GraphStream builder addresses this by processing events incrementally. It maintains the same internal state as the batch algorithm (the var_ids map and active_borrows tracker) but exposes a push() method that accepts a single event and returns what changed. This allows a visualization frontend to update its display after each event without rebuilding the entire graph. 

pub struct GraphStream {
    graph: OwnershipGraph,
    var_ids: HashMap<String, NodeId>,
    active_borrows: HashMap<String, Vec<EdgeId>>,
    callbacks: Vec<Box<dyn Fn(&GraphUpdate)>>,
}

impl GraphStream {
    pub fn new() -> Self;
    pub fn push(&mut self, event: &Event) -> GraphUpdate;
    pub fn push_all(&mut self, events: &[Event]) -> Vec<GraphUpdate>;
    pub fn drain_runtime(&mut self) -> Vec<GraphUpdate>;
    pub fn on_update(&mut self, callback: impl Fn(&GraphUpdate) + 'static);
    pub fn graph(&self) -> &OwnershipGraph;
    pub fn into_graph(self) -> OwnershipGraph;
}

The callbacks field stores registered listeners that are notified on every graph change. This enables a reactive programming model: the visualization layer registers a callback once, and the graph builder pushes updates to it automatically. The callback receives a reference to the GraphUpdate enum, which describes exactly what changed, allowing the frontend to perform targeted DOM updates rather than full re-renders.

4.2 Update Notifications

Each call to push() returns a GraphUpdate describing what changed in the graph. This is a discriminated union with five variants, each carrying the ID of the affected element: 

pub enum GraphUpdate {
    NodeAdded(NodeId),      // A new variable or scope was created
    EdgeAdded(EdgeId),      // A new relationship was established
    NodeDropped(NodeId),    // A variable was dropped (end_time set)
    EdgeEnded(EdgeId),      // A borrow edge was terminated
    NoOp,                   // Event did not produce a graph change
}

The NoOp variant is returned for events that do not produce graph changes (e.g., loop iterations, binary operations, field accesses). This allows consumers to distinguish meaningful updates from no-ops without inspecting the graph state. A visualization tool might skip re-rendering on NoOp, saving CPU cycles during event-heavy sections of the program.

The update carries only an ID, not the full node or edge data. This is intentional: the consumer can look up the full data from the graph reference (stream.graph().get_node(id)) if needed, but many consumers only need to know that something changed. For example, a node-count display only needs to increment on NodeAdded without fetching the node's details.

4.3 Equivalence Guarantee

A critical property of the streaming builder: processing events one at a time via push() produces the exact same graph as processing them all at once via from_events(). This is not merely a design goal but a tested invariant. The equivalence test constructs the same graph both ways and asserts structural equality: 

let batch_graph = OwnershipGraph::from_events(&events);

let mut stream = GraphStream::new();
stream.push_all(&events);
let stream_graph = stream.into_graph();

assert_eq!(batch_graph.node_count(), stream_graph.node_count());
assert_eq!(batch_graph.edge_count(), stream_graph.edge_count());

This guarantee means that analysis results (conflict detection, traversal, statistics) are identical regardless of which construction mode was used. A user can develop their analysis pipeline using batch mode (simpler to debug), then switch to streaming mode for production visualization without worrying about behavioral differences. The graph algorithms do not know or care how the graph was constructed.

The equivalence holds because both modes use the same internal logic. The batch from_events() function is literally implemented as creating a GraphStream and calling push_all(). There is no separate code path for batch construction, which eliminates the possibility of divergence.

4.4 Drain from Runtime

The drain_runtime() method bridges the streaming builder with the global event buffer maintained by borrowscope-runtime. It calls get_events() to retrieve all buffered events, processes each one through push(), and returns the list of updates. This is useful for periodic polling scenarios where a visualization tool checks for new events at regular intervals rather than receiving them via callback. 

// Periodic polling pattern for a visualization server
let mut stream = GraphStream::new();

loop {
    let updates = stream.drain_runtime();
    if !updates.is_empty() {
        send_to_websocket_clients(&updates);
    }
    std::thread::sleep(Duration::from_millis(100));
}

The polling interval determines the trade-off between latency and CPU usage. At 100ms intervals, the visualization updates 10 times per second, which is smooth enough for human perception while consuming minimal CPU. For high-frequency event streams (thousands of events per second), the polling approach naturally batches updates, sending them to the frontend in chunks rather than one at a time.

4.5 Callback-Based Real-Time Updates

For scenarios requiring immediate notification (zero-latency visualization, live debugging), the on_update() method registers a callback that fires synchronously after each graph change: 

use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

let node_count = Arc::new(AtomicUsize::new(0));
let counter = node_count.clone();

let mut stream = GraphStream::new();
stream.on_update(move |update| {
    if let GraphUpdate::NodeAdded(_) = update {
        counter.fetch_add(1, Ordering::Relaxed);
    }
});

stream.push_all(&events);
println!("Total nodes created: {}", node_count.load(Ordering::Relaxed));

Callbacks are invoked during push_all() for each event that produces a non-NoOp update. They execute synchronously on the same thread, so they should be lightweight (updating counters, pushing to a channel) rather than performing expensive operations (rendering, network I/O). For heavy processing, the callback should push the update into a channel that a separate thread consumes.

Multiple callbacks can be registered, and they fire in registration order. This enables composable observers: one callback updates a counter, another logs to a file, a third pushes to a WebSocket. Each operates independently without knowledge of the others.
