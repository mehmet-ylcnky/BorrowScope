7.1 Test Coverage

The implementation is validated with 259 tests organized across 9 test suites, each corresponding to a development milestone. This structure ensures that each capability is tested in isolation before being composed with others. The test suites range from basic data structure operations (can we create a node?) to full integration tests (can we load a real event stream from an instrumented program and produce a valid graph?).

The test count is not inflated by trivial assertions. Each test verifies a specific behavior or invariant that, if broken, would produce incorrect analysis results. For example, the 45 traversal tests cover not just "does DFS visit nodes?" but also "does DFS visit each node exactly once on a diamond graph?" and "does topological order place borrowers before owners?" These are the properties that downstream consumers (conflict detection, visualization) depend on.

7.2 Property-Based Invariants

Hand-written tests verify specific scenarios, but they cannot cover the combinatorial space of possible graphs. Property-based testing with proptest addresses this gap by generating random graphs and verifying that structural invariants hold regardless of the input. Each property test runs 256 cases with automatic shrinking on failure, meaning that any invariant violation produces a minimal reproducible example rather than a complex failing case.

Six invariants are verified, chosen because they represent fundamental correctness properties that all downstream analyses depend on:

  • Edge validity: Every edge references valid node IDs. A dangling edge reference would cause panics in traversal algorithms and produce incorrect adjacency results.
  • DFS uniqueness: DFS visits each reachable node exactly once. Duplicate visits would break cycle detection and produce incorrect component counts.
  • Monotonic node count: Adding nodes never decreases the count. This seems trivial but catches bugs in ID allocation or index maintenance.
  • JSON round-trip: Serializing to JSON and deserializing back preserves node and edge counts. This verifies that no data is lost during export/import.
  • Component coverage: Connected components partition all nodes with no node left out. A missing node would mean some variables are invisible to component-based analysis.
  • BFS monotonicity: BFS distances are non-decreasing in the result vector. This is a fundamental property of breadth-first search that shortest-path computation depends on.

The random graph generator produces graphs with 1-20 nodes and 0-30 edges, with random names, timestamps, and borrow directions. This covers a wide range of topologies including linear chains, stars, diamonds, disconnected components, and dense clusters. The generator avoids self-loops (which are invalid in ownership graphs) but allows multiple edges between the same pair of nodes (which represents multiple borrows over time).

7.3 Battle Test Validation

The graph construction is validated against real event streams captured from instrumented Rust programs. The examples/macro-integration/events.json fixture contains 117 events from a program exercising Rc, RefCell, closures, and method calls. This is not a synthetic test case but actual output from the BorrowScope runtime running on real code.

The validation checks two properties: first, that the graph builds without panic (no unexpected event formats, no missing IDs, no index corruption). Second, that the resulting graph passes the full validation suite (no dangling edges, no borrows outliving owners, no invalid timestamps). Both properties hold for the battle test fixture, confirming that the construction algorithm handles real-world event patterns correctly. 

let events: Vec<Event> = serde_json::from_str(&fixture_json).unwrap();
let graph = OwnershipGraph::from_events(&events);
assert!(graph.node_count() > 0);
assert!(is_valid(&graph));  // Full validation: no dangling refs, no invalid timestamps

The battle test events include patterns that are difficult to test synthetically: nested Rc<RefCell<Vec<T>>> types, closures capturing multiple variables, method chains that create temporary borrows, and drop ordering across scope boundaries. These patterns exercise the construction algorithm's handling of complex event sequences that simple unit tests do not cover.

These numbers confirm that graph construction and analysis add negligible overhead to the development workflow. A typical instrumented function producing 100-500 events can be fully analyzed (graph construction + conflict detection + statistics + DOT export) in under 5ms total. This is fast enough to run on every test execution without noticeable delay.

The performance scales linearly with event count, as expected from the O(n) construction algorithm. The constant factor is dominated by HashMap operations (insert and lookup), which are O(1) amortized but have higher constant overhead than array indexing. For graphs exceeding 100,000 events, the construction time approaches 100ms, which is still acceptable for batch analysis but may be noticeable in interactive scenarios. The streaming construction mode (Section 4) amortizes this cost over time, processing events as they arrive rather than in a single burst.

7.5 Export Format Comparison

Five export formats are provided, each optimized for a different use case. The choice of format depends on whether the consumer is a human (DOT, full JSON), a machine (MessagePack, compact JSON), or a web frontend (D3.js JSON). The following table compares their characteristics for a graph with 100 nodes and 150 edges:

FormatSizeHuman ReadableRound-tripUse Case
JSON (full)~15 KBYesYesDebugging, inspection, version control diffs
JSON (compact)~9 KBPartiallyYesStorage, API responses, transmission
MessagePack~6 KBNoYesEfficient storage, caching, large graphs
DOT (Graphviz)~4 KBYesNoRendered diagrams (SVG, PNG, PDF)

The size differences are significant for large graphs. A program with 10,000 nodes produces approximately 1.5 MB of full JSON, 900 KB of compact JSON, or 600 KB of MessagePack. For graphs that are stored on disk or transmitted over a network, the 60% size reduction from MessagePack is meaningful. For graphs that are only used locally and inspected by humans, full JSON's readability outweighs its size overhead.

Round-trip capability (export then import produces an identical graph) is verified by dedicated tests for JSON and MessagePack. DOT and D3.js formats are one-way exports designed for visualization tools; they do not contain enough information to reconstruct the full graph (e.g., DOT does not preserve NodeIds or temporal metadata). If persistence is needed, use JSON or MessagePack; if visualization is needed, use DOT or D3.js.
