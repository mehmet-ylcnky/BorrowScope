1. Introduction

1.1 The Flat Event Stream Problem

The BorrowScope system instruments Rust programs to emit ownership events at runtime. Each event records a single operation: a variable is created, a borrow begins, a value moves, a reference count increments, a lock is acquired. The result is a chronological log that faithfully captures every ownership operation in the program's execution. For a simple function with 10 variables, this might produce 30-50 events. For a complex function with iterators, closures, and smart pointers, the count can easily reach hundreds.

The fundamental limitation of a flat event stream is that it encodes relationships implicitly through temporal ordering and shared identifiers, rather than explicitly through structure. To determine that variable r borrows from variable data, you must find the Borrow event where borrower_id matches r's ID and owner_id matches data's ID. To determine whether that borrow is still active at a given point, you must scan forward for either a Drop event on r or the end of the stream. These are linear scans over the entire event history.

Consider a concrete example. A program creates a Vec, borrows it twice (once mutably), clones an Rc, and moves a value into a closure. The event stream looks like this: 

// Flat event stream (chronological order)
t=0   New      { var_id: "data_0", name: "data", type: "Vec<i32>" }
t=10  New      { var_id: "r_0",    name: "r",    type: "&Vec<i32>" }
t=10  Borrow   { borrower_id: "r_0", owner_id: "data_0", mutable: false }
t=20  New      { var_id: "rc_0",   name: "rc",   type: "Rc<String>" }
t=30  RcClone  { var_id: "rc2_0",  source_id: "rc_0", strong_count: 2 }
t=40  Drop     { var_id: "r_0" }
t=50  New      { var_id: "m_0",    name: "m",    type: "&mut Vec<i32>" }
t=50  Borrow   { borrower_id: "m_0", owner_id: "data_0", mutable: true }
t=70  Move     { from_id: "data_0", to_id: "moved_0", to_name: "moved" }
t=80  Drop     { var_id: "m_0" }
t=90  Drop     { var_id: "rc2_0" }
t=100 Drop     { var_id: "rc_0" }

From this stream, answering "who borrows from data?" requires scanning all Borrow events and filtering by owner_id == "data_0". Answering "is the borrow still active at t=45?" requires finding the borrow's start (t=10) and checking whether a corresponding Drop occurred before t=45 (it did, at t=40). Answering "what happened to data after the borrow ended?" requires scanning forward from t=40 to find the Move at t=70. Each of these queries is O(n) in the number of events.

These are fundamentally graph queries masquerading as list scans. The natural representation of ownership relationships is a directed graph where nodes are variables and edges are ownership operations. Once constructed, the graph enables O(1) adjacency queries, standard graph algorithms, and structural analysis that would be prohibitively expensive on the raw event stream.

1.2 Requirements for an Ownership Graph

An ownership graph for Rust is not a simple directed graph. It must capture the rich semantics of Rust's type system, where different kinds of "pointing to another value" have fundamentally different implications for memory safety, concurrency, and performance. A shared borrow (&T) allows read access but not mutation. A mutable borrow (&mut T) grants exclusive access. An Rc::clone creates shared ownership where the value lives until the last clone is dropped. A Mutex::lock blocks the thread until exclusive access is available. Each of these relationships has different rules about what can coexist, and the graph must distinguish them all.

Beyond type distinction, ownership relationships are inherently temporal. A borrow does not exist for the entire program's lifetime; it begins when the reference is created and ends when it is dropped. Two mutable borrows of the same variable are perfectly legal if they do not overlap in time. This means the graph must support temporal queries: "what borrows are active at timestamp 42?" is a question that a static graph cannot answer without additional metadata on each edge.

The graph must also support hierarchical containment. Variables exist within scopes (functions, blocks, loops), and understanding which variables belong to which scope is essential for drop-order analysis and lifetime visualization. A variable declared inside a loop body has a different lifetime pattern than one declared outside it, and the graph should represent this nesting.

Finally, the graph must support incremental construction. In a real-time visualization scenario, events arrive one at a time as the program executes. Rebuilding the entire graph from scratch on each new event would be prohibitively expensive for large programs. The graph must support efficient single-event updates that maintain all internal indices consistently.

1.3 Contributions

This paper presents the design and implementation of borrowscope-graph, a Rust crate that addresses all of these requirements. The crate transforms the flat event stream produced by borrowscope-runtime into a structured ownership graph that supports constant-time adjacency queries, temporal filtering, and standard graph algorithms.

The type system defines 2 node kinds (variables and scopes) and 11 edge kinds that cover every ownership relationship expressible in Rust's type system. The edge kinds were derived by analyzing the 88 event types in the runtime and grouping them by the ownership relationship they represent, ensuring that no semantic information is lost during the transformation.

The construction algorithm processes events in a single O(n) pass, maintaining a HashMap of active borrows for correct edge termination. Two construction modes are provided: from_events() for batch processing after execution completes, and GraphStream for streaming construction with update callbacks. Both modes produce identical graphs, a property verified through dedicated equivalence tests.

The graph supports incremental modifications after construction (node removal, edge removal, graph merging) with consistent index maintenance. Integration with borrowscope-runtime is provided through from_runtime(), which reads the global event buffer and constructs the graph in a single call. The implementation is validated with 259 tests including property-based invariant verification and benchmarked with Criterion to confirm sub-millisecond construction times for typical program sizes.
