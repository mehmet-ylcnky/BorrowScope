2. The Node/Edge Type System

2.1 Node Types

The graph contains two kinds of nodes, unified under a Node enum. Each node carries a unique NodeId (a newtype around usize, cheap to copy and compare) and temporal metadata indicating when it was created and when it ceased to exist. The decision to use only two node types, rather than a richer hierarchy, reflects a deliberate trade-off: variables are the primary entities in Rust's ownership model, and scopes provide the containment context needed for drop-order analysis. Adding more node types (e.g., separate types for parameters, temporaries, statics) would complicate the API without enabling new queries.

The VariableNode is the primary entity. Every let binding, function parameter, and temporary value that the runtime tracks becomes a variable node. It carries the variable's name and fully-qualified type string (e.g., "Rc<Vec<i32>>"), enabling type-aware queries without needing access to the original source code. The is_copy flag distinguishes types where assignment is a copy (no ownership transfer) from types where assignment is a move, which fundamentally changes how edges are interpreted.

The ScopeNode provides containment context. It represents the function or block that encloses a set of variables, with a ScopeKind enum distinguishing functions from blocks, loops, and match arms. Scope nodes enable hierarchical queries: "which variables are declared inside this loop?" or "what is the nesting depth of this borrow?" The entered_at and exited_at timestamps define the scope's lifetime, which bounds the lifetimes of all variables it contains. 

/// Opaque node identifier. Cheap to copy and compare.
pub struct NodeId(pub usize);

/// A variable in the ownership graph.
pub struct VariableNode {
    pub id: NodeId,
    pub name: String,
    pub type_name: String,
    pub created_at: u64,
    pub dropped_at: Option<u64>,
    pub scope_depth: u32,
    pub is_copy: bool,
    pub is_mutable: bool,
}

impl Node {
    pub fn is_alive_at(&self, timestamp: u64) -> bool;
    pub fn start_time(&self) -> u64;
    pub fn end_time(&self) -> Option<u64>;
}

The is_alive_at() method is the foundation for temporal queries. It uses a half-open interval: a node is alive at timestamp t if t >= created_at and either dropped_at is None (still alive) or t < dropped_at. This convention means that at the exact moment of drop, the variable is no longer alive, which matches Rust's semantics where the destructor has already run.

2.2 Edge Types

Edges represent ownership relationships between nodes. Each edge is directed (from source to target), typed (one of 11 kinds), and temporal (has a creation time and optional end time). The direction convention is consistent: the source is the entity that "acts on" the target. A borrower points to its owner. A clone points to its source. A move points from the old location to the new one.

The 11 edge kinds cover every ownership relationship that Rust's type system expresses. They are grouped into four categories based on their ownership semantics:

Borrowing relationships create temporary access without transferring ownership. The original owner retains the value, and the borrow must end before the owner can be moved or dropped. BorrowShared allows multiple simultaneous readers, while BorrowMut grants exclusive access. RefCellBorrow is semantically similar but enforced at runtime rather than compile time, making it relevant for panic analysis.

Ownership transfer moves the value from one variable to another. After a Move, the source variable is invalidated and cannot be used. ChannelSend is a special case of ownership transfer that crosses thread boundaries, making it relevant for concurrency analysis.

Shared ownership via RcClone and ArcClone creates multiple owners of the same value. The value is dropped only when the last owner is dropped (reference count reaches zero). WeakDowngrade creates a non-owning reference that does not prevent deallocation.

Structural relationships include LockAcquire (synchronization), ClosureCapture (variable captured by a closure with a specific mode), and ScopeContains (hierarchical containment).

pub struct Edge {
    pub id: EdgeId,
    pub source: NodeId,
    pub target: NodeId,
    pub kind: EdgeKind,
    pub created_at: u64,
    pub ended_at: Option<u64>,
}

impl Edge {
    pub fn is_active_at(&self, timestamp: u64) -> bool;
    pub fn is_borrow(&self) -> bool;
    pub fn is_mutable(&self) -> bool;
    pub fn duration(&self) -> Option<u64>;
}

The ended_at field is what makes edges temporal rather than permanent. A borrow edge is created when the borrow begins and ended when the borrower is dropped. This allows the graph to answer temporal queries like "what borrows are active at timestamp 42?" by filtering edges where created_at <= 42 < ended_at. Edges that never end (e.g., a move, which is a permanent transfer) have ended_at: None.

2.3 Why 11 Edge Kinds

A simpler graph might use just 3 edge types: borrow, move, and clone. However, this loses critical semantic information that downstream analyses depend on. Consider three scenarios where the distinction matters:

Conflict detection needs to distinguish BorrowShared from BorrowMut. Two simultaneous BorrowShared edges on the same target are perfectly legal (multiple readers). But a BorrowMut edge conflicts with any other borrow edge on the same target. If both were collapsed into a generic "borrow" type, the conflict detector would either miss real conflicts or produce false positives.

Cycle detection needs to distinguish RcClone from ArcClone. An Rc cycle causes a memory leak (reference count never reaches zero). An Arc cycle causes the same leak but also indicates a potential deadlock if the cycle involves mutexes. Collapsing both into "clone" would lose the thread-safety distinction.

Visualization benefits from distinguishing RefCellBorrow from regular borrows. A RefCell::borrow_mut() can panic at runtime if another borrow is active, which is a fundamentally different failure mode than a compile-time borrow error. Visualization tools can highlight RefCell borrows with a warning indicator that regular borrows do not need.

The 11 edge kinds were derived by analyzing the 88 event types in borrowscope-runtime and grouping them by the ownership relationship they represent. Events that create the same kind of relationship (e.g., Event::Borrow with mutable: false and Event::RefCellBorrow with mutable: false) map to different edge kinds because their runtime semantics differ, even though their compile-time semantics are similar.

2.4 The OwnershipGraph Structure

The central data structure stores nodes and edges with dual adjacency indices for efficient traversal in both directions. The design prioritizes query performance over memory compactness: three HashMaps provide O(1) access patterns for the most common operations. 

pub struct OwnershipGraph {
    nodes: Vec<Node>,
    edges: Vec<Edge>,
    outgoing: HashMap<NodeId, Vec<EdgeId>>,  // node -> outgoing edges
    incoming: HashMap<NodeId, Vec<EdgeId>>,  // node -> incoming edges
    name_index: HashMap<String, Vec<NodeId>>, // name -> nodes
    next_node_id: usize,
    next_edge_id: usize,
}

The outgoing map answers "who does this variable borrow from?" or "where was this value moved to?" in O(1). The incoming map answers the reverse: "who borrows from this variable?" or "where did this value come from?" Both directions are needed because ownership queries are inherently bidirectional. A conflict detector needs incoming edges (to find all borrows on a target). A move-chain tracker needs outgoing edges (to follow the value forward).

The name_index provides O(1) lookup by variable name, which is the primary way users identify variables. It handles shadowed variables naturally: if a function declares let x = 1; followed by let x = x + 1;, both nodes are stored under the name "x", and the index returns a slice of both NodeIds. Callers can disambiguate using timestamps or scope depth.

The indices are marked #[serde(skip)] in the serialization derive, meaning they are not included in JSON or MessagePack exports. This avoids redundant data in serialized form (the indices can be reconstructed from the node and edge vectors). After deserialization, rebuild_indices() reconstructs all three maps in O(n + m) time.
