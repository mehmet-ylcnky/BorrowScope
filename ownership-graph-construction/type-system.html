2. The Node/Edge Type System

2.1 Node Types

The graph contains two kinds of nodes, unified under a Node enum. Each node carries a unique NodeId (a newtype around usize, cheap to copy and compare) and temporal metadata indicating when it was created and when it ceased to exist.

Node TypeRepresentsKey Fields
VariableNodeA variable binding in source codename, type_name, created_at, dropped_at, scope_depth, is_copy, is_mutable
ScopeNodeA scope boundary (function, block, loop, match)name, kind, entered_at, exited_at

The VariableNode is the primary entity. Every let binding, function parameter, and temporary value that the runtime tracks becomes a variable node. The ScopeNode provides containment context: it represents the function or block that encloses a set of variables. 

/// Opaque node identifier. Cheap to copy and compare.
pub struct NodeId(pub usize);

/// A variable in the ownership graph.
pub struct VariableNode {
    pub id: NodeId,
    pub name: String,
    pub type_name: String,
    pub created_at: u64,
    pub dropped_at: Option<u64>,
    pub scope_depth: u32,
    pub is_copy: bool,
    pub is_mutable: bool,
}

impl Node {
    pub fn is_alive_at(&self, timestamp: u64) -> bool;
    pub fn start_time(&self) -> u64;
    pub fn end_time(&self) -> Option<u64>;
}

2.2 Edge Types

Edges represent ownership relationships between nodes. Each edge is directed (from source to target), typed (one of 11 kinds), and temporal (has a creation time and optional end time). The 11 edge kinds cover every ownership relationship that Rust's type system expresses:

EdgeKindRust ConceptSemantics
BorrowShared&TImmutable borrow: source borrows from target
BorrowMut&mut TMutable borrow: exclusive access
MoveOwnership transferValue moves from source to target
RcCloneRc::cloneShared ownership (single-threaded), carries strong_count
ArcCloneArc::cloneShared ownership (thread-safe), carries strong_count
WeakDowngradeRc::downgradeNon-owning reference
RefCellBorrowRefCell::borrow[_mut]Runtime borrow checking, carries mutable flag
LockAcquireMutex::lockSynchronization primitive, carries lock_type
ClosureCaptureClosure capturesVariable captured by closure, carries CaptureMode
ScopeContainsScope nestingVariable is contained within a scope
ChannelSendSender::sendOwnership transfer across thread boundary
pub struct Edge {
    pub id: EdgeId,
    pub source: NodeId,
    pub target: NodeId,
    pub kind: EdgeKind,
    pub created_at: u64,
    pub ended_at: Option<u64>,
}

impl Edge {
    pub fn is_active_at(&self, timestamp: u64) -> bool;
    pub fn is_borrow(&self) -> bool;
    pub fn is_mutable(&self) -> bool;
    pub fn duration(&self) -> Option<u64>;
}

2.3 Why 11 Edge Kinds

A simpler graph might use just 3 edge types: borrow, move, and clone. However, this loses critical semantic information. Consider the difference between RefCell::borrow() and a regular &T borrow: both create shared references, but the RefCell variant performs runtime borrow checking and can panic. Similarly, Mutex::lock() creates a guard that holds exclusive access, but it also blocks the thread and can deadlock. These distinctions matter for conflict detection, performance analysis, and visualization.

The 11 edge kinds were derived by analyzing the 88 event types in borrowscope-runtime and grouping them by the ownership relationship they represent. Each event type maps to exactly one edge kind, ensuring that no information is lost during graph construction.

2.4 The OwnershipGraph Structure

The central data structure stores nodes and edges with dual adjacency indices for efficient traversal in both directions: 

pub struct OwnershipGraph {
    nodes: Vec<Node>,
    edges: Vec<Edge>,
    outgoing: HashMap<NodeId, Vec<EdgeId>>,  // node -> outgoing edges
    incoming: HashMap<NodeId, Vec<EdgeId>>,  // node -> incoming edges
    name_index: HashMap<String, Vec<NodeId>>, // name -> nodes
    next_node_id: usize,
    next_edge_id: usize,
}

The dual adjacency lists enable O(1) lookup of both outgoing edges (who does this variable borrow from?) and incoming edges (who borrows from this variable?). The name index provides O(1) lookup by variable name, handling shadowed variables (multiple nodes with the same name) by returning a slice of all matching NodeIds.
