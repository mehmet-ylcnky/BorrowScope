2. System Architecture

The architecture of borrowscope-runtime is built on three fundamental design principles: (1) event sourcing for temporal analysis and replay capabilities, (2) separation of concerns between tracking, storage, and analysis, and (3) zero-cost abstractions through conditional compilation. This section details the architectural decisions that enable comprehensive ownership tracking with minimal runtime overhead.

2.1 Event-Sourced Design

The system employs an event sourcing architecture where all ownership operations are captured as immutable events and stored in a temporal sequence. This design provides several critical advantages: complete audit trails of ownership operations, ability to reconstruct ownership state at any point in time, support for incremental graph construction, and separation of tracking overhead from analysis complexity.

Event Flow and Lifecycle

Each ownership operation follows a consistent lifecycle from instrumentation to analysis. When application code invokes a tracking function, the system generates a unique timestamp using atomic operations, creates an immutable event object with complete metadata, acquires the global tracker lock, appends the event to the storage vector, and releases the lock. This entire process completes in approximately 75 nanoseconds, with the majority of time spent in mutex acquisition and vector append operations. 

// Event lifecycle example
use borrowscope_runtime::*;

// 1. Application code with instrumentation
let data = track_new("data", vec![1, 2, 3]);
// ↓ Internally generates Event::New

// 2. Event structure (simplified)
struct Event {
    timestamp: u64,        // Atomic counter
    var_name: String,      // "data"
    var_id: String,        // "data_0" (unique)
    type_name: String,     // "alloc::vec::Vec"
}

// 3. Storage in global tracker
static TRACKER: Mutex<Vec<Event>> = /* ... */;

// 4. Later analysis (on-demand)
let events = get_events();
let graph = build_graph(&events);

Design Rationale

The event sourcing approach was chosen over alternative architectures for several compelling reasons. Direct graph construction during tracking would impose significantly higher overhead due to complex graph operations under lock contention. Sampling-based approaches would miss critical ownership operations and fail to provide complete audit trails. The event sourcing model defers expensive analysis operations until explicitly requested, maintains complete temporal ordering for replay and debugging, enables multiple analysis algorithms to operate on the same event stream, and supports incremental updates for real-time visualization.

2.2 Core Components

2.2.1 Global Tracker

The global tracker serves as the central coordination point for all ownership tracking operations. It maintains a thread-safe event store, generates unique identifiers for variables, and provides atomic timestamp generation. The implementation uses carefully chosen synchronization primitives to minimize contention while ensuring correctness. 

use parking_lot::Mutex;
use lazy_static::lazy_static!;
use std::sync::atomic::{AtomicU64, Ordering};

// Global tracker instance (singleton pattern)
lazy_static! {
    static ref TRACKER: Mutex<Tracker> = Mutex::new(Tracker::new());
}

// Lock-free timestamp generation
static TIMESTAMP: AtomicU64 = AtomicU64::new(0);

// Tracker implementation
pub struct Tracker {
    /// Event storage (append-only for thread safety)
    events: Vec<Event>,

    /// Variable ID counter (monotonically increasing)
    var_counter: u64,
}

impl Tracker {
    /// Generate next timestamp (lock-free, ~1-2ns)
    fn next_timestamp() -> u64 {
        TIMESTAMP.fetch_add(1, Ordering::Relaxed)
    }

    /// Generate unique variable ID
    fn next_var_id(&mut self, name: &str) -> String {
        let id = format!("{}_{}", name, self.var_counter);
        self.var_counter += 1;
        id
    }

    /// Record a new variable creation event
    pub fn record_new(&mut self, var_name: &str, type_name: &str) -> String {
        let timestamp = Self::next_timestamp();
        let var_id = self.next_var_id(var_name);

        self.events.push(Event::New {
            timestamp,
            var_name: var_name.to_string(),
            var_id: var_id.clone(),
            type_name: type_name.to_string(),
        });

        var_id
    }
}

Synchronization Strategy

The choice of synchronization primitives directly impacts performance. The system uses parking_lot::Mutex instead of std::sync::Mutex for 40-60% better performance in low-contention scenarios. Atomic operations with Relaxed ordering suffice for timestamp generation since strict ordering is not required—only uniqueness matters. The append-only event vector avoids complex synchronization for reads, as the vector is only accessed under lock for writes. 

// Performance comparison of synchronization approaches

// Approach 1: std::sync::Mutex (baseline)

// Average lock acquisition: ~25ns

// Approach 2: parking_lot::Mutex (chosen)

// Average lock acquisition: ~15ns (40% faster)

// Approach 3: Lock-free data structures

// Not suitable for temporal event streams

2.2.2 Event Taxonomy

The event taxonomy represents the complete spectrum of Rust's ownership operations. Each event type captures specific ownership semantics with sufficient metadata for accurate reconstruction of ownership relationships. The taxonomy is organized hierarchically into six major categories, each addressing distinct aspects of Rust's ownership model. 

// Complete event taxonomy (simplified)
use serde::{Serialize, Deserialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(tag = "type")]
pub enum Event {
    // ═══════════════════════════════════════════════════════
    // Category 1: Basic Ownership Operations
    // ═══════════════════════════════════════════════════════

    /// Variable creation (ownership begins)
    New {
        timestamp: u64,
        var_name: String,
        var_id: String,
        type_name: String,
    },

    /// Borrow creation (shared or mutable reference)
    Borrow {
        timestamp: u64,
        borrower_name: String,
        borrower_id: String,
        owner_id: String,
        mutable: bool,
    },

    /// Ownership transfer (move semantics)
    Move {
        timestamp: u64,
        from_id: String,
        to_name: String,
        to_id: String,
    },

    /// Variable destruction (ownership ends)
    Drop {
        timestamp: u64,
        var_id: String,
    },

    // ═══════════════════════════════════════════════════════
    // Category 2: Smart Pointers (Reference Counting)
    // ═══════════════════════════════════════════════════════

    /// Rc<T> allocation
    RcNew {
        timestamp: u64,
        var_name: String,
        var_id: String,
        type_name: String,
        strong_count: usize,  // Initially 1
        weak_count: usize,    // Initially 0
    },

    /// Rc<T> clone (shared ownership)
    RcClone {
        timestamp: u64,
        var_name: String,
        var_id: String,
        source_id: String,
        strong_count: usize,  // Incremented count
        weak_count: usize,
    },

    // Arc<T> variants (thread-safe reference counting)
    ArcNew { /* similar to RcNew */ },
    ArcClone { /* similar to RcClone */ },

    // ═══════════════════════════════════════════════════════
    // Category 3: Interior Mutability
    // ═══════════════════════════════════════════════════════

    /// RefCell<T> allocation
    RefCellNew {
        timestamp: u64,
        var_name: String,
        var_id: String,
        type_name: String,
    },

    /// RefCell borrow (runtime borrow checking)
    RefCellBorrow {
        timestamp: u64,
        borrow_id: String,
        refcell_id: String,
        is_mutable: bool,
        location: String,  // file:line for debugging
    },

    // Cell<T> variants (Copy types only)
    CellNew { /* ... */ },
    CellGet { /* ... */ },
    CellSet { /* ... */ },

    // ═══════════════════════════════════════════════════════
    // Category 4: Unsafe Operations
    // ═══════════════════════════════════════════════════════

    /// Raw pointer creation
    RawPtrCreated {
        timestamp: u64,
        var_name: String,
        var_id: String,
        ptr_type: String,  // "*const T" or "*mut T"
        address: usize,     // Memory address
        location: String,
    },

    /// Unsafe block boundaries
    UnsafeBlockEnter {
        timestamp: u64,
        block_id: String,
        location: String,
    },

    UnsafeBlockExit {
        timestamp: u64,
        block_id: String,
        location: String,
    },

    // FFI and transmute operations
    FfiCall { /* ... */ },
    Transmute { /* ... */ },

    // Category 5: Static and Const
    // ═══════════════════════════════════════════════════════

    StaticInit { /* ... */ },
    StaticAccess { /* ... */ },
    ConstEval { /* ... */ },

Event Design Principles

Each event type adheres to strict design principles: (1) Immutability: Events are never modified after creation, ensuring temporal consistency. (2) Complete Metadata: Each event contains sufficient information for standalone interpretation without requiring context from other events. (3) Unique Identification: All entities (variables, borrows, blocks) receive unique identifiers for unambiguous correlation. (4) Location Tracking: Source code locations are captured for debugging and visualization. (5) Serialization Support: All events serialize to JSON with tagged union format for easy parsing and filtering.

2.2.3 Memory Layout and Performance

The memory layout of events is optimized for cache efficiency and minimal allocation overhead. Each event occupies approximately 80 bytes on average, with the event vector using contiguous memory allocation for optimal cache locality. The system employs several strategies to minimize memory overhead while maintaining complete tracking fidelity.

2.2.4 Thread Safety Model

The thread safety model balances correctness with performance. The global tracker is protected by a mutex, ensuring that event insertion is atomic and events maintain temporal ordering across threads. However, timestamp generation uses lock-free atomic operations to minimize contention. This hybrid approach provides strong consistency guarantees while avoiding unnecessary synchronization overhead. 

// Thread safety guarantees

// Scenario 1: Concurrent tracking from multiple threads
use std::thread;

reset();

let handles: Vec<_> = (0..4)
    .map(|i| {
        thread::spawn(move || {
            let data = track_new(
                &format!("thread_{}", i),
                vec![i; 100]
            );
            // Each thread gets unique timestamps
            // Events are serialized by mutex
        })
    })
    .collect();

for handle in handles {
    handle.join().unwrap();
}

// Result: 4 events with unique timestamps
// Order depends on thread scheduling
let events = get_events();
assert_eq!(events.len(), 4);

Concurrency Patterns

The system handles several concurrent access patterns: (1) Multiple Writers: Multiple threads can track events concurrently, with the mutex serializing insertions. (2) Read-After-Write: Event queries acquire the same mutex, ensuring visibility of all previously written events. (3) Lock-Free Reads: Timestamp generation never blocks on the event storage mutex. (4) Atomic Ordering: Relaxed ordering suffices for timestamps since the mutex provides happens-before relationships for event ordering.
