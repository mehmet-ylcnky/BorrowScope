4. What Gets Instrumented

4.1 Variable Bindings

Every let statement represents the birth of a new owned value, and the macro captures each one. When a variable is bound, the macro records its name, infers the type from the initializer's syntax where possible, and assigns a unique tracking ID that will follow this value through its lifetime. This ID enables correlation—when the variable is later borrowed, moved, or dropped, the tracking system can link those events back to this original binding. The macro handles simple bindings, pattern destructuring, and bindings with type annotations uniformly: 

let x = String::from("hello");  // track_ownership("x", "String", id=1)
let y = 42;                       // track_ownership("y", "i32", id=2)
let z = vec![1, 2, 3];            // track_ownership("z", "Vec", id=3)

4.2 Borrows and Moves

Reference creation and ownership transfers are the heart of Rust's memory safety model, and the macro tracks both with precision. When a reference is created with & or &mut, the macro emits a borrow event that links the new reference to its source variable, recording whether the borrow is shared (immutable) or exclusive (mutable). When a value is moved—assigned to a new variable without Copy—the macro tracks the ownership transfer, marking the source as moved and the destination as the new owner. This creates a chain of custody that visualization tools can render as ownership flowing through the program: 

let r = &x;           // track_borrow("r", id=4, from="x", id=1, Immutable)
let m = &mut x;       // track_borrow("m", id=5, from="x", id=1, Mutable)
let owned = x;        // track_move("owned", id=6, from="x", id=1)

4.3 Function Calls

Function calls are where ownership often changes hands, and the macro instruments these boundaries carefully. When a value is passed by value to a function, it's a move—the caller loses ownership and the function receives it. When passed by reference, it's a borrow that must end before the function returns. Return values represent new ownership flowing back to the caller. The macro cannot see inside the called function (unless it's also annotated), but it tracks the ownership events visible at the call site, providing a complete picture of how values flow into and out of function boundaries: 

consume(x);           // track_move to function parameter
borrow(&x);           // track_borrow for reference parameter
let r = produce();    // track_ownership for return value

4.4 Scope and Drops

Rust's deterministic destruction is one of its defining features—values are dropped exactly when they go out of scope, in reverse declaration order. The macro tracks scope boundaries explicitly, emitting enter and exit events for each block. More importantly, it maintains a scope stack during transformation, recording which variables were declared in each scope. When a scope exits, the macro generates drop events for each variable in reverse order, mirroring the compiler's actual drop behavior. This enables visualization of the "cleanup" phase that's usually invisible, showing exactly when destructors run and resources are released: 

{                              // track_scope_enter("block")
    let temp = String::new();  // track_ownership("temp", id=7)
}                              // track_drop("temp", id=7), track_scope_exit("block")

4.5 Smart Pointers

Rust's smart pointer ecosystem provides powerful abstractions for shared ownership and interior mutability, but these abstractions can obscure what's actually happening with ownership. The macro provides deep tracking for the entire smart pointer family, revealing the hidden complexity. For reference-counted types like Rc<T> and Arc<T>, it tracks creation, cloning (which increments the reference count), and downgrading to weak references. For interior mutability types like RefCell<T> and Cell<T>, it tracks the dynamic borrow checking that happens at runtime. Each clone is linked to its source, enabling visualization of how shared ownership spreads through a program: 

// Reference counting
let rc = Rc::new(data);       // track_rc_new
let rc2 = rc.clone();         // track_rc_clone (links to source)
let weak = Rc::downgrade(&rc);// track_rc_downgrade
let upgraded = weak.upgrade();// track_weak_upgrade

// Interior mutability
let cell = RefCell::new(x);   // track_refcell_new
let guard = cell.borrow();    // track_refcell_borrow
let guard = cell.borrow_mut();// track_refcell_borrow_mut

// Thread-safe variants
let arc = Arc::new(data);     // track_arc_new
let arc2 = arc.clone();       // track_arc_clone

4.6 Concurrency Primitives

Concurrent Rust code introduces ownership patterns that are notoriously difficult to reason about—threads take ownership of closures, mutexes guard shared data behind lock guards, and channels transfer ownership between threads. The macro tracks these patterns explicitly, making the invisible handoffs visible. Thread spawning captures which variables the closure takes ownership of; mutex locks show when exclusive access begins and ends; channel operations reveal ownership crossing thread boundaries. This is particularly valuable for debugging deadlocks and data races, as the event stream shows exactly when each thread acquired or released resources: 

// Thread management
let handle = thread::spawn(|| { });  // track_thread_spawn
handle.join().unwrap();               // track_thread_join

// Synchronization
let guard = mutex.lock().unwrap();   // track_mutex_lock
let guard = rwlock.read().unwrap();  // track_rwlock_read
let guard = rwlock.write().unwrap(); // track_rwlock_write

// Channels
tx.send(value).unwrap();              // track_channel_send
let received = rx.recv().unwrap();   // track_channel_recv

4.7 Control Flow

Control flow structures affect when and whether ownership operations occur. A variable declared inside a loop is created and dropped on each iteration; a value moved in one branch of an if may still be available in the other. The macro tracks loop iterations, branch decisions, and early exits to provide context for the ownership events that occur within them. This is essential for understanding conditional ownership patterns—the visualization can show that a value was dropped early due to a return, or that a move only happened because a particular match arm was taken: 

// Loops
for item in collection { }  // track_loop_enter/exit, iteration tracking
while condition { }         // track_loop_enter/exit

// Branches
if condition { } else { }   // track_branch (which arm taken)
match value { ... }         // track_match_arm

// Control flow
break;                      // track_break
continue;                   // track_continue
return value;               // track_return
value?;                      // track_try (? operator)

4.8 Expressions

Compound expressions create new values from existing ones, and each has distinct ownership semantics. Struct literals take ownership of their field values; tuple and array expressions similarly consume their elements. Range expressions create iterator-like values; casts may copy or reinterpret data; index expressions borrow from collections. The macro tracks these expression types to show how values are assembled and transformed, completing the picture of data flow beyond simple variable-to-variable transfers: 

// Struct/tuple/array literals
Point { x: 1, y: 2 }         // track_struct_literal
(a, b, c)                    // track_tuple_expr
[1, 2, 3]                    // track_array_expr

// Other expressions
0..10                        // track_range_expr
value as u64                // track_cast_expr
array[index]                 // track_index_expr

4.9 Closures

Closures in Rust capture variables from their environment, and the capture mode—by reference, by mutable reference, or by value—determines ownership behavior. The macro analyzes closure expressions to determine which variables are captured and how. A closure without move borrows by default, taking references to captured variables; a move closure takes ownership, transferring values into the closure's environment. This tracking is crucial for understanding why a variable becomes unavailable after a closure is created, or why a closure can outlive its creating scope: 

let x = String::from("hello");

// Borrow capture
let f = || println!("{}", x);  // track_closure(captures: [("x", Borrow)])

// Move capture
let f = move || x;            // track_closure(captures: [("x", Move)])

4.10 Async/Await

Asynchronous Rust introduces unique ownership challenges: async blocks capture variables like closures, and .await points are where the future may be suspended, potentially holding borrows across yield points. The macro tracks async block creation and each await point, enabling visualization of how ownership flows through asynchronous code. This is particularly valuable for diagnosing lifetime errors in async contexts, where the compiler's error messages can be cryptic and the actual ownership flow spans multiple suspension points: 

async { computation }        // track_async_block
future.await                 // track_await
