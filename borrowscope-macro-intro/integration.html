6. Integration with Runtime

The macro and runtime form a complete system, each handling a distinct phase of ownership tracking. The macro operates at compile time, transforming source code to inject tracking calls. The runtime operates at execution time, receiving those calls and building data structures for analysis. Neither component is useful alone—the macro generates code that calls the runtime, and the runtime expects calls in the format the macro produces. Understanding their relationship clarifies how ownership tracking works end-to-end:

Event Flow

The journey from annotated source code to ownership visualization spans four distinct phases. At compile time, the Rust compiler invokes the macro when it encounters the #[trace_borrow] attribute; the macro parses, analyzes, and transforms the function, emitting instrumented code that the compiler then type-checks and compiles normally. At runtime, when the instrumented function executes, each tracking call sends an event to the runtime's global tracker, which stores events in a thread-safe, lock-free buffer designed for minimal overhead. During analysis, the runtime processes the event stream to construct ownership graphs—data structures representing variables as nodes and ownership/borrow relationships as edges, with temporal information enabling queries at any point in execution history. Finally, for output, the runtime provides APIs to export graphs in various formats: JSON for custom tooling, DOT for Graphviz visualization, or direct integration with the BorrowScope web interface for interactive exploration.

Zero-Cost When Disabled

Both crates support conditional compilation. When the tracking feature is disabled, all tracking calls compile to no-ops, achieving true zero-cost abstraction as described in the borrowscope-runtime whitepaper. This means you can leave #[trace_borrow] annotations in production code and simply disable the feature for release builds—no code changes required, no runtime overhead incurred.
