5. Usage Guide

5.1 Basic Usage

Getting started with borrowscope-macro requires two dependencies: the macro crate that provides the #[trace_borrow] attribute, and the runtime crate that receives and stores the tracking events. Add both to your Cargo.toml: 

[dependencies]
// check most recent version in crates.io
borrowscope-macro = "0.1"
borrowscope-runtime = "0.1"

With the dependencies in place, annotate any function you want to trace with the #[trace_borrow] attribute. The macro transforms the function at compile time, injecting tracking calls that emit events to the runtime. The original function's behavior remains unchanged—it accepts the same arguments, returns the same values, and has the same side effects. The only addition is the ownership event stream: 

use borrowscope_macro::trace_borrow;

#[trace_borrow]
fn my_function(data: String) -> usize {
    let len = data.len();
    len
}

After executing traced functions, the runtime holds a buffer of ownership events that can be retrieved for analysis, visualization, or export. The get_events() function returns an iterator over all recorded events in chronological order. Each event contains the operation type, variable names, tracking IDs, timestamps, and contextual information like scope depth and source location: 

use borrowscope_runtime::get_events;

fn main() {
    my_function(String::from("hello"));
    
    for event in get_events() {
        println!("{:?}", event);
    }
}

5.2 Configuration Options

The macro supports extensive configuration via attribute arguments, allowing developers to tune the instrumentation for their specific needs. Whether you want minimal overhead for production profiling, comprehensive tracing for debugging, or something in between, the configuration system provides the flexibility to achieve it.

Presets

For common use cases, presets provide sensible defaults with a single argument. The minimal preset tracks only the essential ownership operations—creation, moves, and drops—producing a clean event stream focused on ownership transfer. The standard preset (the default) enables most features for general-purpose tracing. The verbose preset enables everything including function entry/exit events, while debug adds diagnostic warnings for ambiguous patterns: 

#[trace_borrow(preset = "minimal")]   // Only new/move/drop
#[trace_borrow(preset = "standard")]  // Default - most features
#[trace_borrow(preset = "verbose")]   // Everything including functions
#[trace_borrow(preset = "debug")]     // All features + diagnostics

Feature Flags

For fine-grained control, individual feature flags enable or disable specific categories of tracking. Each flag corresponds to a family of ownership operations, allowing you to focus on exactly what matters for your analysis. Disabling irrelevant features reduces both compile-time overhead (less generated code) and runtime overhead (fewer events):

FlagDefaultDescription
track_newtrueVariable creation (let x = ...)
track_movetrueOwnership transfers
track_droptrueScope exit drops
track_borrowtrue&x and &mut x
track_smart_pointerstrueRc, Arc, RefCell, Cell, Weak, Pin, Cow, etc.
track_loopstruefor, while, loop
track_branchestrueif/else, match
track_control_flowtruebreak, continue, return
track_trytrue? operator
track_methodstrueclone, lock, unwrap, etc.
track_asynctrueasync blocks, await
track_unsafetrueunsafe blocks, raw pointers
track_expressionstruestruct, tuple, array, range, cast
track_functionsfalseFunction entry/exit

Flags can be combined freely. For example, to focus exclusively on borrow tracking without the noise of loop iterations and branch decisions, disable those specific features. Conversely, enable track_functions when you need to see the call hierarchy alongside ownership events: 

// Disable specific features
#[trace_borrow(track_loops = false, track_branches = false)]
fn focused_trace() { }

// Enable function entry/exit (off by default)
#[trace_borrow(track_functions = true)]
fn with_function_events() { }

Variable Filtering

When tracing complex functions, the event stream can become overwhelming. Variable filtering lets you focus on specific variables using glob patterns with * (matches any sequence) and ? (matches single character) wildcards. The include pattern specifies which variables to track; the exclude pattern specifies which to ignore. When both are provided, a variable must match include and not match exclude to be tracked: 

// Only track variables starting with "data"
#[trace_borrow(include = "data*")]
fn filtered() { }

// Exclude temporary variables
#[trace_borrow(exclude = "_*,tmp*")]
fn no_temps() { }

// Combine include and exclude
#[trace_borrow(include = "user*", exclude = "user_cache*")]
fn precise_filter() { }

Sampling

For performance-sensitive code or long-running analysis, sampling reduces overhead by tracking only a fraction of events. The sample_rate parameter accepts a value between 0.0 and 1.0, representing the probability that any given event will be recorded. For reproducible results—essential when debugging or comparing runs—provide a sample_seed to initialize the random number generator deterministically: 

// Track only 10% of events
#[trace_borrow(sample_rate = 0.1)]
fn sampled() { }

// Reproducible sampling with seed
#[trace_borrow(sample_rate = 0.5, sample_seed = 42)]
fn reproducible() { }

Conditional Compilation

Tracing overhead, however small, may be unacceptable in production builds. Conditional compilation modes let you enable tracing only in specific contexts. The debug_only mode compiles tracking calls only in debug builds; test_only enables them only when running tests. For maximum flexibility, feature_gate ties tracing to a custom Cargo feature, letting users opt in explicitly: 

// Only trace in debug builds
#[trace_borrow(debug_only)]
fn debug_trace() { }

// Only trace in tests
#[trace_borrow(test_only)]
fn test_trace() { }

// Gate on custom feature
#[trace_borrow(feature_gate = "tracing")]
fn feature_gated() { }

Diagnostics

The macro operates on syntax alone and cannot always determine the correct tracking for ambiguous patterns—FFI calls, unions, and certain generic contexts may produce incorrect or incomplete traces. Diagnostic options enable compile-time warnings when the macro encounters these patterns, alerting you to potential issues before runtime. The warn_ambiguous flag enables all warnings; specific flags like warn_ffi and warn_unions target particular categories: 

// Warn about patterns that may not track correctly
#[trace_borrow(warn_ambiguous = true)]
fn with_warnings() { }

// Specific warning categories
#[trace_borrow(warn_ffi = true, warn_unions = true)]
fn ffi_aware() { }

5.3 Output Interpretation

The runtime emits events in execution order, creating a chronological record of every ownership operation. Each event carries contextual information: the operation type, the variables involved, their tracking IDs for correlation, and a timestamp for ordering. The event stream below shows a typical function execution—scope entry, parameter ownership, a borrow for the method call, the drop at scope exit, and finally scope exit: 

ScopeEnter { name: "my_function", timestamp: 1001 }
VariableCreated { name: "data", type: "String", id: 1, timestamp: 1002 }
BorrowCreated { borrower: "len", id: 2, owner: "data", owner_id: 1, kind: Immutable, timestamp: 1003 }
VariableDropped { name: "data", id: 1, timestamp: 1004 }
ScopeExit { name: "my_function", timestamp: 1005 }

The tracking IDs enable correlation across events. When BorrowCreated references owner_id: 1, visualization tools can draw a line from the borrow back to the VariableCreated event with id: 1. This linking is what transforms a flat event stream into a rich ownership graph. The runtime's graph construction algorithms process these events to build data structures representing ownership relationships, borrow lifetimes, and scope hierarchies—enabling interactive visualization, conflict detection, and temporal queries like "what was borrowing this variable at timestamp X?"
