7. Limitations

The macro operates on syntax only—it cannot access type information. This is not a design flaw but a fundamental constraint of Rust's compilation model. Procedural macros execute early in the compilation pipeline, after lexing and parsing but before type checking, name resolution, and borrow checking. At this stage, the macro sees tokens organized into an Abstract Syntax Tree, but it has no knowledge of what types those tokens represent, which traits they implement, or how the borrow checker will analyze them. This constraint shapes everything the macro can and cannot do.

The Core Constraint

Procedural macros execute before type checking in Rust's compilation pipeline. The macro sees tokens and syntax, not types and semantics. When the macro encounters let y = x;, it cannot know whether this is a move (ownership transfer) or a copy (value duplication)—that depends on whether the type of x implements the Copy trait, information that simply isn't available yet. The macro must make decisions based on syntactic patterns and heuristics, which work correctly for most code but inevitably fail for certain patterns.

What the Macro Cannot Detect

The type information barrier manifests in several specific limitations. The most fundamental is the move vs copy distinction: without knowing whether a type implements Copy, the macro cannot determine if an assignment transfers ownership or merely duplicates the value. It defaults to assuming moves for non-primitive types, which is correct for String and Vec but wrong for user-defined Copy types. FFI boundaries present another challenge—the macro cannot distinguish extern "C" functions from regular Rust functions, so ownership transfers across FFI boundaries may not be tracked correctly. Trait method resolution is impossible without type information; when the macro sees x.clone(), it cannot know which Clone implementation will be called or whether the method even exists. Finally, generic bounds can cause the macro's wrapping to break compilation—inserting a temporary variable may violate bounds that the macro cannot see.

Practical Implications

These limitations do not render the macro useless—far from it. The vast majority of Rust code follows patterns that the macro handles correctly. Simple ownership transfers, explicit borrows with & and &mut, standard library smart pointers, and common control flow all work as expected. The problematic patterns tend to be concentrated in specific areas: FFI-heavy code, heavily generic libraries, and code that relies on Copy semantics for user-defined types. For educational use, debugging application logic, and visualizing ownership in typical Rust programs, the macro provides accurate and valuable insights despite these theoretical limitations.

Mitigation Strategies

Several approaches can mitigate these limitations. Annotation systems allow developers to provide hints the macro cannot infer—marking types as Copy, identifying FFI boundaries, or specifying trait implementations. Validation tools can post-process the generated code to detect likely errors before runtime. Enhanced heuristics can improve accuracy for common patterns—for example, assuming primitive types are Copy and well-known standard library types follow their documented semantics. The diagnostic warning system already implemented in the macro represents a first step, alerting developers to potentially problematic patterns at compile time.
