3. Architecture

3.1 Two-Phase Build Strategy

The core insight behind BorrowScope is that type information can be extracted before compilation and communicated to the procedural macro via a file. This decouples semantic analysis from macro expansion while working within Rust's compilation model rather than against it. Rather than attempting to modify the compiler or inject information through unstable channels, the system uses a simple contract: the analyzer writes a JSON file, and the macro reads it. Both tools operate on the same source code but at different times, creating a temporal bridge across the compilation boundary.

This strategy has a key advantage over alternatives like compiler plugins or custom toolchains: it requires no modifications to the Rust compiler, works with stable Rust, and integrates with existing build systems. The JSON file acts as a stable interface between two independent programs, each of which can evolve independently as long as the schema contract is maintained.

The user workflow is straightforward: run the analyzer once, then build and run normally. The analyzer needs to re-run only when variable types or method signatures change, not on every edit. In practice, this means the analysis step is infrequent during active development, since most code changes (logic, formatting, comments) do not alter the type-level properties that the macro depends on. 

# Step 1: Analyze (generates .borrowscope/type-info.json)
$ cargo run -p borrowscope-analyzer -- .

# Step 2: Build (macro reads type-info.json automatically)
$ cargo build

# Step 3: Run (events captured at runtime)
$ cargo run

3.2 Data Flow: JSON as Inter-Process Communication

The analyzer and macro run in different processes at different times. They communicate through a JSON file at .borrowscope/type-info.json. The schema (v3.0) is designed for backward compatibility: all fields use #[serde(default)], so older macro versions gracefully ignore new fields. 

// Simplified schema structure
{
  "version": "3.0",
  "files": {
    "src/main.rs": [
      {
        "name": "data",
        "ty": "Rc<RefCell<Vec<i32>>>",
        "initializer_kind": "rc_new",
        "is_rc": true,
        "is_clone": true,
        "copy_semantics": false,
        "function_name": "example",
        "method_calls": [
          {
            "method": "borrow",
            "operation": "core::cell::borrow",
            "self_borrow": "immutable"
          }
        ]
      }
    ]
  },
  "by_function": { ... },  // Primary lookup index
  "by_name": { ... },      // Fallback lookup index
  "await_points": { ... }, // 17 additional analysis maps
  ...
}

The macro loads this file once via a OnceLock and builds two lookup indices: by_function (primary, keyed by function name + variable name + declaration index) and by_name (fallback, keyed by variable name only). This enables O(1) lookups during transformation. The two-tier design handles variable shadowing correctly: when the same name appears multiple times within a function, the declaration index disambiguates them. The by_name fallback covers cases where the macro cannot determine the enclosing function context, ensuring that type information is always available even in edge cases like top-level bindings or complex nested scopes.

3.3 Why Three Separate Crates

The separation into three crates is not arbitrary. Each operates at a different execution boundary with different constraints. Rust's compilation model enforces strict isolation between these boundaries: a procedural macro crate cannot link against arbitrary libraries, a pre-build tool cannot inject code into the compiler, and a runtime library cannot access compile-time information. The three-crate design respects these boundaries while establishing communication channels between them.

The communication pattern is unidirectional: the analyzer produces data that the macro consumes, and the macro produces code that the runtime executes. There are no circular dependencies or bidirectional channels. This makes each component independently testable and replaceable. A different analyzer (perhaps one using rustc internals directly) could produce the same JSON schema, and the macro would work identically.

3.4 Design Decision: Static Pre-Build vs Runtime Type Analysis

An alternative design would embed type analysis into the runtime, inspecting values via std::any::TypeId or trait object introspection. We chose the static pre-build approach for several reasons:

Advantages of static analysis:
  • Zero runtime overhead for type resolution. All classification happens once, before compilation. The generated tracking calls contain string literals, not hash lookups.
  • Access to creation semantics. The distinction between Rc::new() and Rc::clone() depends on analyzing the expression that creates a value, not the value's type at rest. At runtime, both produce an Rc<T>.
  • Full trait resolution. rust-analyzer resolves trait implementations, generic bounds, and type aliases across the entire workspace. A runtime analyzer would only see concrete monomorphized types.
  • No unstable features required. Runtime type introspection in Rust is deliberately limited. TypeId requires 'static bounds, and there is no stable reflection API.
Trade-offs acknowledged:
  • Two-step build workflow (analyzer must run before cargo build)
  • Stale data risk if source changes between analysis and compilation
  • Cannot observe dynamically-dispatched types behind dyn Trait
  • Toolchain coupling to ra_ap_* crate versions

The static approach was chosen because BorrowScope's primary goal is classifying ownership patterns, not just types. Distinguishing Rc::new from Rc::clone, identifying guard types, and recognizing interior mutability wrappers are distinctions that exist in source code and are erased by compilation. A runtime analyzer would see types but not creation semantics.
