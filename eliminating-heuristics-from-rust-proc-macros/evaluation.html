7.2 Heuristic Elimination

35 distinct string-matching heuristics were identified and eliminated across 7 categories. Each heuristic represented a point of potential failure: a place where the macro could produce incorrect tracking events if the naming convention did not hold. The elimination of these heuristics is not merely a code quality improvement; it is a correctness guarantee. The system now produces correct tracking events for any valid Rust code, regardless of naming conventions, type aliases, or import paths.

The deleted code includes the entire smart_pointer.rs file (17 detect_* functions), the infer_self_borrow_type() heuristic function, and approximately 220 lines of dead fallback code. This represents a net reduction in macro complexity despite the addition of new tracking capabilities, because semantic dispatch via a single field read is simpler than multi-branch string matching with edge-case handling.

7.3 Battle Test: ripgrep

To validate that BorrowScope works on real-world code, we applied it directly to the source code of ripgrep, one of the most widely-used Rust projects (45,000+ GitHub stars). We chose ripgrep because it represents idiomatic, performance-critical Rust code written by an experienced developer. The globset crate within ripgrep handles glob pattern matching with complex string manipulation, iterator chains, and Option/Result handling. We instrumented 10 functions across 3 files:

  • pathutil.rs: file_name(), file_name_ext(), normalize_path()
  • glob.rs: literal(), ext(), prefix(), suffix(), required_ext(), basename_literal()
  • lib.rs: matches_candidate_into(), new(), is_match_candidate(), matches_candidate()
Result: All 287 existing ripgrep tests pass with the instrumented source code. The analyzer achieves full type resolution for all instrumented functions. Zero modifications were needed to the macro or analyzer. This confirms that the system handles idiomatic Rust patterns (iterator chains, Option combinators, slice operations, OsStr conversions) without any special-casing.

7.4 Battle Test: lru Crate

The lru crate implements an LRU cache with complex ownership patterns (HashMap, linked list nodes, raw pointers). This crate was chosen because it exercises ownership patterns that are particularly challenging for instrumentation: mutable borrows through &mut self methods, interior data structure manipulation, and closure-based APIs like get_or_insert. We instrumented 6 test functions exercising cache operations:

  • Basic operations: put, get, peek, contains
  • String ownership: owned keys/values, pop
  • Iteration: iter(), filter(), collect()
  • LRU promotion/demotion and eviction
  • get_or_insert with closure
  • Cache resize
Result: 107 ownership events tracked across all tests. One macro fix was required (method borrow wrapping for &mut self methods on owned values). This fix was a general improvement to the pending_inserts pattern that benefits all projects, not a crate-specific workaround. After the fix, all tests pass cleanly.

7.5 Battle Test: uuid Crate

The uuid crate provides UUID generation with String conversions, byte arrays, and collection operations. This crate was selected because it exercises a different ownership profile than the previous tests: Copy types (UUIDs are 128-bit values), collection operations on owned data, and heavy use of Option/Result combinators. We instrumented 6 test functions:

  • UUID creation (v4 random, v5 namespace-based)
  • HashMap with UUID keys, iterator patterns
  • Vec sorting, dedup, min/max
  • Option/Result unwrap patterns
  • Clone and move semantics
Result: 88 ownership events tracked. Zero fixes needed. Passed on first attempt with no modifications to the macro or analyzer. This zero-fix result on a previously unseen codebase demonstrates that the system generalizes beyond the patterns it was developed against.

7.6 Test Suite

Beyond unit and integration tests, the 24 compiled examples serve as end-to-end validation. Each example is a standalone Rust program that exercises specific macro features and must compile and run successfully. These examples catch issues that unit tests miss, such as interactions between multiple tracking features within a single function or conflicts between the macro's transformations and Rust's type inference.
