2. Background

2.1 Rust's Compilation Pipeline

Rust compiles source code through a strict sequence of phases where each stage depends on the output of the previous one. No information flows backward from later stages to earlier ones, meaning that a phase cannot access results that have not yet been computed. The critical ordering for this work is: 

  ┌───────────┐      ┌───────────┐     ┌───────────┐      ┌───────────┐     ┌───────────┐
  │  PARSING  │────▶│   MACRO   │────▶│   NAME    │────▶│   TYPE    │────▶│  BORROW   │
  │           │      │ EXPANSION │     │RESOLUTION │      │ CHECKING  │     │ CHECKING  │
  └───────────┘      └───────────┘     └───────────┘      └───────────┘     └───────────┘
       │                 │                 │                 │                 │
       ▼                 ▼                 ▼                 ▼                 ▼
  Token Stream     Expanded AST      Resolved Names     Typed HIR        Validated MIR
                        ▲
                        │
              Proc macros run HERE
              (no type info available)

Procedural macros execute at the second stage. At this point, the compiler knows the syntactic structure of the code but nothing about types, traits, or lifetimes. The type checker runs after macro expansion, operating on the already-transformed code.

The diagram above illustrates this ordering. Source code is first parsed into a token stream. Procedural macros then transform these tokens, producing an expanded AST. Only after expansion does the compiler resolve names (linking identifiers to their definitions), perform type checking (inferring and verifying types), and finally run the borrow checker (validating ownership and lifetime rules). The wall between macro expansion and type checking is absolute: no information flows backward from later stages to earlier ones.

2.2 Procedural Macro Constraints

A procedural macro is a function that takes a TokenStream and returns a TokenStream. It can inspect tokens, restructure them, and generate new code. What it cannot do:

  • Query the type of any expression or variable
  • Check whether a type implements a trait
  • Resolve a path to its definition (e.g., determine that MyVec is an alias for Vec)
  • Access the filesystem in a portable, guaranteed way
  • Communicate with external tools or processes

For example, given this input: 

use std::rc::Rc;
type SharedData = Rc<Vec<i32>>;

// The macro sees only tokens, not types
#[trace_borrow]
fn example() {
    let data = SharedData::new(vec![1, 2, 3]);  // Macro sees "SharedData::new"
    let cloned = data.clone();                  // Macro sees ".clone()" but on what type?
    let guard = data.borrow();                  // Is this RefCell::borrow or Borrow::borrow?
}

The macro cannot determine that SharedData resolves to Rc<Vec<i32>>, that .clone() here is Rc::clone (reference count increment, not deep copy), or whether .borrow() is the RefCell method or the Borrow trait method. Each of these distinctions carries different ownership semantics: an Rc::clone increments a reference count, while a deep clone allocates new memory; a RefCell::borrow performs runtime borrow checking, while Borrow::borrow is a simple conversion. Making the wrong choice leads to incorrect tracking events that misrepresent the program's actual ownership behavior.

2.3 rust-analyzer as a Semantic Oracle

rust-analyzer is the official language server for Rust, providing IDE features like go-to-definition, type hints, and refactoring. Its internal analysis engine performs full type resolution, trait solving, and semantic analysis on Rust code. Crucially, this engine is published as a set of reusable crates on crates.io under the ra_ap_* prefix.

The key crate is ra_ap_hir, which provides the Semantics struct. Given a syntax node, Semantics can answer questions that procedural macros cannot: 

use ra_ap_hir::{Semantics, HirDisplay};

// Resolve the type of a variable binding
let ty = sema.type_of_pat(&pattern)?.original;

// Check trait implementations
let is_copy = ty.is_copy(db);
let is_clone = ty.impls_trait(db, clone_trait, &[]);

// Resolve a method call to its definition
let func = sema.resolve_method_call(&method_call_expr)?;
let canonical_path = get_function_path(&func, db);  // "alloc::rc::clone"

// Determine self-borrow type (&self, &mut self, self)
let access = func.self_param(db)?.access(db);  // Shared, Exclusive, or Owned

BorrowScope uses version 0.0.318 of the ra_ap_* crates, leveraging 17 distinct APIs across six crates: ra_ap_hir for high-level semantic queries, ra_ap_ide_db for the root database infrastructure, ra_ap_load-cargo for workspace loading and sysroot discovery, ra_ap_project_model for Cargo project structure, ra_ap_syntax for AST traversal, and ra_ap_vfs for virtual file system management. Together, these provide type resolution, trait detection, method resolution, FFI detection, and ADT classification capabilities identical to what powers rust-analyzer's IDE features.

The analyzer runs as a standalone binary before compilation, loading the full project workspace (including standard library metadata via sysroot discovery), performing semantic analysis on every source file, and producing a structured JSON file. The procedural macro then reads this file at expansion time via a OnceLock-based lazy loader, gaining access to the complete type information that the compilation pipeline would otherwise withhold.
