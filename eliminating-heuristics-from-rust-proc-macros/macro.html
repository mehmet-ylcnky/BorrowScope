5. The Macro (borrowscope-macro)

5.1 Type Info Loading and Lookup

The macro loads .borrowscope/type-info.json once per compilation via a OnceLock. The project root is discovered through the CARGO_MANIFEST_DIR environment variable, which Cargo sets for every crate during compilation. If the file is missing, the macro panics with a clear error message directing the user to run the analyzer. This fail-fast behavior is intentional: silent degradation to heuristic-based tracking would undermine the entire purpose of the system.

The loading happens exactly once regardless of how many functions carry the #[trace_borrow] attribute. The OnceLock guarantees thread-safe initialization even when the compiler processes multiple crates in parallel. The deserialized data is stored as a &'static reference, eliminating any per-function allocation overhead. 

static TYPE_INFO_CACHE: OnceLock<Option<TypeInfoCache>> = OnceLock::new();

pub fn get_type_info() -> Option<&'static TypeInfoCache> {
    TYPE_INFO_CACHE
        .get_or_init(|| find_project_root().and_then(|root| TypeInfoCache::load(&root)))
        .as_ref()
}

// Two-tier lookup: function-scoped (primary) → name-only (fallback)
pub fn lookup_in_function(fn_name: &str, var_name: &str, decl_index: Option<u32>)
    -> Option<&'static VariableTypeInfo>;

pub fn lookup_by_name(var_name: &str)
    -> Option<&'static VariableTypeInfo>;

The function-scoped lookup handles variable shadowing correctly. Each variable is identified by the triple (function_name, var_name, decl_index), where decl_index distinguishes multiple declarations of the same name within a function. This is essential for Rust code, where shadowing is idiomatic: patterns like let x = x.unwrap() or let config = config.build() are common and must resolve to the correct type at each point.

5.2 Initializer Kind Dispatch

When the macro encounters a let binding, it looks up the variable's initializer_kind from the analyzer data and dispatches to the appropriate tracking function. This single match statement replaces all 17 detect_* functions that previously existed in the deleted smart_pointer.rs. The old approach required pattern matching on AST structure (looking for paths like Rc::new, Arc::clone, etc.), which failed for any non-standard construction pattern.

The initializer_kind is a string tag computed by the analyzer based on the resolved type and expression form. For example, "rc_clone" is assigned when the expression is a call to Clone::clone on an Rc<T> type, regardless of whether the user wrote Rc::clone(&x), x.clone(), or Clone::clone(&x). All three produce the same tag because the analyzer resolves through the trait system. 

fn transform_by_initializer_kind(&mut self, init_kind: &str, ...) -> Option<Expr> {
    match init_kind {
        "rc_new"       => Some(track_rc_new_with_id(...)),
        "arc_new"      => Some(track_arc_new_with_id(...)),
        "rc_clone"     => Some(track_rc_clone_with_id(...)),
        "box_new"      => Some(track_box_new(...)),
        "refcell_new"  => Some(track_refcell_new(...)),
        "cell_new"     => Some(track_cell_new(...)),
        "weak_new"     => Some(track_weak_new(...)),
        "pin_new"      => Some(track_pin_new(...)),
        "cow_new"      => Some(track_cow_owned(...)),
        "channel_new"  => None, // Handled by tuple destructuring
        "atomic_new"   => Some(track_atomic_new(...)),
        "duration_new" => Some(track_duration_new(...)),
        "instant_new"  => Some(track_instant_new(...)),
        // ... 78 categories total
        _ => None, // Falls through to generic track_new
    }
}

5.3 Semantic Method Call Dispatch

For method calls on tracked variables, the macro reads the operation field (canonical path) from MethodCallInfo and dispatches based on exact path matching. This replaces all method_name == "..." heuristics that plagued the previous implementation. The old approach could not distinguish between methods with the same name on different types, leading to incorrect tracking for common names like lock, write, get, and set.

The canonical path includes the full module hierarchy from the crate root to the method definition. This means "std::sync::poison::rwlock::write" (which acquires a write lock) is never confused with "std::io::Write::write" (which writes bytes to a stream) or "core::ptr::write" (which performs an unsafe memory write). Each has completely different ownership semantics, and only the canonical path can distinguish them reliably. 

// mc_info.operation contains the canonical path from the analyzer
let semantic_op = mc_info.and_then(|mc| mc.operation.clone());

match semantic_op.as_deref() {
    Some("core::cell::set")                    => transform_cell_set(...),
    Some("core::cell::borrow")                 => transform_refcell_borrow(...),
    Some("alloc::borrow::to_mut")              => transform_cow_to_mut(...),
    Some("std::sync::poison::mutex::lock")     => transform_lock(..., "mutex"),
    Some("std::sync::poison::rwlock::read")    => transform_lock(..., "rwlock_read"),
    Some("std::sync::mpsc::send")              => transform_channel_send(...),
    Some("std::thread::join_handle::join")     => transform_thread_join(...),
    // ... 18 canonical path patterns total
    _ => {}
}

The critical difference from the previous approach: "std::sync::poison::rwlock::write" is unambiguous. It cannot be confused with io::Write::write or MaybeUninit::write because the canonical path includes the full module hierarchy. When no canonical path is available (the method call was not found in the analyzer data), the macro falls back to generic method call tracking without attempting to guess the operation type.

5.4 Self-Borrow Inference

The macro previously used a 47-pattern heuristic function that guessed whether a method takes &self, &mut self, or self based on method name prefixes (push* = mutable, as_* = immutable, into_* = consuming). This entire function is replaced by reading the self_borrow field from the analyzer. The heuristic approach was fundamentally flawed: Vec::push takes &mut self, but Button::push in a UI framework might take &self. The method name alone carries no reliable information about the receiver's borrow type.

The analyzer extracts the self parameter's access mode directly from the function signature in the type system. This is always correct because it reads the actual declaration rather than inferring from naming conventions. The only case where the macro uses a default is when the method call was not found in the analyzer data (stale JSON), in which case it conservatively assumes Immutable, which is safe because it never generates incorrect mutable borrow tracking. 

// Before: 47 heuristic patterns
fn infer_self_borrow_type(method_name: &str) -> SelfBorrowType {
    if method_name.starts_with("push") || method_name.starts_with("insert") { Mutable }
    else if method_name.starts_with("as_") || method_name == "len" { Immutable }
    else if method_name.starts_with("into_") { Consuming }
    // ... 47 patterns
}

// After: single field read from analyzer data
fn infer_self_borrow_type(...) -> SelfBorrowType {
    match method_call_info.self_borrow.as_deref() {
        Some("immutable") => SelfBorrowType::Immutable,
        Some("mutable")   => SelfBorrowType::Mutable,
        Some("consuming") => SelfBorrowType::Consuming,
        _ => SelfBorrowType::Immutable, // Safe default
    }
}

5.5 Clone Trait Verification

A method named clone is not necessarily Clone::clone. User types can have inherent methods named clone that do something entirely different: a GitRepo might have a .clone() method that performs a git clone operation, or a Process might have .clone() that forks the process. The macro uses the analyzer's is_trait_method and trait_name fields to verify whether a .clone() call is actually the Clone trait implementation.

This distinction matters for tracking accuracy: Clone::clone creates a new owned value (which should emit a track_clone event), while an inherent .clone() method is just a regular method call with whatever semantics the author defined. Without this verification, the macro would incorrectly report ownership duplication for methods that happen to share the name. 

let is_clone_trait = mc_info
    .and_then(|mc| mc.is_trait_method)  // true if from a trait impl
    .unwrap_or(true);                    // default: assume Clone

if is_clone_trait {
    transform_clone(expr, &mc);  // Emit track_clone
} else {
    transform_method_call(method_call);  // Treat as regular method
}

5.6 The safe_parse_quote! Pattern

A significant challenge emerged during implementation: syn::parse_quote! panics when the generated token stream contains closures with block bodies (e.g., || { println!("..."); 42 }). This is a divergence between syn's parser and rustc's parser for blocks inside function arguments. The issue is subtle: syn parses the token stream eagerly and fails on certain block positions, while rustc's parser handles them correctly during actual compilation.

This divergence was discovered during the ripgrep battle test, where real-world code frequently passes closures with multi-statement bodies as arguments to iterator methods like .filter(), .map(), and .for_each(). The macro must wrap these expressions in tracking calls, but parse_quote! panics when attempting to construct the wrapped form.

The solution is a custom macro that uses quote! + syn::parse2 (which returns Result instead of panicking) with a fallback to the original expression: 

macro_rules! safe_parse_quote {
    ($fallback:expr, $($tt:tt)*) => {
        syn::parse2(quote::quote! { $($tt)* }).unwrap_or_else(|_| $fallback)
    };
}

This pattern is applied to all 36 call sites where user expressions are embedded in generated code. The fallback preserves the original expression unchanged, meaning the program compiles correctly even when the tracking wrapper cannot be constructed. In these cases, the specific tracking event is lost, but the program's behavior remains correct. A contains_block_closure() helper function pre-detects these cases to avoid unnecessary parse attempts.

5.7 The pending_inserts Pattern

When an expression cannot be safely wrapped in a block (because rustc rejects blocks as function arguments in certain positions), the macro emits tracking calls as separate statements before or after the expression, using a pending_inserts queue that is flushed during block processing. This is the complementary strategy to safe_parse_quote!: instead of wrapping the expression (which may fail), the tracking call is emitted as an independent statement that executes before or after the original code.

The queue is processed when the visitor exits a block: all pending statements are inserted at their recorded positions, with indices adjusted to account for prior insertions. This ensures that tracking calls appear in the correct execution order relative to the code they instrument. 

// Instead of wrapping (breaks for closures with block bodies):
*expr = parse_quote! { { track_unwrap(...); receiver.method(|| { ... }) } };

// Emit as separate statement (always safe):
let track_stmt = parse_quote! { borrowscope_runtime::track_unwrap(...); };
self.pending_inserts.push((current_stmt_index, track_stmt));
// Expression remains unmodified

This pattern is used for transform_unwrap, transform_try, method call enrichment, and the track_new fallback path when the expression contains macros, closures, or other block-producing constructs. Together with safe_parse_quote!, it ensures that the macro can instrument any valid Rust code without introducing compilation errors, even in the presence of complex expression nesting.

5.8 Mandatory Analyzer

The macro panics at compile time if the analyzer has not been run. There is no heuristic fallback path. This is a deliberate architectural decision: the system guarantees semantic correctness by refusing to operate without semantic data. A "best effort" mode would reintroduce exactly the heuristics we eliminated, creating a false sense of coverage while silently producing incorrect results.

This is enforced with a check in the visitor constructor: 

#[cfg(not(test))]
if type_info::get_type_info().is_none() {
    panic!("
    ╔════════════════════════════════════════════════════════════╗
    ║  ERROR: BorrowScope analyzer output not found              ║
    ║  Please run: cargo run -p borrowscope-analyzer -- .        ║
    ╚════════════════════════════════════════════════════════════╝
    ");
}

The #[cfg(not(test))] gate allows unit tests to run without analyzer data, while ensuring that any real compilation requires the semantic analysis to be present. This separation is necessary because the macro's unit tests verify AST transformation logic in isolation, using mock type information injected directly rather than loaded from a file. The gate ensures that the test infrastructure does not interfere with the production guarantee.
