1. Introduction

1.1 The Proc-Macro Type Blindness Problem

Rust's procedural macros execute during the early stages of compilation, specifically after parsing but before type checking. At this point, the compiler has tokenized the source code into an abstract syntax tree, but has not yet resolved types, inferred generics, or checked trait implementations. A procedural macro receives only raw tokens: it can see that a variable is initialized with Rc::new(RefCell::new(vec![1, 2, 3])), but it cannot determine that the resulting type is Rc<RefCell<Vec<i32>>>, that Rc<T> implements reference counting, or that the inner RefCell<T> provides interior mutability.

This constraint is not a bug. It is an intentional property of Rust's compilation model, designed to maintain determinism and enable parallel macro expansion. But it creates a fundamental problem for any procedural macro that needs to make type-aware decisions. Consider a macro that must distinguish between:

  • let x = Rc::new(value); (reference-counted allocation)
  • let x = create_shared(value); (factory function returning Rc<T>)
  • let x = MyRc::new(value); (type alias for Rc<T>)
  • let x = if cond { Rc::new(a) } else { Arc::new(b) }; (conditional)

The first case can be detected by matching the literal tokens Rc::new. The remaining three are invisible to syntactic analysis. They require type resolution to identify. This gap widens as codebases grow: real-world Rust projects routinely use type aliases, builder patterns, and factory functions that obscure the underlying types from token-level inspection. Without semantic information, a procedural macro is forced to either miss these cases entirely or resort to fragile naming conventions that break silently when code is refactored.

1.2 The Cost of Heuristics

Without type information, procedural macros resort to string-matching heuristics: pattern-matching on method names, path segments, and naming conventions. As documented in the initial BorrowScope whitepaper (March 2026), the #[trace_borrow] macro originally relied on 109 such patterns to classify ownership-related operations, of which 66 (61%) were pure string-based heuristics with no semantic grounding. These heuristics occupied approximately 500 lines of detection code across multiple files.

The fragility of this approach manifests in concrete failure modes:

Ambiguity: The method name write could mean RwLock::write (lock acquisition), io::Write::write (I/O operation), or MaybeUninit::write (unsafe initialization). String matching cannot disambiguate without knowing the receiver type.
False negatives: A factory function fn create_shared(v: T) -> Rc<T> returns an Rc, but the macro sees only the function name and cannot detect the smart pointer allocation.
False positives: A user-defined struct with a method named clone (not implementing the Clone trait) would be incorrectly classified as a clone operation.
Maintenance burden: Every new tracked type requires adding heuristic patterns, testing edge cases, and documenting limitations. The detection code grows linearly with the number of supported types.

1.3 Contributions

This paper presents the design, implementation, and evaluation of the complete BorrowScope system, a three-component pipeline spanning static analysis, compile-time code transformation, and runtime event capture, after successfully eliminating all heuristic pattern matching from the procedural macro. What began as a research question ("can pre-build semantic analysis replace syntactic heuristics in Rust procedural macros?") has been answered definitively: yes, and the resulting system is more accurate, more maintainable, and validated on real-world open-source code. The specific contributions are:

  1. A complete two-phase build system achieving semantic coverage across all 109 ownership-related patterns, with zero string-matching heuristics remaining in the macro. This fulfills the five-phase roadmap outlined in the previous whitepaper, which estimated 19 hours of development effort for full coverage.
  2. An upstream contribution to rust-analyzer (PR #21835) adding is_mutable_raw_ptr() and as_raw_ptr() to hir::Type, closing an API gap discovered during development.
  3. Validation on real-world projects: ripgrep (287 tests pass with instrumented source code), the lru crate (107 ownership events tracked), and the uuid crate (88 events tracked), all requiring zero modifications to the macro or analyzer.
  4. 88 runtime event types covering the Rust ownership model: smart pointers, interior mutability, concurrency primitives, unsafe operations, async/await, control flow, closures, and more.
