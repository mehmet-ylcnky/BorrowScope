4. The Analyzer (borrowscope-analyzer)

4.1 Workspace Loading and Sysroot Discovery

Before any semantic analysis can occur, rust-analyzer must load the project's workspace: parsing Cargo.toml, resolving dependencies, and locating the Rust standard library (sysroot). The sysroot contains pre-compiled metadata for std, core, alloc, and other standard crates. This loading phase is the most time-consuming part of the analysis (30-40 seconds), as it mirrors the same dependency resolution that cargo build performs, plus the additional step of indexing all type definitions for semantic queries.

The workspace loading produces a RootDatabase, which is rust-analyzer's central data structure for semantic queries. This database holds the entire project's type information in a salsa-based incremental computation framework, allowing efficient queries against any symbol in the project or its dependencies.

Critical discovery during development: Without sysroot discovery, types from the standard library resolve to {unknown}. Initial tests showed only 10% type resolution. Enabling RustLibSource::Discover improved resolution to near-100% for standard library types. This single configuration line is the difference between a usable analyzer and one that cannot distinguish Rc<T> from Arc<T>. 
let mut cargo_config = CargoConfig::default();
cargo_config.sysroot = Some(RustLibSource::Discover);  // Critical!

let load_config = LoadCargoConfig {
    load_out_dirs_from_check: true,
    with_proc_macro_server: ProcMacroServerChoice::None,  // Analyze before expansion
    prefill_caches: true,
};

let (db, vfs, _) = load_workspace_at(project_path, &cargo_config, &load_config, &|_| {})?;

Proc-macro expansion is intentionally disabled (ProcMacroServerChoice::None) because we analyze the source before macro expansion. We want the types as they appear in the user's source code, not after transformation by other macros. This also avoids a circular dependency: if BorrowScope's own macro were expanded during analysis, the analyzer would see the instrumented code rather than the original, leading to incorrect type mappings.

4.2 Type Extraction via type_of_pat

The analyzer walks each source file's syntax tree, finding let statements and extracting the pattern (variable name), its resolved type, and source location. The key API is sema.type_of_pat(), which returns the type after all coercions are applied. This distinction is critical: Rust performs implicit coercions at binding sites (reference-to-raw-pointer, deref coercions, unsizing), and the macro needs the final type, not the expression type.

For each variable, the analyzer extracts 81 fields covering type identity, trait implementations, mutability, reference depth, generic parameters, and source location. This comprehensive extraction means the macro never needs to infer or guess any type property. 

// Why type_of_pat, not type_of_expr:
// let ptr: *const i32 = &value;
//   type_of_expr(&value) = &i32        (before coercion)
//   type_of_pat(ptr)      = *const i32  (after coercion) ✓

if let Some(type_info) = sema.type_of_pat(&pat) {
    let ty = type_info.original;
    var_info.ty = ty.display(db, Edition::Edition2021).to_string();
    var_info.is_copy = ty.is_copy(db);
    var_info.is_reference = ty.is_reference();
    var_info.is_mutable_reference = ty.is_mutable_reference();
    // ... 81 fields total
}

4.3 Trait Detection

The analyzer detects 8 trait implementations for each variable using rust-analyzer's impls_trait() API. Traits are looked up via lang items (for compiler-known traits like Copy, Clone, Drop) or via import map search (for Send, which is not a lang item). The distinction matters because lang items have a stable identity in the compiler's internal representation, while non-lang traits must be discovered through the crate's import map.

Knowing whether a type implements Copy determines whether an assignment is a move or a copy. Knowing whether it implements Drop determines whether the macro should emit drop tracking. These are not properties that can be guessed from a type's name. 

// Lang item traits (compiler-known)
let clone_trait = db.lang_item(krate_id, LangItem::Clone)
    .and_then(|li| li.as_trait());
var_info.is_clone = ty.impls_trait(db, clone_trait, &[]);

// Send trait (not a lang item, found via import_map)
let send_trait = find_trait_by_name(db, krate, "Send");
var_info.is_send = ty.impls_trait(db, send_trait, &[]);

4.4 ADT Classification via Canonical Path

Types are classified by resolving their ADT (Abstract Data Type) identity through canonical module paths. This is the mechanism that replaces all string-matching heuristics. A type alias type MyRc<T> = Rc<T> resolves to the same ADT as Rc<T>, so both are correctly classified. Similarly, re-exports (use std::rc::Rc vs use alloc::rc::Rc) resolve to the same canonical path because they refer to the same underlying type definition.

The canonical path is the type's definition location in the crate hierarchy, not its import path. This means that regardless of how a user imports or aliases a type, the analyzer always identifies it by its true origin. This is fundamentally more robust than any string-matching approach. 

if let Some(adt) = ty.as_adt() {
    // Get canonical path: "alloc::rc::Rc", "std::sync::Mutex", etc.
    let path = get_adt_canonical_path(&adt, db);

    // Exact path matching (not string heuristics)
    var_info.is_rc = path == "alloc::rc::Rc";
    var_info.is_arc = path == "alloc::sync::Arc";
    var_info.is_mutex = path == "std::sync::poison::mutex::Mutex";
    var_info.is_refcell = path == "core::cell::RefCell";
    // ... 21 ADT classifications total
}

The analyzer classifies types into 78 distinct initializer categories (from rc_new to atomic_new to user_struct) by combining the ADT identity with the expression kind (constructor call, clone, method result, etc.).

4.4.1 Enum Variant Resolution (v3.0)

ADT classification alone is insufficient for enum types where different variants require different tracking calls. For example, Cow::Borrowed("hello") and Cow::Owned(String::from("hello")) both have type Cow<'_, str>, but the first should emit track_cow_borrowed while the second should emit track_cow_owned. Prior to v3.0, both were classified as "cow_new" and the macro could not distinguish them without string matching on the constructor path.

Version 3.0 resolves this by using sema.resolve_path() on the constructor expression's path. When the path resolves to PathResolution::Def(ModuleDef::Variant(variant)), the analyzer extracts the variant name and its parent enum's ADT classification, producing a combined tag like "cow_borrowed" or "cow_owned". 

// Resolve enum variant construction semantically
if let ast::Expr::CallExpr(call) = expr {
    if let Some(ast::Expr::PathExpr(path_expr)) = call.expr() {
        if let Some(path) = path_expr.path() {
            if let Some(resolved) = sema.resolve_path(&path) {
                if let PathResolution::Def(ModuleDef::Variant(variant)) = resolved {
                    let variant_name = variant.name(db);
                    let parent_enum = variant.parent_enum(db);
                    if let Some(classification) = known_types.classify(
                        &Adt::Enum(parent_enum), db
                    ) {
                        // Produces: "cow_borrowed", "cow_owned", "option_some", etc.
                        return format!("{}_{}", classification, variant_name.to_lowercase());
                    }
                }
            }
        }
    }
}

This resolution runs before the ADT-based classification, ensuring that variant-specific tags take priority over generic type tags. The approach is fully semantic: it uses the compiler's own path resolution to identify which variant is being constructed, regardless of how the user imports or aliases the enum.

4.4.2 Sync vs Rc Weak Distinction

A similar ambiguity exists for Weak references: Rc::downgrade(&rc) produces std::rc::Weak<T> while Arc::downgrade(&arc) produces std::sync::Weak<T>. Both display as Weak<T> in type output, but require different tracking calls (track_weak_new vs track_weak_new_sync). The analyzer resolves this by comparing the ADT identity against both weak_rc and weak_arc known types, setting a dedicated is_sync_weak field when the type matches std::sync::Weak.

4.5 Method Call Analysis

For each tracked variable, the analyzer records all method calls made on it. This is the key capability that eliminates the 47 self-borrow heuristics and 18 semantic dispatch patterns from the macro. The analyzer resolves each method call to its actual function definition, extracting the self parameter's access mode directly from the function signature rather than guessing from the method name.

This resolution handles complex cases that no heuristic can: a method named write could take &self (on io::Write), &mut self (on RwLock), or self (on MaybeUninit). Only by resolving to the actual definition can the correct borrow type be determined. 

fn analyze_method_calls(sema: &Semantics, method_call: &MethodCallExpr, db: &RootDatabase) {
    // Resolve to the actual function definition
    let func = sema.resolve_method_call(method_call)?;

    // Build canonical path: "core::cell::set", "std::sync::mpsc::send"
    let operation = get_function_path(&func, db);

    // Determine self-borrow type from the method signature
    let self_borrow = match func.self_param(db)?.access(db) {
        Access::Shared => "immutable",
        Access::Exclusive => "mutable",
        Access::Owned => "consuming",
    };

    // Detect trait methods (e.g., Clone::clone vs inherent .clone())
    let is_trait_method = func.as_assoc_item(db)
        .and_then(|item| item.containing_trait(db))
        .is_some();
}

The resulting MethodCallInfo contains 10 fields: method, line, column, operation (canonical path), self_borrow, receiver_type, result_type, is_trait_method, trait_name, and is_unsafe.

4.6 Standalone Expression Tracking

Some ownership-relevant operations do not create variables or call methods on tracked variables. Functions like thread::spawn, mem::transmute, and mem::drop are tracked via FunctionId comparison, not string matching. The analyzer resolves these functions once at startup and stores their unique identifiers. During the analysis pass, each call expression is compared against these known IDs.

This approach is immune to shadowing and aliasing. A user could write let transmute = some_other_fn; and call it as transmute(x), and the analyzer would correctly identify it as not being mem::transmute because the FunctionId differs. String matching would incorrectly flag this as a transmute operation. 

// TrackedFunctions: resolved once at startup via FunctionId
let tracked = TrackedFunctions::resolve(db, krate);

// For each call expression, compare FunctionId (not strings)
if let Some(func) = sema.resolve_path(&call_path) {
    if func == tracked.thread_spawn {
        expressions.push(ExpressionInfo { operation: "thread_spawn", .. });
    } else if func == tracked.transmute {
        expressions.push(ExpressionInfo { operation: "transmute", .. });
    }
}

4.8 Upstream Contribution: Raw Pointer Mutability API

During development, we discovered that hir::Type provided is_raw_ptr() to check if a type is a raw pointer, but no way to distinguish *mut T from *const T. This was asymmetric with references, where both is_mutable_reference() and as_reference() exist. The only workaround was parsing the display string, which is exactly the kind of heuristic this project aims to eliminate: 

// Before PR #21835: string parsing heuristic (exactly what we're eliminating)
let is_mut = ty.is_raw_ptr() && ty.display(db).to_string().starts_with("*mut ");

We contributed the fix upstream as rust-analyzer PR #21835 (merged April 2026), adding two methods: 

// After PR #21835: semantic API (no string parsing)
pub fn is_mutable_raw_ptr(&self) -> bool {
    matches!(self.ty.kind(), TyKind::RawPtr(.., Mutability::Mut))
}

pub fn as_raw_ptr(&self) -> Option<(Type, Mutability)> {
    let TyKind::RawPtr(ty, m) = self.ty.kind() else { return None };
    Some((self.derived(ty), Mutability::from_mutable(matches!(m, Mutability::Mut))))
}

This contribution demonstrates that building tools on rust-analyzer's ra_ap_* crates can identify API gaps and drive improvements to the platform, benefiting all downstream consumers. The PR was reviewed and merged by ChayimFriedman2, one of rust-analyzer's core maintainers, within a week of submission. It closes a long-standing asymmetry in the hir::Type API that affected any tool needing to reason about raw pointer mutability.
