8. Limitations and Future Work

8.1 Current Limitations

Six edge-case patterns remain where the macro cannot correctly instrument code. These functions have #[trace_borrow] removed in the examples. Each limitation stems from a fundamental tension between AST transformation and Rust's type system: the macro modifies syntax, but certain syntactic modifications change the semantics in ways that the type checker rejects.

It is important to note that these are instrumentation limitations, not analysis limitations. The analyzer correctly identifies types and method calls in all these patterns. The issue is that the macro's code transformation strategy (wrapping expressions in tracking calls) interacts poorly with specific Rust language features.

Pattern Root Cause
Nested async functions The fn_enter/fn_exit wrapping changes the return type of nested async fn from the declared type to ()
Nested functions with format! Macro expansion inside nested function bodies produces blocks that conflict with outer wrapping
Complex unsafe blocks (partially resolved in v3.0) v3.0: syn::parse2 fallback restores original block on parse failure. Some inner transformations may be skipped.
MaybeUninit assume_init_drop (resolved in v3.0) v3.0: Skipped gracefully — MaybeUninit creation is still tracked.
Closure-returning functions Nested fn with impl Fn return type conflicts with visitor traversal
Mutable borrow patterns track_new wrapping can change borrow semantics for &mut bindings in specific contexts

These represent less than 3% of the patterns encountered in the battle tests and do not affect the semantic coverage of the 109 ownership patterns. In practice, developers can simply remove the #[trace_borrow] attribute from the affected functions while keeping instrumentation on the rest of the codebase.

8.2 The parse_quote! vs rustc Parsing Divergence

A fundamental challenge: syn::parse_quote! and syn::parse2 accept token streams that rustc subsequently rejects. Specifically, block expressions ({ ... }) inside function call arguments are parsed differently by syn and rustc. This is not a bug in either parser; it reflects a genuine ambiguity in Rust's grammar that the two parsers resolve differently.

This manifests when:

  • A closure with a block body (|| { ... }) appears as a function argument
  • A macro like vec![] expands to a block inside a function argument
  • A previous transform wraps an expression in a block, and a later transform embeds that block as an argument

The safe_parse_quote! and pending_inserts patterns (Sections 5.6 and 5.7) mitigate this, but the underlying divergence between syn and rustc remains a source of complexity. A complete solution would require either syn to match rustc's parsing behavior exactly (which the syn maintainers have explicitly declined to guarantee), or a fundamentally different code generation strategy that avoids embedding blocks inside arguments entirely.

8.3 Stale Data Risk

If source code changes between running the analyzer and compiling, the JSON file becomes inconsistent. The macro handles this gracefully: variables not found in the lookup are tracked with generic track_new calls, and method calls without analyzer data use a safe default (Immutable borrow). However, tracking precision degrades silently without an explicit error.

This is a deliberate trade-off. The alternative (failing compilation when any variable is missing from the JSON) would force developers to re-run the analyzer after every edit, which contradicts the design goal of infrequent analysis runs. The current approach ensures that the program always compiles and runs correctly; only the tracking metadata may be incomplete. A future improvement could emit compile-time warnings (rather than errors) for unresolved variables, alerting developers that re-analysis would improve tracking precision.

8.4 Future Work

Several directions extend the current system toward a complete ownership visualization and debugging platform:

  • borrowscope-graph: Graph algorithms for ownership analysis. Build ownership graphs from event streams, detect reference cycles, compute borrow lifetimes, and identify ownership hotspots. This would transform the flat event stream into a queryable data structure that answers questions like "which variables hold references to this allocation?" or "what is the longest borrow chain in this function?"
  • borrowscope-ui: Interactive web visualization. Timeline view of ownership events, ownership graph rendering, borrow scope highlighting, and drill-down into specific variables. The event stream's JSON format is already designed for consumption by web frontends.
  • IDE integration: Direct integration with rust-analyzer's LSP could eliminate the separate analysis step entirely, providing real-time type information to the macro without a JSON intermediary. This would solve the stale data problem completely, as the type information would always reflect the current source code.
  • Incremental analysis: Caching the rust-analyzer database between runs would reduce the 30-40 second workspace loading cost to near-zero for subsequent analyses. The salsa framework that rust-analyzer uses already supports incremental computation; exposing this through the ra_ap_* API would make re-analysis nearly instantaneous.
  • Fix remaining edge cases: The 6 patterns in Section 8.1 require refactoring the macro's visitor to avoid modifying expressions inside nested function bodies and to handle &mut bindings without changing borrow semantics. A potential approach is to use the pending_inserts pattern more broadly, emitting tracking as separate statements rather than expression wrappers.

8.3 The Name Collision Problem (v3.0)

During comprehensive testing, a critical bug was discovered in the macro's variable lookup strategy. The v2.0 system used a two-tier lookup: first by (function_name, var_name, decl_index), then falling back to a global by_name index. The fallback was intended to handle cases where the function-scoped lookup failed (e.g., when the analyzer didn't process a particular function).

The bug: when a variable named p appeared in function test_fn (creating a Point struct) and the by_name index contained a different p from function rc_test_13 (with is_rc = true), the macro would incorrectly wrap the Point construction with track_rc_new, causing a type mismatch compile error.

Root cause: The by_name index is inherently unsafe for cross-function lookup because common variable names (x, data, result, p) appear in many functions with different types.

Fix: Remove the by_name fallback entirely. If function-scoped lookup returns None, the macro uses default (non-semantic) transformation. This is correct: if the analyzer didn't see the variable, the macro cannot make semantic decisions about it and should not guess.

Lesson learned: Global name-based indexes are fundamentally incompatible with function-scoped semantic analysis. The type-info schema retains the by_name index for backward compatibility, but the macro no longer uses it.
