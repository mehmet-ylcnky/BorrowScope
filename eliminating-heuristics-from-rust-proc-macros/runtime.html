6. The Runtime (borrowscope-runtime)

6.1 Event Architecture

The runtime defines 88 distinct event types organized into 14 categories. Each event captures a specific ownership operation with all relevant metadata (timestamps, variable IDs, type names, locations). The event taxonomy mirrors Rust's ownership model: every way that ownership can be created, transferred, shared, or destroyed has a corresponding event type.

This granularity is intentional. A coarser event model (e.g., just "borrow" and "move") would lose the distinction between an Rc::clone (cheap reference count increment) and a Clone::clone (potentially expensive deep copy). Similarly, distinguishing RefCellBorrow from a regular immutable borrow captures the runtime borrow-checking semantics that RefCell introduces. Each event type carries exactly the metadata needed for its category, avoiding both information loss and unnecessary overhead.

6.2 Pass-Through Design

Every tracking function follows the same principle: accept a value, record an event, return the value unchanged. This makes instrumentation transparent to program behavior. The function signature is designed so that the macro can wrap any expression E as track_*(metadata, E) without changing the expression's type or value. The Rust compiler sees the same types before and after instrumentation, so type inference, borrow checking, and lifetime analysis are unaffected.

This design also means that tracking functions can be composed: if a variable is created via Rc::new(value), the macro wraps it as track_rc_new_with_id(id, name, type_name, loc, Rc::new(value)). The inner Rc::new executes first, producing an Rc<T>, which is then passed through the tracking function and returned unchanged. The program's observable behavior is identical with or without instrumentation. 

pub fn track_rc_new_with_id<T>(
    var_id: usize,
    name: &str,
    type_name: &str,
    location: &str,
    value: Rc<T>,
) -> Rc<T> {
    #[cfg(feature = "track")]
    {
        let mut tracker = TRACKER.lock();
        tracker.record_rc_new(var_id, name, type_name, location,
            Rc::strong_count(&value), Rc::weak_count(&value));
    }
    value  // Pass-through: tracking is invisible to the program
}

The #[cfg(feature = "track")] gate means that when the track feature is disabled, all tracking functions compile to no-ops that simply return their input. This enables zero-cost builds for production. The compiler's optimizer completely eliminates the function call, leaving only the original expression. This two-mode design allows developers to keep #[trace_borrow] annotations in their source code permanently, enabling tracking on demand without code changes.

6.3 Global Tracker

Events are accumulated in a thread-safe global tracker using parking_lot::Mutex for efficient locking and AtomicU64 for lock-free monotonic timestamp generation. The choice of parking_lot over std::sync::Mutex is deliberate: it provides faster lock acquisition (no poisoning overhead), smaller memory footprint, and does not require unwrap() on every lock call.

The timestamp counter is separate from the mutex to minimize contention. Even when multiple threads record events simultaneously, the atomic increment ensures a globally consistent ordering without requiring the mutex to be held during timestamp generation. This means the event stream always reflects the true temporal order of ownership operations, even in highly concurrent programs. 

static TRACKER: Lazy<Mutex<Tracker>> = Lazy::new(|| Mutex::new(Tracker::new()));
static TIMESTAMP: AtomicU64 = AtomicU64::new(0);

impl Tracker {
    fn next_timestamp() -> u64 {
        TIMESTAMP.fetch_add(1, Ordering::SeqCst)
    }

    pub fn record_rc_new(&mut self, ...) {
        self.events.push(Event::RcNew {
            timestamp: Self::next_timestamp(),
            var_id, var_name, type_name, location,
            strong_count, weak_count,
        });
    }
}

// Public API
pub fn reset() { TRACKER.lock().clear(); }
pub fn get_events() -> Vec<Event> { TRACKER.lock().events.clone() }
pub fn print_summary() { TRACKER.lock().print_summary(); }

6.4 Enriched Events

Several event types carry metadata from the static analysis phase, providing richer information than would be available from runtime observation alone. These fields are populated by the macro using analyzer data and are backward-compatible via #[serde(default, skip_serializing_if)]. This design means that older event consumers can ignore the new fields, while newer tools can leverage the additional context for deeper analysis.

The enrichment pattern bridges the gap between static and dynamic analysis. The analyzer knows what is possible (which variables could be live at an await point), while the runtime knows what actually happened (the await was reached during execution). By combining both, the event stream provides a complete picture that neither analysis could produce alone.

For example, an AwaitStart event not only records that an await point was reached, but also which variables are live across that suspension point, information that is only available through static analysis. This is particularly valuable for diagnosing async lifetime issues: if a future holds a reference across an await, the event stream shows exactly which variables are involved, enabling precise diagnosis of "future is not Send" errors.

6.5 Event Serialization

All events implement Serialize and Deserialize via serde, enabling JSON export for external visualization tools. The serialization format uses tagged enums, where each event variant includes its type name as a discriminator field. This makes the JSON output self-describing: a consumer can process events without knowing the full schema in advance.

The public API is intentionally minimal: reset() clears the event buffer for a fresh trace, get_events() returns a snapshot of all captured events, and print_summary() outputs a human-readable overview. This simplicity makes integration straightforward, whether the consumer is a test assertion, a CLI tool, or a web-based visualization frontend. 

use borrowscope_runtime::*;

fn main() {
    reset();
    my_instrumented_function();

    // Get all captured events
    let events = get_events();
    println!("Captured {} events", events.len());

    // Export to JSON
    let json = serde_json::to_string_pretty(&events).unwrap();
    std::fs::write("ownership_trace.json", json).unwrap();

    // Print human-readable summary
    print_summary();
    // Output: Variables: 12 created, 8 dropped
    //         Borrows: 3 immutable, 1 mutable
}
