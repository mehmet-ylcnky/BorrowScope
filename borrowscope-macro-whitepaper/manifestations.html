5. Concrete Manifestations of the Problem

The type information barrier manifests in specific, concrete ways when building instrumentation tools. This section examines four categories of patterns that BorrowScope’s macro cannot reliably detect, demonstrating with code examples how syntactically identical constructs carry fundamentally different semantic meanings.

5.1 FFI Function Detection

Foreign Function Interface calls represent one of Rust’s most significant safety boundaries. When Rust code calls a function declared in an extern block, it crosses into territory where Rust’s safety guarantees no longer apply. The foreign function might dereference invalid pointers, cause data races, or exhibit undefined behavior that Rust’s type system cannot prevent. For BorrowScope, tracking these boundary crossings is valuable: they represent moments where ownership and borrowing semantics become the programmer’s responsibility rather than the compiler’s enforcement.

The challenge is that FFI calls look exactly like regular function calls at the syntactic level:

extern "C" {
    fn external_func(ptr: *mut i32);
}

fn regular_func(ptr: *mut i32) {
    // Safe Rust implementation
}

fn process(ptr: *mut i32) {
    external_func(ptr);  // FFI call - crosses safety boundary
    regular_func(ptr);   // Regular call - stays within Rust's guarantees
}
parenthesized arguments. The token sequence for external_func(ptr) is indistinguishable from regular_func(ptr). A procedural macro examining the process function sees two call expressions with the same structure. Nothing in the tokens indicates that external_func was declared in an extern "C" block while regular_func was defined as a normal Rust function.

To distinguish these cases, the macro would need to resolve the identifier external_func to its declaration, examine that declaration’s context, and determine whether it carries foreign linkage. This requires name resolution—knowing which definition each identifier refers to—and access to the declaration site’s attributes. Both are unavailable during macro expansion.

The situation becomes more complex with real-world patterns. FFI functions might be re-exported through wrapper modules, aliased with use statements, or called through function pointers. A function pointer of type extern "C" fn(...) carries its foreign calling convention in its type, but the macro cannot see types. The macro might attempt heuristics—perhaps functions with certain naming patterns or in certain modules are likely FFI—but such heuristics are unreliable and will produce both false positives and false negatives.

For BorrowScope, this means track_ffi_call cannot be automatically inserted. Users who want FFI boundary tracking must either manually instrument their code or provide explicit annotations indicating which functions are foreign.

5.2 Union Field Access

Unions in Rust provide a mechanism for reinterpreting memory, allowing the same bytes to be viewed as different types depending on which field is accessed. Unlike structs, where each field occupies distinct memory, union fields overlap completely. Reading a union field interprets the raw bits according to that field’s type, regardless of which field was most recently written. This operation is inherently unsafe—the programmer must ensure that the bits constitute a valid value for the accessed type—and represents a point where Rust’s type safety relies on programmer discipline rather than compiler enforcement.

For ownership tracking, union field access deserves distinct treatment. When code reads u.int_val from a union, it is not accessing a value that was stored as an i32; it is reinterpreting whatever bits happen to be in the union’s memory as an i32. This differs fundamentally from struct field access, where s.x retrieves a value that was stored as the field’s declared type. BorrowScope’s track_union_field_access function exists to capture these reinterpretation events, but the macro cannot determine when to call it.

The syntactic problem is stark:

union MyUnion {
    int_val: i32,
    float_val: f32,
}

struct MyStruct {
    x: i32,
    y: i32,
}

fn access(u: MyUnion, s: MyStruct) {
    let a = u.int_val;   // Union field access - reinterprets bits
    let b = s.x;         // Struct field access - retrieves stored value
}

Both u.int_val and s.x parse to the same syntactic form: a field access expression with a base and a field identifier. The tokens are structurally identical. Nothing in the syntax distinguishes a union field access from a struct field access; the distinction exists only in the types involved.

Determining whether a field access targets a union requires knowing the type of the base expression. If u has type MyUnion, and MyUnion is declared as a union, then u.int_val is a union field access. If s has type MyStruct, and MyStruct is declared as a struct, then s.x is a struct field access. Both pieces of information—the type of the expression and the nature of that type’s declaration—require semantic analysis that occurs after macro expansion.

The macro might attempt to track variable declarations and remember that u was declared with type MyUnion. But this approach fails in numerous scenarios: when the union value comes from a function return, when it is accessed through a reference, when the type is aliased, when the variable is a field of another struct, or when generic code operates on union types. The syntactic context simply does not contain enough information to reliably identify union field access.

5.3 Static Variable Access

Static variables occupy a unique position in Rust’s memory model. Unlike local variables that live on the stack and are created and destroyed with each function invocation, statics persist for the entire duration of the program. They have a fixed memory address, can be accessed from any point in the code, and—when declared as static mut—introduce the possibility of data races that Rust’s ownership system normally prevents. Even immutable statics, when they contain interior mutability through types like AtomicU32 or Mutex<T>, represent shared global state that multiple threads might access concurrently.

Tracking static variable access provides valuable insight into a program’s use of global state. For debugging and analysis, knowing when code reads from or writes to statics helps identify potential sources of unexpected behavior, thread-safety issues, or hidden dependencies between distant parts of a codebase. BorrowScope’s runtime includes track_static_access and track_static_init functions for this purpose, but the macro cannot reliably determine when an identifier refers to a static.

The syntactic indistinguishability is complete:

use std::sync::atomic::{AtomicU32, Ordering};

static COUNTER: AtomicU32 = AtomicU32::new(0);

fn increment() {
    let local_counter = AtomicU32::new(0);
    
    COUNTER.fetch_add(1, Ordering::SeqCst);       // Static variable access
    local_counter.fetch_add(1, Ordering::SeqCst); // Local variable access
}
local_counter.fetch_add(1, Ordering::SeqCst) have identical structure: an identifier, a dot, a method name, and arguments. The macro cannot distinguish them without knowing that COUNTER was declared with the static keyword while local_counter was declared with let.

One might suggest using naming conventions as a heuristic. Rust convention recommends SCREAMING_SNAKE_CASE for statics and constants, while local variables use snake_case. A macro could check whether an identifier is all uppercase and assume it refers to a static. However, this heuristic is unreliable in both directions. Programmers might use uppercase names for local variables in certain contexts, and statics imported from external crates might be renamed with use ... as to follow different conventions. Constants declared with const also use uppercase naming but have different semantics than statics. A heuristic based on naming would produce both false positives and false negatives, undermining the accuracy that instrumentation tools require.

The fundamental issue remains: determining whether an identifier refers to a static requires resolving that identifier to its declaration and examining whether that declaration uses the static keyword. This is name resolution, unavailable during macro expansion.

5.4 Type-Dependent Method Behavior

Some method names carry fundamentally different semantics depending on the type they are called on. The clone method provides the clearest example: calling .clone() on an Rc<T> increments a reference count and returns a new handle to the same allocation; calling .clone() on an Arc<T> performs an atomic increment suitable for concurrent access; calling .clone() on a Vec<T> allocates new memory and copies all elements. These operations have vastly different performance characteristics and ownership implications, yet they share identical syntax.

For BorrowScope, distinguishing these cases enables more informative tracking. An Rc::clone represents the creation of a new shared owner, incrementing the strong count. An Arc::clone represents the same semantic operation but with thread-safe atomics. A regular clone might perform deep copying, shallow copying, or something else entirely depending on the type’s Clone implementation. Emitting track_rc_clone versus track_arc_clone versus track_clone provides users with precise information about what kind of operation occurred.

The syntactic uniformity defeats pattern matching:

use std::rc::Rc;
use std::sync::Arc;

fn example<T: Clone>(rc: Rc<i32>, arc: Arc<i32>, vec: Vec<i32>, generic: T) {
    let a = rc.clone();      // Rc clone - reference count increment
    let b = arc.clone();     // Arc clone - atomic reference count increment
    let c = vec.clone();     // Vec clone - deep copy of elements
    let d = generic.clone(); // Unknown - depends on what T is
}
four method calls to clone and cannot distinguish them. Determining the appropriate tracking call requires knowing the type of each receiver expression: Rc<i32>, Arc<i32>, Vec<i32>, and T respectively.

BorrowScope’s macro employs a partial workaround for this specific case. When it sees a variable initialized with Rc::new(...), it records that variable as holding an Rc. When that variable later appears as the receiver of a .clone() call, the macro can emit track_rc_clone. This syntactic tracking works for simple cases but fails when the Rc comes from a function return, is stored in a struct field, passes through a generic function, or is accessed through a reference. The macro’s knowledge is limited to what it can observe syntactically within the function body.

Generic code presents the most challenging case. When the receiver has a generic type T, the macro cannot know what concrete type will be substituted at each call site. The same generic function might be instantiated with Rc<String>, Arc<Vec<u8>>, and HashMap<K, V> in different parts of the program. Each instantiation should ideally receive different tracking, but the macro transforms the generic function once, before any instantiation occurs. It must emit code that works for all possible type substitutions, which means it cannot emit type-specific tracking calls.

5.5 Summary: The Pattern

A common theme emerges from these examples: constructs that are syntactically identical carry semantically different meanings, and distinguishing them requires type information that procedural macros cannot access. The macro sees tokens arranged in patterns; it needs to know what those tokens represent in the program’s semantic model.

What We See (Syntax)What We Need (Type)Why It Matters
func(args)Is func extern?FFI boundary track
expr.fieldIs expr a union?Unsafe reinterpret
IDENTIs IDENT static?Global state track
expr.clone()Type of expr?Rc vs Arc vs Copy

In each case, the syntactic form provides no distinguishing information. A function call is a function call; a field access is a field access; an identifier is an identifier; a method call is a method call. The semantic distinctions—foreign versus native, union versus struct, static versus local, reference-counted versus deep-copied—exist only in the type system, accessible only after type checking completes.

This is not a limitation that clever macro engineering can overcome. No amount of sophisticated pattern matching, context tracking, or heuristic analysis within a procedural macro will reliably solve these problems. The information simply does not exist at macro expansion time. The tokens have been parsed, but their meaning has not been determined. The macro operates in a pre-semantic world where syntax is all that exists.

Recognizing this boundary is essential for tooling authors. Attempting to solve these problems within the procedural macro model leads to fragile heuristics, incomplete coverage, and subtle bugs. The correct response is to acknowledge the limitation and either accept reduced functionality, require user annotations to supply the missing information, or adopt an entirely different architectural approach that operates after type checking.
