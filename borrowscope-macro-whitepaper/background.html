2. Background: The BorrowScope Project

2.1 Project Overview

BorrowScope is a runtime tracking library that makes Rust’s ownership and borrowing system observable during program execution. Rust’s memory safety guarantees stem from its borrow checker, a compile-time analysis that enforces strict rules about how references and ownership flow through a program. While this system prevents entire categories of bugs—use-after-free, data races, dangling pointers—it operates invisibly. Developers see only the borrow checker’s error messages when rules are violated, never the successful ownership transfers and borrows that occur in working code. BorrowScope bridges this visibility gap by capturing these events as they happen at runtime, producing structured data that can be exported, visualized, or analyzed.

The project consists of two primary components. The first, borrowscope-runtime, provides a comprehensive set of tracking functions that record ownership events. These functions cover the full spectrum of Rust’s memory model: basic ownership operations like variable creation, moves, and drops; borrowing operations for both shared and mutable references; smart pointer operations for Rc, Arc, Box, and Weak; interior mutability patterns with RefCell, Cell, Mutex, and RwLock; and advanced scenarios including raw pointer manipulation, unsafe blocks, and asynchronous boundaries. Each tracking function records an event with contextual information—variable names, source locations, timestamps—that together form a complete trace of ownership flow through the program.

The second component, borrowscope-macro, provides automatic instrumentation through the #[trace_borrow] procedural macro. Rather than requiring developers to manually insert tracking calls throughout their code, this macro transforms annotated functions to inject the appropriate tracking automatically. When a developer writes a function and applies #[trace_borrow], the macro analyzes the function body, identifies ownership-relevant operations, and wraps them with corresponding tracking calls. The result is instrumented code that behaves identically to the original but produces a detailed event stream capturing every ownership transfer, borrow, and drop.

The motivation behind BorrowScope addresses a persistent challenge in the Rust ecosystem: the ownership system’s learning curve. Newcomers to Rust often struggle to build mental models of how ownership flows through their programs, particularly in complex scenarios involving smart pointers, interior mutability, or async code. Even experienced developers sometimes need to debug subtle ownership issues in production systems. By making the invisible visible, BorrowScope serves as both an educational tool for learners and a diagnostic tool for practitioners. The event data it produces can be exported to JSON for analysis, fed into visualization tools to render ownership graphs, or simply printed to understand what code is actually doing at runtime.

2.2 The Role of borrowscope-macro

The borrowscope-macro crate exists to eliminate the friction of manual instrumentation. Without it, using BorrowScope would require developers to wrap every ownership operation with explicit tracking calls—a tedious and error-prone process that would discourage adoption and clutter code with instrumentation noise. The macro transforms this burden into a single annotation: apply #[trace_borrow] to a function, and the macro handles the rest.

The transformation process operates through syntactic pattern matching. When the macro receives a function’s token stream, it parses it into an abstract syntax tree using the syn crate, then walks this tree looking for patterns that correspond to ownership events. A let binding with a clone() call on the right-hand side suggests a clone operation. A method call to .borrow() or .borrow_mut() indicates RefCell access. An expression wrapped in Rc::new() or Arc::new() signals smart pointer creation. For each recognized pattern, the macro wraps the expression with the appropriate tracking call from borrowscope-runtime, preserving the original semantics while adding observability.

This approach has proven remarkably successful for the majority of ownership patterns. The macro currently detects and instruments approximately 35 different event types spanning the full range of common Rust idioms. Basic ownership tracking covers variable creation, moves between bindings, and scope-based drops. Smart pointer support includes Rc and Arc creation and cloning, Box operations, and Weak reference handling including upgrades and failed upgrades. Interior mutability tracking captures RefCell borrows, Cell get and set operations, and mutex and read-write lock acquisitions. Recent development has extended coverage to include Cow::to_mut for copy-on-write semantics, channel send and receive operations for concurrency patterns, thread join handle tracking, and closure creation with captured variable detection.

The implementation represents a significant engineering effort. The macro maintains context as it traverses function bodies, tracking which variables hold which types of values based on their initialization patterns. When it sees let rc = Rc::new(value), it records that rc is an Rc-typed variable; when it later encounters rc.clone(), it can emit track_rc_clone rather than a generic clone tracker. This propagation of type knowledge through syntactic analysis enables surprisingly accurate instrumentation for patterns that follow conventional Rust idioms.

Yet despite this success, a gap remains. The borrowscope-runtime library provides tracking functions that the macro cannot automatically invoke because detecting when to use them requires information beyond syntax. Functions like track_ffi_call, track_union_field_access, track_static_access, and track_static_init exist in the runtime, ready to record these important events, but the macro has no reliable way to determine when code is calling an FFI function, accessing a union field, or reading from a static variable. These patterns look syntactically identical to their non-special counterparts, and distinguishing them requires knowing the types and definitions involved—information that procedural macros fundamentally cannot access.

2.3 The Instrumentation Gap

The borrowscope-runtime library was designed with comprehensive coverage in mind. Its API includes tracking functions for scenarios that represent important boundaries in Rust’s safety model: track_ffi_call records when code crosses the foreign function interface boundary into C or other languages; track_union_field_access captures the inherently unsafe operation of reading from a union where type interpretation depends on programmer discipline rather than compiler enforcement; track_static_access and track_static_init monitor interactions with global state that persists across function calls and potentially across threads. These events matter because they represent points where Rust’s usual guarantees weaken or require additional programmer care.

The macro, however, cannot reliably detect any of these patterns. Consider a function call expression like process_data(buffer). From the macro’s perspective, this is simply an identifier followed by parenthesized arguments—syntactically indistinguishable from any other function call. Whether process_data was declared in an extern "C" block, making it an FFI call into foreign code, or defined as a normal Rust function cannot be determined from the call site’s syntax alone. The macro would need to resolve the identifier to its definition, examine that definition’s context, and determine whether it carries foreign linkage. This requires name resolution and access to the module structure—capabilities that exist only after macro expansion completes.

The same problem manifests with union field access. When the macro encounters data.value, it sees a field access expression: some base expression, a dot, and a field name. Whether data is a struct, where field access is safe and well-defined, or a union, where field access reinterprets raw bits according to the accessed field’s type, depends entirely on the type of data. The syntax provides no indication. A struct field access and a union field access are lexically identical, differentiated only by the semantic category of the base expression’s type.

Static variable access presents a similar challenge. An expression like COUNTER.fetch_add(1, Ordering::SeqCst) looks exactly like a method call on any other value. Whether COUNTER refers to a static variable with global lifetime and potential thread-safety implications, or a local variable that happens to use uppercase naming, cannot be determined syntactically. The macro sees an identifier; it cannot query whether that identifier was declared with the static keyword in some other part of the codebase.

This creates what we term the “instrumentation gap”—a divergence between the runtime library’s capabilities and the macro’s ability to leverage them. Quantitatively, approximately six categories of tracking events fall into this gap: FFI function calls, union field access, static variable reads, static variable initialization, type-dependent clone behavior (distinguishing Rc::clone from Arc::clone from regular Clone), and transmute operations where the source and destination types matter. Together, these represent a meaningful subset of the ownership events that BorrowScope aims to capture, particularly for code that interacts with unsafe boundaries or global state. The gap is not merely an inconvenience; it represents a fundamental architectural mismatch between what the macro can observe and what the runtime can record.
