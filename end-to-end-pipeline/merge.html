7. The Merge: Combining Both Worlds

The merge is where the two tracks converge. After the pipeline command completes (runtime events are available) and the LSP is active (static analysis is ready), the VS Code extension has both data sources simultaneously. The merge algorithm correlates them, produces a unified view per variable, and detects divergences where predictions disagree with observations. This section describes how the merge fits into the pipeline, what divergences mean in the E2E context, and how the type-info.json enables enhanced memory visualization.

7.1 Automatic Merge After Pipeline Completion

The merge triggers automatically without developer intervention. When the pipeline command writes .borrowscope/events.json, the VS Code extension's RuntimeWatcher (a file system watcher) detects the change and fires an onEventsUpdated event. The extension then: (1) parses the events, (2) filters to the active file, (3) requests the LSP's ownership graph for context, (4) runs mergeViews() to correlate runtime events with static variables, (5) runs divergence detection on each merged variable, and (6) applies runtime decorations to the editor.

This automatic chain means the developer experience is seamless: click the status bar button, wait for the progress notification to show "Done! N events", and the editor immediately shows the merged visualization. No additional action is needed. The runtime overlay (green timing annotations, drop order badges, divergence highlights) appears on top of the existing static decorations (inlay hints, lifelines, conflict highlights), creating a layered visualization where both perspectives are visible simultaneously.

7.2 Divergence Detection in the Pipeline Context

Divergence detection is especially reliable when triggered by the pipeline command rather than manually loaded events. The pipeline guarantees three properties that reduce false positives: (1) fresh type-info: the analyzer ran immediately before compilation, so the macro's instrumentation decisions are correct for the current code, (2) matching code versions: the events were generated from the exact same source that the LSP is analyzing (no stale events from a previous version), and (3) complete instrumentation: the track feature was enabled, so all annotated functions produce events (no missing data due to disabled features).

These guarantees mean that any divergence detected after a pipeline run is highly likely to be a genuine issue rather than an artifact of stale data or partial instrumentation. An rc_leak divergence after a pipeline run means the Rc truly leaked in this execution. A conditional_move divergence means the branch genuinely was not taken. The developer can trust the findings because the pipeline ensures that both data sources are synchronized with the current code.

When events are loaded manually (from a previous run or a different code version), the merge still operates but with lower confidence. The extension detects version mismatches by comparing the event count with the number of static variables: if the overlap is low (many "runtime_only" and "static_only" entries), it shows a warning that the events may be stale. The pipeline command eliminates this concern entirely by always producing fresh events from the current code.

7.3 Enhanced Memory Visualization

The full pipeline enables a richer memory visualization than either track alone can provide. The LSP provides static memory layout: field offsets, sizes, alignments, and heap allocation categories (based on type analysis). The runtime provides observed behavior: which allocations were made, how large they grew, and in what order they were freed. The type-info.json adds a third dimension: the initializer_kind field tells the visualization exactly what kind of allocation each variable represents.

With all three sources active, the Memory view in the VS Code panel shows:

  • From LSP (static): Stack frame with byte offsets, field-level decomposition (String: ptr/len/cap at offsets 0/8/16), pointer relationship arrows from stack to heap.
  • From runtime (dynamic): Actual variable lifetimes (when each stack slot is occupied), drop order visualization (which slot is freed first), and timing annotations.
  • From type-info.json (semantic): Allocation origin classification. A Vec created via Vec::with_capacity(1000) (initializer_kind: "vec_with_capacity") is labeled differently from one created via vec![1,2,3] (initializer_kind: "vec_macro"). An Rc::new is distinguished from a Box::new in the heap column. This classification drives color coding and grouping in the visualization.

This three-source memory view is only possible when the full pipeline is active. Without the analyzer, the macro cannot produce type-specific events (all allocations look the same). Without the runtime, there is no timing or drop order. Without the LSP, there is no field-level layout. The pipeline brings all three together, producing the most comprehensive memory ownership visualization achievable for Rust programs.
