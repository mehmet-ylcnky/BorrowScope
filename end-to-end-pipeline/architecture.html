2. Pipeline Architecture

The pipeline connects five components through well-defined data formats. Each component reads a specific input and produces a specific output, with no implicit dependencies or shared mutable state. This section describes the data flow, the orchestration command that automates the sequence, and the independence property that allows each component to be used in isolation.

2.1 Data Flow Overview

The pipeline has two parallel tracks that converge in the VS Code extension. The instrumentation track flows linearly: source code enters the analyzer, which produces type-info.json; the macro reads this file at compile time and emits track_* calls; the compiled binary executes and the runtime records events to events.json. The static analysis track operates independently: the LSP server loads the workspace into a Salsa database and answers ownership queries in real-time as the developer types. Both tracks produce data that the VS Code extension consumes: runtime events from the instrumentation track, and LSP responses from the static analysis track.

The data formats between components are deliberately simple and human-readable. type-info.json is a JSON file with per-function, per-variable entries containing boolean flags and string fields. events.json is a JSON array of timestamped event objects. LSP communication uses standard JSON-RPC over stdio. This choice enables easy debugging (developers can inspect intermediate files), easy testing (tests can construct JSON fixtures), and easy extension (new fields can be added without breaking existing consumers).

2.2 The Orchestration Command (borrowscope.runInstrumented)

The borrowscope.runInstrumented command automates the instrumentation track in sequence. When triggered (via the status bar button or command palette), it executes three stages: (1) run the analyzer binary on the workspace root to produce fresh type-info.json, (2) run cargo run on the workspace to compile and execute the instrumented program, producing events.json, and (3) enable the runtime overlay if not already active. The existing file watcher detects the new events file and triggers the merge automatically.

The command uses vscode.window.withProgress to show a notification with cancellation support. The status bar button updates in real-time to reflect the current stage: $(sync~spin) Analyzing... during type extraction, $(sync~spin) Compiling & running during execution, $(check) N events on success, or $(error) Pipeline failed on failure. Errors are caught at each stage with descriptive messages: "Analyzer failed (exit 1)" includes the first 200 characters of stderr, and "cargo run failed" indicates compilation or runtime errors. 

export async function executeE2E(outputChannel?, statusBar?): Promise<void> {
  const workspaceRoot = vscode.workspace.workspaceFolders[0].uri.fsPath;
  const analyzerPath = resolveAnalyzerPath();

  statusBar?.setRunning("Analyzing...");

  const result = await vscode.window.withProgress(
    { location: ProgressLocation.Notification, title: "BorrowScope: Running pipeline", cancellable: true },
    async (progress, token) => {
      // Stage 1: Analyze types
      progress.report({ message: "Analyzing types..." });
      const analyzerResult = await spawnProcess(analyzerPath, [workspaceRoot], workspaceRoot);
      if (analyzerResult.code !== 0) return { success: false, error: "Analyzer failed" };

      // Stage 2: Compile and run
      progress.report({ message: "Compiling & running..." });
      const runResult = await spawnProcess("cargo", ["run"], workspaceRoot);
      if (runResult.code !== 0) return { success: false, error: "cargo run failed" };

      // Stage 3: Count events
      const eventsCount = countEvents(workspaceRoot);
      return { success: true, eventsCount };
    }
  );

  if (result.success) {
    statusBar?.setSuccess(result.eventsCount);
    // Enable runtime overlay (file watcher triggers merge automatically)
    config.update("runtime.enabled", true, ConfigurationTarget.Workspace);
  } else {
    statusBar?.setError(result.error);
  }
}

2.3 Component Independence

A critical architectural property is that each component functions independently. The analyzer can generate type-info.json without the macro being installed. The LSP can analyze code without the runtime being present. The VS Code extension can render static visualizations without any runtime events. The macro can instrument code without the VS Code extension being active. This independence has three practical benefits:

  • Incremental adoption: A team can start with just the LSP (instant static feedback, no instrumentation needed), then add the analyzer + macro when they want runtime insights, without changing their development workflow.
  • Isolated testing: Each component has its own test suite that runs without dependencies on other components. The macro's 563 tests use fixture type-info.json files, not a live analyzer. The LSP's 107 tests spawn the server binary without the extension. The extension's 721 tests use mock data without a running LSP.
  • Graceful degradation: If the analyzer fails (e.g., workspace loading error), the macro falls back to generic tracking. If the runtime is not enabled, the extension shows only static visualizations. If the LSP is still loading, the extension returns cached or "loading" responses. No single component failure crashes the pipeline; each degrades to its independent baseline.

The pipeline command is an optimization, not a requirement. It orchestrates the components for convenience, but each component's contract (input format, output format) remains stable whether invoked by the pipeline or manually. This separation of orchestration from functionality ensures that the pipeline can evolve (adding new stages, changing execution order) without modifying the components themselves.
