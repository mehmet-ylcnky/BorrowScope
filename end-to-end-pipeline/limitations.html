10. Limitations and Future Work

The pipeline achieves its goal of one-click ownership visualization, but several limitations remain. Some are inherent to the approach (requiring compilation and execution for runtime data), some are engineering trade-offs (analyzer latency), and some represent future opportunities to further reduce friction. This section documents each limitation and the planned enhancements that would address them.

10.1 First-Run Analyzer Latency

The analyzer's workspace loading takes 30-40 seconds because it must resolve the entire dependency graph and build a complete Salsa database. This is the same cost that rust-analyzer pays on first open, and it is dominated by dependency resolution (downloading and parsing crate metadata) and sysroot discovery (finding the standard library source). Once loaded, type extraction for the project's own code completes in under 5 seconds.

Currently, the pipeline command always re-runs the analyzer from scratch, paying the 30-40 second cost on every invocation. This is conservative (guarantees fresh type-info) but wasteful when only the project's source changed (not its dependencies). A future optimization would implement incremental analysis: check if Cargo.lock has changed since the last analysis; if not, reload only the project's source files into the existing database. This would reduce subsequent runs from 35 seconds to under 5 seconds.

An even more ambitious optimization would persist the Salsa database to disk between runs (similar to rust-analyzer's workspace cache). On subsequent invocations, the analyzer would load the cached database and only recompute queries for changed files. This would bring the analyzer's warm-start time close to zero, making the pipeline feel instant for small edits.

10.2 Manual #[trace_borrow] Annotation

Currently, the developer must manually add #[trace_borrow] to each function they want instrumented. This creates friction: the developer must decide which functions to annotate, add the attribute, and remember to annotate new functions as they are written. Functions without the annotation produce no runtime events, creating gaps in the merge where those functions appear as "static_only."

The zero-cost property (no overhead when the track feature is disabled) makes it safe to annotate all functions permanently. However, adding the attribute to every function in a large project is tedious. A future enhancement would provide automatic annotation through one of three mechanisms:

  • Cargo subcommand: cargo borrowscope annotate would scan all .rs files and add #[trace_borrow] to every fn that doesn't already have it. Reversible via cargo borrowscope remove.
  • VS Code quick-fix: A code action that adds #[trace_borrow] to the current function, all functions in the file, or all functions in the project. Triggered via the lightbulb menu or a keyboard shortcut.
  • Crate-level attribute: #![trace_borrow_all] at the crate root would instruct the macro to instrument every function without individual annotations. This would require a new macro type (a crate-level proc-macro attribute).

10.3 Planned: Selective Instrumentation UI

Not every run needs full instrumentation. A developer investigating an Rc leak needs only Rc/Arc events. A developer debugging a move error needs only move and drop events. Full instrumentation produces many events that are irrelevant to the current investigation, increasing noise in the visualization and slightly increasing runtime overhead.

A planned enhancement would add a VS Code quick-pick menu before running the pipeline: "What do you want to track?" with options like [All events], [Rc/Arc only], [Moves and drops only], [Borrows only], [Async events only]. The selected option would configure the macro's event filter (already supported via #[trace_borrow(only = "Rc,Arc")]) before compilation, producing a focused event stream with less noise and lower overhead.

This selective instrumentation would also improve merge quality: fewer irrelevant events means fewer "runtime_only" entries that clutter the visualization. The merge's agreement statistics would be more meaningful when the event stream is focused on the ownership patterns the developer is investigating. The status bar button could show the active filter as a label: ▶ BorrowScope [Rc/Arc] to remind the developer which subset is being tracked.
