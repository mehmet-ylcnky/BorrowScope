8. Performance Budget

A multi-stage pipeline must be fast enough that the developer does not lose context while waiting. The pipeline's total latency is the sum of its stages, and each stage has been optimized to stay within a defined budget. This section measures each stage, reports end-to-end latency for typical projects, and quantifies the overhead of instrumentation on program execution.

8.1 Per-Stage Timing

Each pipeline stage has a distinct performance profile. Some stages are one-time costs (analyzer workspace loading), some scale with project size (compilation), and some scale with program behavior (runtime event count). 8.2 End-to-End Latency

The total time from button click to visualization update depends on whether the analyzer's workspace loading is needed. On first run (cold start), the pipeline takes 35-40 seconds, dominated by the analyzer's workspace loading (which loads all dependencies into the Salsa database). On subsequent runs (warm), if only the source code changed (not dependencies), the analyzer can skip workspace loading and only re-extract types, reducing the total to 5-10 seconds (compile + run + merge).

The pipeline command does not currently implement the "skip if fresh" optimization for the analyzer (it always re-runs from scratch). This is a conservative choice that guarantees correctness at the cost of the 30-40 second workspace loading on every run. A future optimization would check whether Cargo.lock has changed since the last analysis; if not, the workspace loading can be skipped and only type extraction re-runs (reducing analyzer time from 35s to <5s).

For the developer's perceived experience, the key metric is time from button click to seeing the first visual update. The status bar provides immediate feedback ("Analyzing..." appears within 100ms of clicking), and the merge + render completes within 200ms of the events file being written. The wait is in the middle stages (compilation and execution), which are inherent to the instrumentation approach and cannot be reduced by BorrowScope. The LSP's static analysis, by contrast, provides instant feedback (under 100ms after any edit) because it requires no compilation or execution.

8.3 Overhead of Instrumentation

When the track feature is enabled, each track_* call adds approximately 75 nanoseconds of overhead: ~30ns for the mutex lock acquisition, ~35ns for event construction (timestamp capture, string formatting), and ~10ns for the vector push. For a function that performs 20 ownership operations, the total overhead is approximately 1.5 microseconds, which is negligible compared to any I/O, allocation, or computation the function performs.

For compute-intensive code with very tight loops, the overhead can become measurable. A loop that iterates 1 million times with a tracked variable inside the loop body would add 75ms of overhead (1M * 75ns). The runtime mitigates this through event deduplication: LoopIteration events are recorded only for the first N iterations (configurable), not all of them. Ownership-relevant events (New, Borrow, Move, Drop) typically occur outside tight loops and are not affected by iteration count.

When the track feature is disabled (production builds), the overhead is exactly zero. The compiler inlines the identity functions and eliminates them completely. Binary size is unchanged. Runtime performance is unchanged. This zero-cost guarantee means the #[trace_borrow] annotations can remain in the source code permanently, activated only when the developer needs ownership visibility.
