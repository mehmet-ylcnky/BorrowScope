9. Test Coverage Across the Ecosystem

A multi-component pipeline is only as reliable as its weakest link. A bug in the analyzer's type extraction propagates through the macro into incorrect instrumentation, producing misleading runtime events that cause false divergences in the merge. To prevent this cascade, each component has its own comprehensive test suite, and the E2E test project validates the full chain end-to-end. This section documents the test counts, the cross-component validation strategy, and the zero-heuristics guarantee that testing enforces.

9.1 Per-Component Test Counts

Each component is tested independently with its own runner, fixtures, and assertions. The total exceeds 2,100 tests, with no single component having fewer than 100. The following table shows the breakdown:

The macro has the highest integration test count (376) because it must verify correct code generation for every combination of ownership pattern and type-info configuration. Each integration test compiles and executes an instrumented function, checking that the expected runtime events are produced. The VS Code extension has the highest overall count (721) because it covers 11 visualization views, each with multiple interaction scenarios, plus the merge layer's 64 divergence tests and the 18 E2E runner tests.

9.2 Cross-Component Validation

Individual component tests verify that each piece works correctly in isolation. But the pipeline's value comes from components working together, so cross-component validation is essential. The E2E test project (/tmp/e2e-test) exercises the full chain: the analyzer produces type-info.json for the project's source, the macro reads it during compilation, the runtime generates events, and the extension's tests verify that the merge produces correct MergedVariables.

The cross-component contract is enforced at the data format level. The macro's tests use fixture type-info.json files (committed to the repository) that match the schema the analyzer produces. If the analyzer changes its output format, the macro's tests fail immediately. Similarly, the extension's runtime parser tests use fixture events.json files matching the runtime's serde output. If the runtime changes its serialization, the extension's tests fail. This "contract by fixture" approach catches integration bugs without requiring all components to run simultaneously.

The VS Code extension's 18 E2E runner tests additionally validate the orchestration: they spawn fake analyzer binaries, fake cargo projects, and verify that the pipeline handles success, failure, cancellation, malformed output, and missing binaries correctly. These tests confirm that the glue code connecting components is robust even when individual stages fail or produce unexpected output.

9.3 Zero Heuristics Guarantee

A critical property maintained across the entire pipeline is the absence of heuristics. No component makes decisions based on string matching, naming conventions, or pattern guessing. This property is enforced by the test suite:

  • Analyzer: Tests verify that type aliases (type MyRc<T> = Rc<T>) are correctly classified as Rc (via ADT canonical path resolution, not display name matching). Tests verify that factory functions (fn create() -> Rc<T>) produce the correct initializer_kind based on return type, not function name.
  • Macro: Tests verify that the by_name fallback (which previously matched variables by name across functions, causing cross-function collisions) was removed. All lookups now use the strict (function_name, var_name, decl_index) triple.
  • LSP: Tests verify that ownership classification uses ty.as_adt().module().path_to_root() (semantic path), not ty.display().contains("Rc") (string matching). The ADT path for Rc resolves to alloc::rc::Rc regardless of imports or aliases.
  • Extension: The merge uses structured RuntimeEvent types (discriminated union), not string parsing of event names. The divergence detectors check specific boolean/numeric conditions, not patterns in description strings.

This zero-heuristics property is not merely a design choice; it is a testable invariant. The "Eliminating Heuristics" paper (v3.0) documented the removal of the last heuristic (the by_name fallback) and the addition of 563 tests verifying purely semantic behavior. The E2E pipeline preserves this property end-to-end: from the analyzer's first type query to the extension's last divergence check, every decision is grounded in compiler-grade semantic resolution.
