3. The type-info.json Bridge

The central integration point of the pipeline is type-info.json, a structured file that carries semantic type information from the analyzer to the macro. Without this file, the macro cannot distinguish an Rc::clone from a generic .clone(), or a Cow::Borrowed from a Cow::Owned. With it, the macro makes precise instrumentation decisions for 82 initializer categories, emitting type-specific tracking calls that produce semantically rich runtime events. This section documents the schema, how it is produced, how it is consumed, and how staleness is handled.

3.1 Schema Design

The type-info.json file is organized as a nested structure: at the top level, a by_function map keyed by function name, where each function contains a map of variable names to arrays of type entries (arrays because shadowing produces multiple variables with the same name). Each entry contains the full semantic characterization of one variable binding.

A single entry has over 40 fields organized into categories: identity (name, ty, file, line, column, function_name, decl_index), boolean type flags (is_rc, is_arc, is_box, is_weak, is_sync_weak, is_refcell, is_cell, is_mutex, is_rwlock, is_guard, is_vec, is_string, is_raw_ptr, is_mutable_raw_ptr, is_reference, is_mutable_reference, is_pin, is_cow, is_option, is_result, is_once_cell, is_maybe_uninit, is_channel, is_atomic, is_join_handle, is_closure, is_fn_ptr, is_future, is_iterator, is_callable, is_dyn_trait, is_union, is_static, is_const), semantic properties (copy_semantics, is_tuple_binding, is_mut_binding, binding_mode, contains_reference, is_ref_binding), and the critical dispatch field: initializer_kind. 

// Example entry for: let shared = Rc::new(Config::default());
{
  "name": "shared",
  "ty": "Rc<Config>",
  "is_rc": true,
  "is_arc": false,
  "is_box": false,
  "is_weak": false,
  "is_copy": false,
  "is_clone": true,
  "copy_semantics": false,
  "is_closure": false,
  "binding_mode": "move",
  "initializer_kind": "rc_new",
  "deref_chain": ["Config"],
  "type_arguments": ["Config"],
  "file": "src/main.rs",
  "line": 12,
  "column": 8,
  "function_name": "ownership_demo",
  "decl_index": 3
}

The initializer_kind field is the most important for the macro. It tells the macro exactly which track_* function to emit. The analyzer resolves this by examining the initializer expression: if it matches Rc::new(...), the kind is "rc_new". If it matches Cow::Borrowed(...), the kind is "cow_borrowed". If it matches thread::spawn(...), the kind is "join_handle". The analyzer uses semantic path resolution (not string matching) to determine these kinds, ensuring that type aliases and re-exports are handled correctly.

3.2 How the Analyzer Produces It

The analyzer loads the Rust workspace using ra_ap_load_cargo::load_workspace_at, which resolves all dependencies, discovers the sysroot, and builds a complete Salsa database. It then iterates every function in every file, and for each let binding, queries the hir::Type to extract all boolean flags and the initializer expression to determine the initializer_kind.

Type resolution uses the same ra_ap_* APIs as the LSP server: ty.is_copy(db), ty.as_adt() for struct/enum classification, module.path_to_root(db) for canonical path resolution, and sema.resolve_path() for expression analysis. The key difference from the LSP is that the analyzer writes its results to a file (for the macro to consume at compile time) rather than serving them via protocol (for the editor to consume in real-time).

On a typical project, the analyzer resolves 94-100% of variable types. The remaining unresolved types are usually in generated code (proc-macro output not available without a proc-macro server) or in conditional compilation blocks. Unresolved variables receive "initializer_kind": null, causing the macro to fall back to generic tracking for those bindings.

3.3 How the Macro Consumes It

At compile time, the #[trace_borrow] proc-macro attribute loads type-info.json from CARGO_MANIFEST_DIR/.borrowscope/type-info.json. The file is loaded once (on first access) and cached in a static OnceCell for the duration of compilation. For each let binding in the function body, the macro looks up the variable's entry by (function_name, var_name, decl_index) and reads the initializer_kind field.

The dispatch logic is a match on the initializer_kind string, mapping each to a specific transformation. For example, "rc_new" wraps the initializer with borrowscope_runtime::track_rc_new(name, expr), which records an RcNew event with strong_count and weak_count. "cow_borrowed" wraps with track_cow_borrowed(name, expr), recording a CowBorrowed event. Without the type-info lookup, all variables would receive the generic track_new(name, expr) which records only a basic New event without type-specific metadata.

3.4 Staleness and Refresh

The type-info.json file is a point-in-time snapshot. The moment the developer edits source code (adds a variable, changes a type, renames a function), the file becomes potentially stale. A stale file causes incorrect instrumentation: a variable that was changed from Rc to Arc will still be instrumented as Rc until the analyzer re-runs. A new variable added after the last analysis will have no entry, causing the macro to fall back to generic tracking.

The pipeline command solves this by always running the analyzer first, before compilation. This guarantees freshness: the type-info.json is regenerated from the current source before the macro reads it. In manual workflows (without the pipeline command), the developer must remember to re-run the analyzer after edits. If they forget, the instrumentation will be partially incorrect: existing variables may have wrong kinds, and new variables will lack entries.

The LSP server does not suffer from this problem because it uses Salsa's incremental computation (always-fresh, recomputes on every edit). This is precisely why the LSP was created: it provides the same semantic information as type-info.json but without the staleness issue. The trade-off is that the LSP cannot feed the macro (the macro runs at compile time, before the LSP is even started). The type-info.json file remains necessary as the bridge between pre-build analysis and compile-time instrumentation.
