5. Runtime Event Generation

Once the macro has instrumented the code and the program is compiled with the track feature enabled, execution produces a stream of ownership events. The borrowscope-runtime library manages the recording infrastructure: a thread-local event buffer, nanosecond timestamps, automatic variable ID generation, and JSON export. This section describes the recording architecture, shows how source code maps to events in practice, and explains the export mechanism that delivers events to the VS Code extension.

5.1 Event Recording Architecture

The runtime uses a global TRACKER protected by a parking_lot::Mutex. Each track_* function acquires the lock, records one event, and releases the lock. Events are stored in a Vec<Event> that grows as the program executes. Timestamps are captured via std::time::Instant::now() relative to a baseline established at tracker initialization, giving nanosecond-precision elapsed time from program start.

Variable IDs are generated automatically in the format "name_counter": the first variable named "data" gets ID "data_0", the second (shadowing) gets "data_1", etc. The counter is global across all variables, ensuring uniqueness. This ID scheme is the key to the merge: the VS Code extension strips the counter suffix to recover the variable name, then matches by name + declaration order against the static analysis output.

The lock-based design prioritizes correctness over performance. Each event recording is atomic (no partial events), and the global ordering is deterministic for single-threaded programs. For multi-threaded programs, events from different threads interleave based on lock acquisition order. The overhead is approximately 75 nanoseconds per event (lock acquire + event construction + lock release), which is negligible for typical functions with 10-50 ownership operations but may become measurable for tight loops with millions of iterations.

5.3 Export to JSON

At program exit (or when explicitly requested via borrowscope_runtime::get_events()), the accumulated events are available as a Vec<Event>. The typical export pattern writes them to .borrowscope/events.json using serde_json serialization. The E2E test project demonstrates the standard export code: 

fn main() {
    borrowscope_runtime::reset(); // clear any previous events

    ownership_demo();  // instrumented functions record events
    move_demo();

    // Export events to JSON for VS Code consumption
    std::fs::create_dir_all(".borrowscope").ok();
    let events = borrowscope_runtime::get_events();
    std::fs::write(
        ".borrowscope/events.json",
        serde_json::to_string_pretty(&events).unwrap(),
    ).unwrap();
    println!("Exported {} events", events.len());
}

The file is written atomically in the sense that std::fs::write creates a complete file in one operation (no partial writes visible to the file watcher). The VS Code extension's RuntimeWatcher detects the file creation or modification and triggers the merge pipeline automatically. The developer does not need to manually reload or refresh; the visualization updates within 100ms of the file being written.

The JSON format uses serde's default externally-tagged enum serialization: each event is an object with a single key (the event type name) whose value contains the event fields. For example: {"RcNew": {"timestamp": 100, "var_name": "shared", "var_id": "shared_1", "type_name": "Rc<Config>", "strong_count": 1, "weak_count": 0}}. This format is human-readable (developers can inspect the file directly for debugging), self-describing (each event carries its type name), and easily extensible (new event types can be added without breaking existing parsers).
