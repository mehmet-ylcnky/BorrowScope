6. Static Analysis via LSP

While the instrumentation track (analyzer -> macro -> runtime) requires compilation and execution, the static analysis track operates continuously in the background. The borrowscope-lsp server loads the workspace once, then provides ownership analysis in real-time as the developer types. It answers queries about any function within 100ms, without requiring the program to be compiled or run. This section describes how the LSP operates in parallel with the instrumentation track, what it provides that runtime cannot, and what runtime provides that the LSP cannot.

6.1 Parallel Analysis (No Instrumentation Needed)

The LSP server starts when VS Code opens a Rust project. It loads the workspace via ra_ap_load_cargo (the same expensive 30-40 second operation as the analyzer), builds a Salsa incremental computation database, and then responds to queries instantly. Critically, the LSP operates on the source code as written, not on instrumented code. It does not need #[trace_borrow] annotations, does not need the track feature enabled, and does not need the program to compile successfully. Even partially written code (mid-edit, with syntax errors in other functions) can be analyzed for the functions that are syntactically complete.

This means the developer gets ownership feedback immediately upon opening a file, long before the instrumentation pipeline has a chance to run. The static analysis provides the baseline visualization: ownership category annotations, borrow lifelines, conflict highlights, cross-function annotations. When the developer later clicks the "Run Instrumented" button, the runtime events overlay on top of this baseline, enriching it with observed behavior. The two tracks are additive: static analysis provides the structure (what exists, what is predicted), runtime adds the dynamics (what actually happened, with what timing).

The LSP also survives code changes without re-running. When the developer edits a file, Salsa recomputes only the affected queries (typically under 50ms for a single-function edit). The static visualization updates almost instantaneously. By contrast, the runtime data becomes stale on any edit (it reflects the previous execution, not the current code). This asymmetry is resolved by the merge layer's agreement classification: after an edit, static variables show as "match" or "static_only" while runtime variables from the previous run show as "runtime_only" until the pipeline is re-run.

6.2 What the LSP Provides That Runtime Cannot

The LSP's static analysis has four capabilities that are impossible for runtime observation alone:

  • All-path analysis: The LSP sees every branch of every if, match, and loop. It reports conflicts that could occur on any execution path, not just the one that was taken. A borrow conflict inside a rarely-executed error handler is visible immediately, without needing to trigger that error path.
  • Cross-function borrow tracking: The LSP resolves call targets via sema.resolve_path() and traces borrows into callees. It knows that validate(&db) borrows db as a shared reference into the validate function, even without executing that function. Runtime observation only sees events within instrumented functions.
  • Memory layout computation: The LSP queries ty.layout(db) to determine sizes, alignments, and field offsets for any type. It reconstructs the stack frame showing each variable's byte offset and internal structure. This information is not available at runtime without platform-specific introspection.
  • Instant feedback: The LSP responds to queries in under 100ms after the initial load. The developer sees ownership information while typing, without waiting for compilation or execution. This immediacy is the primary reason the LSP was created as a complement to the runtime approach.

6.3 What Runtime Provides That the LSP Cannot

Conversely, the runtime has four capabilities that static analysis fundamentally cannot achieve:

  • Actual reference counts: The LSP knows a variable is Rc, but not whether its strong_count is 1 or 100. Only runtime observation can track the count at each point, detect when it peaks, and determine whether it ever reaches zero. The divergence detector uses this to identify Rc leaks and reference cycles.
  • Precise timing: The LSP knows a variable's scope spans lines 5-12, but not how long it lives in wall-clock time. Runtime records nanosecond timestamps, revealing that a borrow held across an await lasted 45ms (a potential performance issue) or that a variable lived only 200ns (suggesting it was never used meaningfully).
  • Drop order: While Rust specifies LIFO destruction within a scope, the actual order can be complex with nested scopes, early drops, and conditional destruction. Only runtime observation reveals the exact sequence: "clone1 dropped first (#1), then shared (#2), then data (#3)."
  • Branch decisions: The LSP sees that a move could happen in an if block, but runtime shows whether it did. This enables the conditional_move divergence: the static analysis predicted a possible move, but runtime never observed it (the branch was not taken in this execution).

Together, these complementary capabilities justify the two-track architecture. Neither alone provides a complete picture. The merge layer (Section 7) combines them into a unified view where static predictions and runtime observations are shown side-by-side, with divergences highlighted where they disagree.
