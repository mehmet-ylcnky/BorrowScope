1. Introduction

1.1 The Vision: One Click from Source to Visualization

The ultimate goal of the BorrowScope project is to make Rust's ownership system visible without disrupting the development workflow. A developer writes code, clicks a single button in the editor, and within seconds sees a complete ownership visualization: which variables are borrowed, where moves happen, which Rc clones share ownership, where conflicts exist, and how the observed runtime behavior compares to static predictions. No terminal commands, no manual annotation of functions, no switching between tools. The ownership system becomes as visible as syntax highlighting.

This vision requires five distinct capabilities working together: type extraction (knowing what each variable is), code instrumentation (adding tracking calls without manual effort), event recording (capturing what happens at runtime), static analysis (predicting what could happen without running), and visualization (rendering both perspectives in the editor). Each capability was developed as an independent component with its own paper, test suite, and API. This paper shows how they connect into a single automated pipeline triggered by one button click.

1.2 The Five Components

The BorrowScope ecosystem consists of five Rust/TypeScript crates, each with a clearly defined role and interface:

Component Language Role Input Output
borrowscope-analyzer Rust Extract semantic type information Rust workspace (Cargo.toml) type-info.json
borrowscope-macro Rust (proc-macro) Instrument code with tracking calls Source code + type-info.json Instrumented binary
borrowscope-runtime Rust Record ownership events during execution Instrumented program execution events.json (88 event types)
borrowscope-lsp Rust Real-time static ownership analysis Source code (via VFS) JSON-RPC responses (5 custom requests)
borrowscope-vscode TypeScript Visualization + merge + orchestration LSP responses + events.json 11 interactive views + inline decorations

Each component can be used independently. The analyzer works without the macro. The LSP works without the runtime. The VS Code extension works with only static analysis (no runtime events). But when all five operate together, the developer gets the complete picture: instant static feedback while editing, precise runtime validation after execution, and divergence detection where the two perspectives disagree.

1.3 Why a Unified Pipeline Matters

Without the orchestration command, using the full BorrowScope ecosystem requires five manual steps: (1) run cargo run -p borrowscope-analyzer -- . to generate type-info.json, (2) add #[trace_borrow] annotations to target functions, (3) run cargo run to execute the instrumented program, (4) verify that .borrowscope/events.json was produced, and (5) enable borrowscope.runtime.enabled in VS Code settings. Each step requires context switching between the editor and terminal, knowledge of specific command syntax, and awareness of file paths. Any step failing (stale type-info, missing annotation, feature flag not set) breaks the chain silently.

The unified pipeline reduces this to one action: click the status bar button (or invoke borrowscope.runInstrumented from the command palette). The orchestration command handles every step internally: resolves binary paths, spawns the analyzer, waits for completion, triggers compilation and execution, monitors for the events file, and enables the runtime overlay automatically. Errors at any stage are caught and reported as VS Code notifications with actionable messages. The developer never needs to know the internal mechanics; they see only the result.

This integration also solves the staleness problem. When code changes, the type-info.json file becomes outdated. Manual workflows often suffer from stale type information causing incorrect instrumentation (e.g., a variable that changed from Rc to Arc still being instrumented as Rc). The pipeline always runs the analyzer first, ensuring type information is fresh for every instrumented run. The developer cannot accidentally use stale data because the pipeline enforces the correct ordering.

1.4 Contributions

This paper makes the following contributions. Together, they demonstrate that a complex multi-component analysis ecosystem can be delivered as a seamless one-click experience without sacrificing the modularity or testability of individual components.

  1. A one-click orchestration command (borrowscope.runInstrumented) with a status bar button that automates the full pipeline: type analysis, compilation, execution, and merge trigger. The button shows live progress and error state.
  2. The type-info.json schema as the central bridge between static analysis (analyzer) and runtime instrumentation (macro), enabling 82 semantic dispatch categories with zero heuristics.
  3. A documented performance budget across all pipeline stages: analyzer (30-40s one-time), macro (negligible), runtime (~75ns/event), LSP (<100ms/function), merge (<100ms for 1000 events), totaling under 45 seconds for a complete first-run cycle.
  4. Cross-component validation through 2,100+ tests that exercise both individual components and the full end-to-end flow, ensuring that changes to any component do not break the pipeline contract.
  5. Zero heuristics maintained throughout the entire pipeline: every decision (type classification, instrumentation dispatch, borrow scope computation, conflict detection) is based on semantic resolution through compiler APIs, never on string matching or naming conventions.
