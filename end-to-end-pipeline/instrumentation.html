4. Instrumentation via Macro

The borrowscope-macro crate provides the #[trace_borrow] procedural macro attribute that transforms function bodies to emit ownership tracking calls. The macro operates at compile time, reading the type-info.json file produced by the analyzer and using the initializer_kind field to decide which specific track_* function to emit for each variable binding. This section describes the attribute's behavior, the 82 dispatch categories, and the zero-cost property that makes instrumentation safe to commit to version control.

4.1 The #[trace_borrow] Attribute

The macro is applied to a function definition: #[trace_borrow] fn example() { ... }. When the Rust compiler expands this attribute, the macro parses the function body's token stream, identifies all let bindings and ownership-relevant expressions (method calls, assignments, closures, unsafe blocks), and wraps each with the appropriate track_* call from borrowscope-runtime. The original function signature remains unchanged; only the body is transformed.

The transformation preserves semantics: each track_* function is designed as a pass-through that records an event and returns its argument unchanged. For example, track_rc_new("shared", Rc::new(Config::default())) records an RcNew event and returns the Rc<Config> value. The type system guarantees that the instrumented code compiles if and only if the original code compiles: no type errors are introduced by the transformation. 

// Before: original source code
fn ownership_demo() {
    let data = vec![1, 2, 3];
    let shared = Rc::new(Config::default());
    let clone1 = Rc::clone(&shared);
    let r = &data;
    println!("{:?} {:?}", r, clone1);
}

// After: macro-expanded (simplified)
fn ownership_demo() {
    let data = track_new("data", vec![1, 2, 3]);
    let shared = track_rc_new("shared", Rc::new(Config::default()));
    let clone1 = track_rc_clone("clone1", "shared", Rc::clone(&shared));
    let r = track_borrow("r", &data);
    println!("{:?} {:?}", r, clone1);
    track_drop_batch(&["r", "clone1", "shared", "data"]);
}

Notice that data gets track_new (generic creation), shared gets track_rc_new (Rc-specific with ref counts), clone1 gets track_rc_clone (records source variable), and r gets track_borrow (records borrower/owner relationship). At the end of the scope, track_drop_batch records the destruction sequence. Each decision was made by looking up the variable in type-info.json and reading its initializer_kind.

4.2 Semantic Dispatch (82 Categories)

The macro supports 82 distinct initializer_kind values, each mapping to a specific track_* function. These categories cover the full spectrum of Rust's ownership patterns:

Category Group initializer_kind values track_* function
Smart Pointers rc_new, arc_new, box_new, box_block track_rc_new, track_arc_new, track_box_new, track_box_from_raw
Weak References weak_new, weak_clone, weak_upgrade track_weak_new, track_weak_clone, track_weak_upgrade
Interior Mutability refcell_new, cell_new, mutex_new, rwlock_new track_refcell_new, track_cell_new, track_lock_guard_acquire
Clone-on-Write cow_borrowed, cow_owned track_cow_borrowed, track_cow_owned
Concurrency join_handle, channel_new, atomic_new track_thread_spawn, track_channel, track_atomic_new
Lazy Init once_cell_new, once_lock_new, maybe_uninit_new track_once_cell_new, track_once_lock_new, track_maybe_uninit_new
Pinning pin_new track_pin_new
Time duration_new, instant_new track_duration_new, track_instant_new
Fallback null / unknown track_new (generic)

Each category produces a runtime event with type-specific metadata. An RcNew event includes strong_count and weak_count. A ThreadSpawn event includes the thread ID. A CowBorrowed event records that the Cow holds borrowed data (not owned). This metadata flows through the runtime into the VS Code extension, where it drives specialized visualizations: the reference count chart needs strong_count history, the cross-references view needs thread/channel relationships, and the divergence detector needs the precise event type to classify issues.

4.3 Zero-Cost When Disabled

The borrowscope-runtime crate uses a Cargo feature flag (track) to control whether events are actually recorded. When the feature is enabled (features = ["track"] in Cargo.toml), all track_* functions record events to the thread-local buffer. When the feature is disabled (the default), all track_* functions are defined as identity functions that simply return their argument: 

// When "track" feature is ENABLED:
pub fn track_rc_new<T>(name: &str, rc: Rc<T>) -> Rc<T> {
    let strong = Rc::strong_count(&rc);
    let weak = Rc::weak_count(&rc);
    TRACKER.lock().record(Event::RcNew { var_name: name, strong_count: strong, weak_count: weak, .. });
    rc // pass through unchanged
}

// When "track" feature is DISABLED:
#[inline(always)]
pub fn track_rc_new<T>(_name: &str, rc: Rc<T>) -> Rc<T> {
    rc // identity - compiler inlines this away completely
}

When disabled, the compiler's optimizer inlines the identity function and eliminates it entirely. The resulting binary is byte-for-byte identical to one compiled without the macro (verified through binary diffing). This means developers can commit #[trace_borrow] annotations to their repository permanently: in production builds (without the track feature), there is zero runtime overhead, zero binary size increase, and zero behavioral change. The annotations become active only when explicitly opted into via features = ["track"], making them safe for continuous use throughout the development lifecycle.

The pipeline command compiles with the track feature enabled automatically (it passes no special flags because the demo project's Cargo.toml already specifies features = ["track"] in the dependency). Production builds omit this feature, getting the zero-cost guarantee. This separation allows the same codebase to support both instrumented development builds and zero-overhead production builds without any code changes or conditional compilation in the application code itself.
